# 47 · ADR-0015 최종 검토 보고서 — UserId 선점 · 변경 · 인증 연속성

> **작성 2026-09-06** · 대상 = [46 ADR-0015](46-adr-0015-userid-handle-passphrase.md)(📐 D-32) · 브랜치 `feat/userid-handle`
> **검토 요청(사용자 09-06)**: *"UserId로 상호 인증했을 때 ① 특정 조건에서 UserId를 다른 사람에게 선점당할 수 있는가 ② UserId를 변경했을 때 인증이 유지될 수 있는가. PeerId는 유지되는 값이니 참조할 수 있을 것 같은데, UserId도 '값'과 'UserKey' 방식으로 나눠 UserId가 변경되는 경우를 감안한 구조가 필요한지."*
> **결론 먼저**: **필요하다.** 46 §3-1의 *"UserId = H(handle ‖ KP)"* 는 **변경에 취약**(암호를 바꾸면 남에게 다른 사람이 된다)하고 **서버 이름공간 보호가 약하다**(UserId가 공개값이라 누구나 가명을 계산). **3층 구조**(PeerId 앵커 · 무작위 UserKey · 핸들+암호는 "문 열쇠")로 개정한다 — §4. 선점은 **구조적으로 불가능**하게 되고(§2), 변경은 **후계 증명서**로 연속된다(§3).

## 0. 한 장 요약

| 질문 | 46 원안(H(handle‖KP)) | **개정안(3층)** |
|---|---|---|
| 남이 내 UserId를 **선점**할 수 있나 | 핸들만으로는 불가(KP 필요) · 그러나 **약한 암호 추측 = 완전 탈취** · 서버 가명은 공개값에서 계산 가능 → **이름공간 오염 가능** | **불가** — UserId = H(무작위 UserKey 공개키) · 서버 쓰기는 UserKey 서명 요구 · 핸들은 라벨(중복 허용 · 충돌 경고) |
| **암호를 바꾸면** 인증이 유지되나 | ✗ UserId가 바뀐다 → 상대에게 **다른 사람**(TOFU 지문 변경과 같은 고통) · 내 기기 전부 재입력 | ✅ **UserId 불변** — 암호는 UserKey를 감싸는 열쇠일 뿐(재래핑) · 상대는 아무것도 모른다 |
| **핸들을 바꾸면** | ✗ 사용자 변경과 같다 | ✅ 라벨 변경 — `UserHello`로 새 이름 통지(FR-D-9 결) |
| **기기를 잃으면**(폐기) | 암호 변경 = 새 UserId(= 위와 같은 고통을 폐기 수단으로 씀) | **UserKey 교체(rotation) + 옛 키가 서명한 후계 증명서** → 상대는 스레드·핀을 새 UserId로 접는다 · 잃은 기기는 폐기 목록 · ⚠️ 경쟁 시 **정직한 충돌 표시**(§3-3) |
| PeerId를 앵커로 쓸 수 있나 | 부분(핀은 PeerId) | ✅ **핀·세션·후계 판정의 앵커 = PeerId**. "신원 신뢰는 키에"(DR-28)를 사용자 층까지 확장 |
| 비용 | — | 서명 원시 1종 추가(Ed25519 · 새 의존 1 · §5) · 슬라이스 S0에 +1일 · S2에 +1일 |

## 1. 문제 정의 — "UserId"라는 말이 세 가지를 뭉뚱그렸다

| 층 | 무엇 | 성질 | 46 원안에서의 자리 |
|---|---|---|---|
| **① 라벨** | 핸들("kiros33") | 사람이 고른다 · **유일하지 않다** · 바뀐다 | UserId 솔트 재료 |
| **② 신원값** | 남이 나를 가리키는 32B | **바뀌면 안 된다**(스레드·핀·차단의 키) | `H(handle‖KP)` ← ★ 라벨과 비밀에 묶여 **둘 중 하나만 바뀌어도 신원이 바뀐다** |
| **③ 비밀** | 패스프레이즈 | 바꿀 수 있어야 한다(유출·분실) | PSK·RID·래핑 재료 |

> 원안의 결함 한 줄: **②를 ①과 ③에서 파생시켜서, ③을 바꾸는 정당한 행위(분실 대응)가 ②를 파괴한다.** ADR-0007이 UserId를 "장기 키"로 둔 이유가 정확히 이것이었고, 46은 경량화하면서 그 성질을 잃었다. 사용자의 지적("값과 UserKey 방식으로 나눠야 하지 않나")이 맞다.

## 2. 선점(pre-emption) 분석

### 2-1. 원안에서 "선점"이 되는 조건

| # | 조건 | 결과 | 심각도 |
|:--:|---|---|:--:|
| P-1 | 남이 **같은 핸들 + 같은 암호**를 쓴다(우연 또는 추측) | 같은 UserId → 내 PSK 세션에 들어온다 = **내 기기 전부와 동등**(A-1의 비밀 판) | 🔴 |
| P-2 | 남이 **같은 핸들 + 다른 암호** | 다른 UserId. 목록에 같은 이름이 둘 → 현행 `name_conflict` 경고와 같은 급 | 🟡(표시 문제) |
| P-3 | 컨텐츠 서버에서 **내 UserId를 본 사람**(UserHello로 공개된다)이 가명 `HMAC(server_salt, UserId)`를 계산해 **내 이름공간에 먼저 쓴다/채운다** | 서버가 UserKey 없이 UserId만으로 인증하면 **이름공간 오염·쿼터 소진** | 🔴 |
| P-4 | 릴레이 `RID_pair` 만남 지점 점유(1 RID = 1 연결) | KP 없이는 계산 불가 → 불가. KP를 아는 남 = P-1 | — |

P-1은 **암호 강도 문제**이지 구조 문제가 아니다(온라인 추측만 가능 — 46 §3-3). **P-3이 구조 문제**다: UserId를 "값"으로만 두면 서버가 "이 값의 주인"을 확인할 방법이 없다.

### 2-2. 개정안에서

| # | 개정안 |
|:--:|---|
| P-1 | 여전히 암호 강도 문제. 단 **탈취 범위가 줄어든다** — 암호를 안 남이 얻는 것은 "PSK 세션 진입 + 래핑 해제"이며, 그 순간 UserKey를 복제해 가므로 **그 뒤 암호를 바꿔도 남은 UserKey를 쥐고 있다** → 반드시 **UserKey 교체**(§3-2)까지 해야 끝난다. UI가 "암호 변경"과 "침해 대응(키 교체)"을 **다른 버튼**으로 둔다 |
| P-2 | 동일(라벨 충돌 경고). 핸들은 유일성을 주장하지 않는다 |
| P-3 | **불가** — 서버 쓰기는 **UserKey 서명 챌린지**로만 인증. UserId를 알아도 서명을 못 만든다 |
| P-4 | 동일 |

> ★ **"선점"은 등록소가 있을 때 생기는 개념**이다. 이 제품에는 등록소가 없고(DR-1), 핸들은 유일하지 않으며, 신원값은 256비트 무작위 키에서 나온다 — **선점할 대상 자체가 없다.** 유일하게 등록소처럼 동작하는 곳(컨텐츠 서버 이름공간)은 서명으로 막는다. 핸들 유일성을 원한다면 그것은 모드 ③(Registered · 조직 명부)의 일이고 여기서 다루지 않는다.

## 3. 변경(rotation) 분석 — 인증 연속성

### 3-1. 무엇이 바뀔 수 있고, 각각 상대에게 어떻게 보이나

| 바뀌는 것 | 원안 | **개정안** |
|---|---|---|
| **핸들** | UserId 변경 = 다른 사람 | 라벨만. `UserHello{name}` 갱신 · 상대 목록의 이름이 바뀐다(FR-D-9) |
| **패스프레이즈** | UserId 변경 = 다른 사람 · 내 기기 전부 재입력 | **UserId 불변.** UserKey·마스터 키를 새 KP로 **재래핑**(재암호화 없음 — V1-4의 값) · 내 기기는 새 암호 입력 시 **PSK만 갱신**(기기 목록·기록 그대로) |
| **기기 추가** | PSK 세션 성립 = 소속 | 동일 + 기존 기기가 **서명된 기기 목록 version+1** 발행 → 상대가 목록을 검증(A-1 방어가 "재확인"에서 **서명**으로 승격) |
| **기기 분실**(폐기) | 암호 변경 = 신원 포기 | **UserKey 교체**: 새 키 생성 → `Succession{old_pub, new_pub, revoked=[P_lost], ver, sig_old, sig_new}` → 내 기기들이 다음 세션에서 상대에게 제시 → 상대는 **스레드·핀·차단을 새 UserId로 접는다**(병합 · 대화 연속) · 잃은 기기는 `revoked` |
| **UserKey 분실**(전 기기 동시 소실 · 암호도 잃음) | 신원 재생성 | 동일 — 재생성. 단 **PeerId 앵커**가 남아 있으면 상대에게 *"이 기기(P1)는 예전 X였다 — 병합할까"* 를 **사용자 확인**으로 제안(자동 병합 금지 · §3-3) |

### 3-2. 후계 증명서(Succession) — 왜 "옛 키의 서명"이 근거가 되나

```text
Succession v1 {
  old_user_pub, new_user_pub,
  devices:  [PeerId …]        ← 새 UserId 소속(서명된 기기 목록의 첫 버전)
  revoked:  [PeerId …]        ← 잃은 기기
  version:  u64 (옛 목록 version + 1)
  issued_at,
  sig_old:  Sign(old_key, 위 전부)      ← "예전 나"가 인정한다
  sig_new:  Sign(new_key, 위 전부)      ← "새 나"가 받는다
}
```

상대의 검증 = ① `sig_old`가 **내가 핀한 옛 UserId(= old_pub)** 로 검증되고 ② 이 증명서를 **내가 이미 핀한 PeerId**(Noise로 소유 증명된 기기)가 세션 위로 제시했고 ③ `version`이 본 최대값보다 크다 → **스레드·핀을 new로 접는다**(옛 기록은 그대로 · 표시만 병합). **세 근거가 전부 "이미 신뢰한 것"에서 나온다** — 새 신뢰를 만들지 않는다.

### 3-3. ⚠️ 풀리지 않는 경우 — 폐기 경쟁(ADR-0007 §9)과 정직한 충돌

UserKey가 **모든 기기에 복제**돼 있으므로(개정안의 전제 · 아래 §4-2) **잃은 기기도 옛 키로 후계 증명서를 만들 수 있다.** 나와 공격자가 각각 `version n+1`을 만들면 상대는 둘 다 검증에 성공한다 — ADR-0007이 "모든 기기 복제(안 A)"를 버린 바로 그 이유다.

| 안 | 내용 | 판정 |
|---|---|---|
| ⓐ 높은 version 승리 | 공격자가 이긴다(ADR-0007 §9 논증) | ✗ |
| ⓑ 먼저 도착 승리 | 운 · 공격자가 먼저 접촉하면 진다 | ✗ |
| **ⓒ 경쟁 = 충돌 표시 · 사람이 정한다** | 상대 화면에 *"홍길동의 기기 P1과 P3이 서로 다른 후계를 주장합니다"* — 둘 다 **미확정** · 스레드는 옛 UserId에 머문다 · 상대가 다른 채널로 확인 후 하나를 고른다 | ✅ **채택** — 자동으로 틀리는 것보다 정직하다 |
| ⓓ 주 기기 전용 키(ADR-0007 원안) | 경쟁 자체가 없다 | v2 승격 경로로 유지 — 이번 경량판은 ⓒ |

> 완화 두 가지: **(1) 시간 우위** — 정당한 사용자는 분실 즉시 교체한다. 공격자의 후계가 도착하기 전에 정당 후계가 `version n+1`로 상대에게 닿아 있으면 공격자의 `n+1`은 **"이미 같은 version을 봤다 + 다른 키"** 로 충돌 표시된다. **(2) 잃은 기기의 PSK가 죽는다** — 암호를 동시에 바꾸면 잃은 기기는 내 다른 기기와 **더는 세션을 못 만든다**(따라잡기·sender copy 차단). 남는 것은 "제3자에게 옛 키로 서명하는 능력"뿐이고 그것이 ⓒ로 드러난다.

## 4. 개정 구조 — 3층 (46 §3-1 대체)

### 4-1. 층과 역할

```text
③ 문 열쇠   handle + passphrase ──PBKDF2──► KP ──► PSK(형제 기기 세션) · RID_pair(만남) · K_wrap_user(래핑)
                                                     ★ 신원이 아니다. 바꿔도 아무도 모른다.
② 신원      UserKey = 무작위 Ed25519 쌍(최초 기기가 1회 생성 · 형제 기기에 PSK 세션으로 복제 · 디스크에는 K_wrap_user로 봉인)
            UserId  = SHA-256("nbeep-user-id-v2" ‖ UserKey.pub)          ★ 남이 나를 가리키는 값 · 불변
            서명 대상 = UserHello(기기 목록·version) · Succession · 서버 인증 챌린지
① 앵커      PeerId(기기 정적 키 · 불변) — 핀·세션·후계 판정의 근거. "신원 신뢰는 키에"(DR-28)
```

| 규칙 | 이유 |
|---|---|
| UserId는 **UserKey에서만** 나온다 — 핸들·암호 무관 | §1의 결함 제거 |
| 핸들은 `UserHello.name`으로만 다닌다(서명 대상 아님) | ADR-0007 §4 "표시 이름은 서명 대상이 아니다" 그대로 |
| **부트스트랩**: 핸들·암호를 넣은 첫 기기가 UserKey를 만든다. 두 번째 기기는 PSK 세션에서 **암호문(K_wrap_user 봉인) 그대로** 받는다 | 세션은 이미 PSK로 인증·암호화돼 있으므로 평문 전달도 가능하나, 봉인본을 그대로 옮기면 저장 형식이 하나로 통일된다 |
| **동시 부트스트랩**(두 기기가 각자 먼저 만듦 → UserKey 둘) | 첫 PSK 세션에서 `created_at`이 빠른 쪽(같으면 pub 사전순)이 이기고, 진 쪽이 **자기 키로 후계 증명서**를 만들어 상대들에게 병합시킨다 — §3-2와 같은 기구 |
| 서명 검증 실패 = **세션은 유지, 소속만 미확정** | 다른 사용자와의 세션은 UserId가 틀려도 대화는 된다(PeerId 신뢰는 그대로) |

### 4-2. UserKey를 전 기기에 복제하는 이유(ADR-0007 안 A를 알면서 택하는 이유)

| | 주 기기 전용(ADR-0007 B) | **전 기기 복제(개정안)** |
|---|---|---|
| 기기 추가 | 주 기기가 켜져 있어야 | **아무 기기에서나**(사용자 요구 "아이디/패스워드처럼") |
| 폐기 경쟁 | 없음 | 있음 → §3-3 ⓒ 정직한 충돌 |
| 복구 시드 | 필요 | 불필요(암호 + 살아 있는 기기 1대) |
| DR-1 마찰 | 시드 보관 책임 | 암호 하나 |

> 사용자 요구의 무게가 "일반 메신저처럼 · 승인 없이"에 있으므로 복제를 택하되, **주 기기 승격은 v2 경로로 남긴다**(그때 UserKey는 주 기기만 쥐고 나머지는 서명된 인증서만 — ADR-0007 원안). 지금의 데이터 형식(UserId = H(pub) · Succession · 기기 목록 version)은 **그 승격에서 하나도 안 바뀐다.**

### 4-3. 46 본문에 반영할 개정 목록

| 46 위치 | 원안 | 개정 |
|---|---|---|
| §3-1 파생식 | `UserId = SHA-256("nbeep-user-id-v1" ‖ handle ‖ KP)` | **삭제** → `UserId = SHA-256("nbeep-user-id-v2" ‖ UserKey.pub)` · KP는 PSK·RID·래핑에만 |
| §3-2 판정 | PSK 성립 = 같은 사용자 | 동일 + 성립 직후 **UserKey 봉인본 동기**(없는 쪽이 받는다) |
| §3-5 폐기 | 암호 변경 = 새 UserId | **암호 변경 ≠ 신원 변경** · 폐기 = UserKey 교체 + Succession · 경쟁 = 충돌 표시 |

## 7. 검토 결론

1. **구조 분리는 필요하다** — 사용자의 문제 제기가 정확했다. 46 원안은 "아이디/패스워드"를 **신원값의 재료**로 써서, 암호 변경이라는 정상 행위가 신원을 파괴한다. 개정안은 아이디/패스워드를 **문 열쇠**로 강등하고 신원은 무작위 키에 둔다 — 사용자 체감(같은 두 값 = 같은 사용자)은 그대로다.
2. **선점은 구조적으로 없다** — 등록소가 없고 신원값이 무작위 키다. 서버 이름공간만 서명으로 잠근다.
3. **변경은 후계 증명서로 잇는다** — 근거는 전부 "이미 신뢰한 것"(옛 키 서명 · 핀된 PeerId · version). 잇지 못하는 유일한 경우(전 기기+암호 소실)는 PeerId 앵커로 **사용자 확인 병합**을 제안한다.
4. **풀리지 않는 것은 숨기지 않는다** — 전 기기 복제의 대가인 폐기 경쟁은 자동 승자를 두지 않고 충돌로 드러낸다. 그것이 싫으면 v2 주 기기 승격(ADR-0007 원안)이며, 데이터 형식은 그대로 이어진다.
5. 비용은 **서명 원시 1종 + 이틀**. 사용자 요구 다섯 가지(46 §1)는 전부 유지된다.

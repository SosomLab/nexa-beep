# 12 · 차용 자산 실측 평가 — `nexa-dir2`에서 무엇을 가져올 수 있나 (D-11)

> **결론 먼저**: **Nexa Controls(`ctl`)는 재사용할 수 없다.** HWND 기반 모델이라 우리 아키텍처와 근본적으로 다르다.
> **진짜 자산은 `nexa-gui`**(8,488 LOC · 플랫폼 중립 · `DrawCtx`/`Widget` 트레이트)다.
>
> ⚠️ **이 문서는 정정을 포함한다** — [10 §4 차용 자산 원장](10-decision-record.md)에 "Nexa Controls 14종 계약 계승"이라고 적었던 것을 실측으로 뒤집는다([16 §2-5](16-doc-git-conventions.md) — 과거 기록은 남기고 정정 항목을 추가).
> **측정 2026-08-08** · 대상 `../nexa-dir2` · 출처 [`nexa-dir2/docs/23-cross-platform-feasibility.md`](../../nexa-dir2/docs/23-cross-platform-feasibility.md) + 직접 확인.

## 2. `ctl`을 쓸 수 없는 이유 — 모델이 다르다

`ctl`의 각 컨트롤은 **Win32 창 클래스**다(`Nexa.NxButton`, `Nexa.NxComboBoxPop` …). 생성하면 `HWND`가 나오고, 통지는 부모 `WM_COMMAND`로 올라가며, 상태는 `GWLP_USERDATA`에 붙는다.

| HWND 모델이 OS에서 공짜로 받는 것 | 우리(픽셀 버퍼 위젯 트리)는 |
|---|---|
| 히트 테스트 · Z 순서 | 직접 계산 |
| 포커스 · Tab 순회(`IsDialogMessageW`) | 직접 구현 |
| 메시지 라우팅 · 클리핑 | 직접 라우팅 |
| 팝업 창(콤보·메뉴 드롭다운) | 창이 아니라 **오버레이 레이어**로 |
| 무효화·재그리기 | 무효화 사각형 직접 관리 |

[ADR-0001 §3](07-adr-0001-stack.md)이 채택한 B안은 **"창 1개 + 픽셀 버퍼"** 다. 컨트롤마다 OS 창을 만드는 순간 **플랫폼 중립성도, 픽셀 동일성(S-7)도 성립하지 않는다.** 즉 `ctl`은 코드로도, 구조로도 이식 대상이 아니다.

> **`ctl` 7,139 LOC 중 우리가 가져올 수 있는 코드는 사실상 0**이다. 가져올 것은 **코드가 아니라 계약과 시각 규약**이다([§3-B](#b-설계계약-계승--ctl에서-가져오는-것)).

## 3. 실제로 가져오는 것 — 3계층

### A. 코드 이식 — `nexa-gui` 인프라 1,187 LOC

우리 [01 아키텍처](01-architecture.md)의 `gfx`/`ui` 분리와 **구조가 정확히 일치**한다.

| 모듈 | 우리 대응 | 이식 판단 |
|---|---|---|
| **`draw.rs` — `DrawCtx` 트레이트** | `gfx` ↔ `ui` 경계 | ★★ **핵심 자산.** 이미 **백엔드 교체를 전제**한 추상화다(테스트 백엔드가 존재). 우리 CPU 래스터라이저가 그 자리에 그대로 들어간다 |
| `widget.rs` — `Widget` 트레이트 | `ui` 위젯 기반 | ★★ 그대로 |
| `event.rs` — 입력 이벤트 모델 | `ui` 입력 라우팅 | ★★ 그대로 |
| `geom.rs` — Rect·Point | 공통 | ★★ 그대로 |
| `theme.rs` — 색 토큰 | `ui` 테마 | ★ 값은 교체, 구조 계승 |
| `edit.rs` — 텍스트 편집 모델(400 LOC) | 메시지 입력창 | ★★ **IME 연결 지점**(FR-U-7)이라 값이 크다 |
| `typeahead.rs` | 피어 목록 타입어헤드(FR-U-4) | ★ 그대로 |
| `columns.rs` | 목록 컬럼 | △ 메신저에는 용도가 적다 |

> ⚠️ **`DrawCtx`는 GDI/DirectWrite 모델을 전제한 API**(`text_opaque` = `ExtTextOutW(ETO_OPAQUE)`, `draw_image(hint: &str)` = 백엔드가 경로로 디코드)가 일부 섞여 있다. **그대로 복사하지 않고 우리 렌더 모델에 맞춰 다듬는다** — 특히 `draw_image`가 파일 경로를 받는 설계는 [FR-S-12](05-requirements.md)(격리 디코드·재인코딩본만)와 충돌하므로 **반드시 바꾼다**.

### B. 설계·계약 계승 — `ctl`에서 가져오는 것

코드가 아니라 **규약**이다. 이건 값이 크다 — 14종 컨트롤을 실제로 만들며 얻은 결론이기 때문이다.

| 계승 항목 | 내용 |
|---|---|
| **`Style` 팔레트 모델** | `bg`/`border`/`text`/`text_dim`/`accent`/`sel_bg`/`behind`/`danger` — **색 하드코딩 금지, 전 컨트롤이 팔레트를 인자로 받는다.** 다크/라이트가 값 교체만으로 끝난다(FR-U-5) |
| **공통 자동 높이** | `h <= 0` = 글꼴 + 상하 4px(버튼/세그는 +2px) — *"수정 없이 배치만 해도 반듯"*. 4타깃 동일 UI(NFR-C-1)에 직결 |
| **텍스트 세로 중앙 +1px 보정** | 콤보·글상자·세그 공통 QA 결과 |
| **`behind`(배후색) 개념** | AA 도형 가장자리를 부모 배경색으로 블렌드 — 1비트 리전 클립을 폐기하고 얻은 결론. **CPU 래스터라이저에서도 그대로 유효** |
| **라벨 실측 정렬**(`text_width`) | 언어 전환에도 정렬 유지 — 다국어(FR-U-3) 필수 |
| **상태 소유·해제 규율**(`base`) | 생성 시 상태 설치 / 파괴 시 회수(RAII). 우리는 Rust 소유권으로 자연스럽게 대응되지만 **"자원을 쥔 위젯은 Drop을 구현한다"** 는 규율은 그대로(NFR-B-6 누수 0) |
| **통지 모델** | `WM_COMMAND` 재발행 → 우리는 **콜백/이벤트 열거**로 번역. "컨트롤은 부모를 모른다"는 성질만 계승 |

### C. 함정 원장 — 선별 계승

`ctl` 문서의 "Win32 함정 원장"은 대부분 **P2(창 라이브러리) 채택으로 무의미**해지지만, 두 개는 살아남는다:

| 함정 | 우리에게 유효한 이유 |
|---|---|
| **잦은 갱신 위젯은 더블버퍼 + 배경 지우기 억제** | 깜빡임 원인은 렌더 모델과 무관. 우리도 무효화 사각형만 다시 그린다 |
| **가시 영역만 그리기** | `rows.rs`가 100k 행에서 검증한 방식. 피어 500 목록 60fps(NFR-B-12)에 그대로 적용 |

## 4. R-3(자체 렌더링 비용) 재평가

| | 이전 가정 | 실측 후 |
|---|---|---|
| 재사용 대상 | Nexa Controls 14종(7,139 LOC) | **`nexa-gui` 인프라 1,187 LOC + `ctl`의 계약·규약** |
| 절감 성격 | "컨트롤을 가져다 쓴다" | **"경계 설계와 시각 규약을 검증된 상태로 시작한다"** |
| 남는 일 | 렌더 백엔드 교체 | **위젯 세트 전체 신규 구현** + CPU 래스터라이저 + 텍스트 스택 |

> **R-3은 완화되지만 해소되지 않는다.** 절감의 실체는 LOC가 아니라 **"어떤 경계로 잘라야 하는지 이미 안다"** 는 것과 **시각 규약을 처음부터 다시 시행착오하지 않는다**는 것이다. 원본 문서 23의 결론 — *"이식이 아니라 UI 셸 재작성"* — 이 우리에게도 그대로 적용된다.
>
> ⇒ [05 §4](05-requirements.md) **R-3의 대응란을 정정**하고, [02 로드맵](02-roadmap.md) **M3(셸·UI)의 규모 산정**을 이 전제로 다시 본다.

# 40. 알려진 한계 — 정직한 경계 한 장 (M5-6 · 2026-08-21 초안 · 11-08 v0.10.1 현행화)

> **이 문서는 사용자에게 보여줄 "무엇을 막지 못하는가"의 SSOT다**(NFR-S-5 —
> "안전하다"고 단정하지 않는다). 각 항목은 설계 문서의 원장을 가리키고, 릴리스
> 노트·위키·설정 화면 문구가 여기서 가져다 쓴다. v1.0 마감(D-24) 때 최종 확정.

## 1. 신원·신뢰

| 한계 | 내용 | 원장 |
| --- | --- | --- |
| **TOFU가 못 막는 것** | 첫 접촉 **그 순간**의 중간자는 원리적으로 탐지 불가 — 핀은 "처음 본 키를 기억"할 뿐이다. 확신이 필요하면 **지문을 다른 채널로 대조**(`/fingerprint` → 구두·메신저 → `/verify`) | [09 ADR-0002] · [26 §2-2] |
| **이름은 신원이 아니다** | 표시 이름·프로필은 상대의 **주장**이다. 같은 이름의 새 키 = 새 사람으로 취급되고, v1에서 사칭을 드러내는 유일한 가시 신호는 **이름 충돌 표식**뿐 | [21 §3] · [14 §13] |
| **고정 공개키 = 재식별자** | 발견 패킷의 키로 같은 LAN 관찰자가 기기를 장기 추적할 수 있다(R-18 · 11-07 결정 = 감수 + 고지 + 광고 끄기 옵션). **광고 끄기(조용한 노드 · `net.discovery_advertise`)는 숨김이 아니다** — 주기 광고·기동 HELLO만 멎고, 남이 보낸 HELLO에는 유니캐스트로 답하므로 같은 LAN의 능동 프로브(HELLO 1발)는 존재와 키 지문을 알 수 있다. 수동 등록·릴레이 명부도 그대로다 | [29 §2] · TODO R-18 · journal 11-07 |
| **패스프레이즈를 아는 기기 = 내 기기** | 다중 기기 신원에서 같은 핸들·패스프레이즈를 넣은 기기는 "내 기기"가 되어 **사람 판정(승인·지문 대조)이 전부 해제**된다(파일 판정은 그대로 — 격리·검사·기기별 실체화). 패스프레이즈 유출 = 그 사용자의 기기를 만들 수 있다는 뜻이다 | [46](46-adr-0015-userid-handle-passphrase.md) · DR-29 |
| 폐기 경쟁은 드러낼 뿐 풀지 않는다 | 기기 분실로 사용자 키를 교체할 때 옛 키를 가진 쪽과 경쟁이 생기면 **"정직한 충돌"로 표시할 뿐 자동으로 해소하지 않는다** — 어느 쪽이 진짜인지는 사람이 다른 채널로 정한다 | [46](46-adr-0015-userid-handle-passphrase.md) · [47](47-adr-0015-review-userid-continuity.md) |
| 수동 IP 형제의 경로 등급 | 수동 IP(원격)로 만난 내 기기는 신원 신뢰와 별개로 **경로 등급은 원격**이다(Unmanaged 경계) — 신원 신뢰는 키에, 경로 등급은 경로에 | DR-28 · [19 §5-1](19-adr-0006-manual-endpoint.md) |
| 차단의 한계 | 익명 제로 컨피그에서 새 키+새 IP+새 이름 = 새 사람 — 차단은 우회 비용을 올릴 뿐 근절하지 못한다 | [38 §7] |

## 2. 기록·저장

| 한계 | 내용 | 원장 |
| --- | --- | --- |
| **기기를 바꾸면 기록은 안 따라간다** | 기록은 각 PC에만 있다(서버 보관 없음 · V-7). 이전·백업은 신원 키 백업과 별개 설계(포스트 v1). 예외 = 다중 기기 신원의 **따라잡기**(살아 있는 내 기기끼리 최근 줄을 나눈다 · 파일 본문 제외) — 내 기기가 모두 꺼져 있던 구간과 새 기기의 옛 전체 기록은 해당 없다 | [17 §8] |
| **`identity.key`가 뚫리면 전부 뚫린다** | 저장 암호화(NBSE 전면 — 08-21 실측 감사)는 **기기 키 파생**이다. 같은 OS 계정으로 로그인한 공격자·키 파일 유출에는 무력(승격 B/C는 실격 — DR-4/DR-1 충돌) | [17 §3-1] |
| **삭제가 물리 삭제를 보장하지 않는다** | SSD 웨어 레벨링·백업 사본 때문에 지운 세그먼트 바이트가 남을 수 있다. **크립토 셰레딩은 구현됐지만**(08-21 — 대화별 데이터 키를 폐기해 잔존 바이트를 난수로 만든다) 그것은 *못 읽게* 하는 것이지 *지우는* 것이 아니다 — 백업본에 옛 키가 함께 남아 있으면 무력 | [17 §7] |
| 동기화 폴더 | OneDrive류 안에 데이터 폴더를 두면 충돌·**구버전 복원**(지운 대화 부활) 위험 — 감지 시 경고만 하고 막지 않는다 | [17 §6] · 08-21 구현 |

## 3. 전달·오프라인

| 한계 | 내용 | 원장 |
| --- | --- | --- |
| **서버리스 오프라인의 근본 한계** | 오프라인 큐는 **내 PC가 켜져 있고** 상대가 나타날 때만 전달한다. 양쪽 다 꺼져 있던 구간의 전달은 서버 모드 ②(v1 이후)의 몫 | [32 §5 GS-2] · Q-25-2 |
| "보냈다" ≠ "닿았다" | 전달/읽음 점은 **검증·설정 게이트**를 통과한 상대만 되쏜다 — 점이 없다고 미수신이 아니다(오프라인·미검증·설정 off 구분 불가) | [24 §5] |
| 발견은 확률적이다 | 기업 무선망(클라이언트 격리·IGMP 스누핑)에서 S1~S3가 전멸할 수 있다 — S4 유니캐스트·수동 IP 등록이 폴백이며, 그래도 안 닿는 망이 있다(E-3 실측 잔여) | [06 §4·§7] |

## 4. 수신 파일 안전

| 한계 | 내용 | 원장 |
| --- | --- | --- |
| **"검사됨(탐지 없음)" ≠ 안전** | AMSI 검사는 설치된 백신의 판정일 뿐이다(제로데이·비Windows = "검사 안 됨"). 격리·승인 마찰이 본체이고 검사는 보조다 | [11 §6] · NFR-S-5 |
| 아카이브 점검 범위 | zip만(**zip64 포함** — 08-21) · **중앙 디렉터리만 읽고 절대 해제하지 않는다**(폭탄 구조는 구조만 보고 거른다) · 암호화 zip·중첩 아카이브·비zip 포맷은 **"판정 불가"**(통과 아님) · 점검은 표시·마찰의 근거일 뿐이며 사용자가 직접 푼 항목은 각자 다시 게이트를 탄다 | [docs/38의 형제 · nbeep-safe::zip] |
| 새 격리물 = v2(11-07) | 이번 버전부터 받은 파일의 격리물은 **v2 형식**이라 **이전 버전 앱으로 데이터 폴더를 되돌리면 그 격리물을 열지 못한다**(fail-closed · 원본은 보낸 쪽에서 다시 받기) · 반대(새 앱이 옛 v1 격리물 열기)는 된다 · 이어받기 중이던 옛 `.part`는 재개 대상에서 빠진다 | [11 §2] · [37 §3-1] |
| 큰 파일은 검사하지 않는다(11-07) | AMSI 검사는 **32MiB 이하**만 — 그보다 크면 "검사 불가(크기)"로 표기(검사됨이라 하지 않는다) · zip은 64MiB 초과면 내부 점검 생략을 표기 | [04 §4] |
| 실체화 이후는 OS 몫 | 승인·실체화된 파일의 실행 결과는 앱 밖이다 — MotW/quarantine 표식을 남겨 OS 방어선에 넘길 뿐 | [04 §5] |

## 5. 네트워크 노출

| 한계 | 내용 | 원장 |
| --- | --- | --- |
| **존재 자체는 평문 방송** | 발견 패킷(키·표시 이름·포트)은 같은 LAN에 평문이다 — 내용은 없지만 존재·이름은 숨기지 못한다(이름 기본값은 실명 정제 `beep-{지문}`) | [29 §2·§5] · M1-10 |
| **누가 누구와 언제 연결했는가** | TCP 연결 자체가 관찰된다 — 막을 수 없다(릴레이도 목적지는 본다) | [29 §5] |
| **파일 크기·전송 시간** | 암호화해도 길이와 시각은 남는다 | [29 §5] |
| **`tcp_port`** | 연결에 필요해 발견 패킷에 실린다(필수 노출) | [29 §5] |
| 가상 인터페이스 제외는 휴리스틱 | VPN·VM 어댑터 판별이 이름 접두 기반이라 완전하지 않다(예: "이더넷 N"으로 표시된 VM host-only) — 새 접두는 실측으로 추가 | [nbeep-net::netif] |
| **메시지 길이·타이밍** | 내용은 E2E 암호화지만 AEAD는 **길이를 숨기지 않고** 시각 패턴도 관찰된다(패딩·커버 트래픽은 채택하지 않는다 — 대역폭·복잡도 대비 이득이 작다 · DR-5) | [29 §3·§5] |

## 7. 릴레이 서버(선택 · 관리형)

서버 없이 쓰면 이 절은 해당 없다. 서버 `nexa-beepd`도 **봉투만 본다**.

| 구분 | 내용 | 원장 |
| --- | --- | --- |
| **서버가 보는 것** | **클라이언트 공개키**(Noise 상호 인증이라 핸드셰이크에서 보인다 — 서버는 "서버 사용자에게 나를 표시"를 켠 경우만 담고 그 밖은 비기록 운영이다. 기술적으로 못 보는 것이 아니다) · 회전 RID · 앱 이름·버전 · 접속 IP와 시각 · 랑데부 상대(누가 누구를 찾았는가) · 중계 바이트 수와 타이밍 | [41](41-beepd-ops-guide.md) · [42](42-relay-rendezvous-walkthrough.md) · [56](56-adr-0016-beepd-wire-v2.md) · `nexa-beepd/src/session.rs` |
| **서버가 못 보는 것** | 메시지 본문 · 파일 내용 · 표시 이름(종단 간 암호화 — 서버는 암호문만 나른다) | DR-7 · [42](42-relay-rendezvous-walkthrough.md) |
| **운영자를 믿는 범위** | 존재와 연결 관계라는 **메타데이터**는 서버 운영자에게 드러난다. 서버 키는 처음 접속 때 고정(핀)되고, 바뀌면 접속을 거절한다 | [41](41-beepd-ops-guide.md) |
| 구버전 클라이언트 | 서버 모드는 **0.10.0 이상**만 — 0.9 이하는 와이어 v2 서버(nexa-beepd 1.0.0)에 붙지 못한다(LAN 사용은 영향 없음) | [56 ADR-0016](56-adr-0016-beepd-wire-v2.md) |

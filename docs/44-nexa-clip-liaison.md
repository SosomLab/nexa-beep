# 44 · `nexa-clip` 연계 — 공유 서버·와이어에서 지켜야 할 것

> **작성 2026-08-26** · 요청자: `SosomLab/nexa-clip`(같은 개발자·자매 프로젝트).
> **왜 이 문서가 있나** — `nexa-clip`(크로스플랫폼 클립보드 매니저)이 **릴레이 서버 `nexa-beepd`와
> 와이어 `nbeep-relay`를 그대로 재사용**한다. 같은 서버에 **beep 사용자와 clip 사용자가 함께 붙는다**는 뜻이므로,
> 양쪽이 어긋나면 **조용히 못 만나게 되는 규약**이 생겼다. 그것들을 여기 모은다.

## 1. 🟡 지켜 주셔야 하는 것 — 앱 격리 규약

### 1-1. 랑데부 RID 파생 문자열은 **앱 식별자다**

```rust
// crates/nbeep-relay/src/lib.rs
pub fn rid_for(peer: &PeerId, epoch_day: u64) -> Rid {
    h.update(b"nbeep-rid-v1");   // ★ 이 문자열이 앱을 가른다
    …
}
```

| 앱 | 도메인 문자열 |
|---|---|
| **nexa-beep** | `"nbeep-rid-v1"` |
| **nexa-clip** | `"nclip-rid-v1"` |

★ **같은 공개키라도 도메인 문자열이 다르면 RID가 달라진다** → 두 앱 사용자는 **같은 만남 지점에 서지 않는다.**
이것이 앱 격리의 1차 방어이고, **서버 코드는 전혀 바뀌지 않는다**(서버는 여전히 16바이트를 라우팅할 뿐).

> 🔴 **부탁**: `"nbeep-rid-v1"` 을 **임의로 바꾸지 말아 주세요.**
> 바꿔야 할 이유가 생기면(예: 파생 방식 개정) **clip 쪽에도 같은 시점에 반영**돼야 합니다 —
> 한쪽만 바뀌면 **격리가 깨지거나(같은 값이 되거나) 각 앱 내부에서 서로를 못 찾게** 됩니다.
> 위 코드에 그 취지의 주석을 함께 제안드립니다([§4](#4-코드-주석-제안)).

### 1-2. Noise `prologue` 도 앱 식별자로 쓴다

clip은 종단 핸드셰이크의 `prologue`를 `"nexa-clip/1"` 로 둘 예정입니다.
**Noise는 양측 prologue가 같아야 핸드셰이크가 성립**하므로, RID가 우연히 겹치거나 누군가 의도적으로
다른 앱의 RID를 계산해 붙어도 **핸드셰이크가 수학적으로 실패**합니다(검사 코드 불필요).

> 🔴 **부탁**: beep이 prologue를 쓰신다면 **`"nexa-beep/<major>"` 형태**로 잡아 주시면
> 양쪽 규약이 한 모양이 됩니다. (현재 beep 구현을 확인하지 못했습니다 — 이미 다르게 쓰고 계시면 알려 주세요.)

### 1-3. 나중에 앱 간 교환을 열 때

두 앱이 안정화되면 **상호 메시지 교환**을 열 수 있습니다. 그때는 **격리를 푸는 것이 아니라 브리지를 얹습니다**:

```text
공용 브리지 도메인 : "nexa-bridge-rid-v1"   ·   prologue : "nexa-bridge/1"
→ 브리지에 옵트인한 사용자끼리만 만난다
```

★ **기본을 격리로 두고 브리지를 옵트인으로 추가**하는 방향입니다.
반대(기본 개방 + 나중에 차단)는 **이미 섞인 것을 되돌릴 수 없습니다.**

## 2. 🟡 공유하고 싶은 발견 — glare(양쪽 동시 `Open`) 타이브레이크가 없다

clip에서 릴레이 코드를 읽다가 발견한 것으로, **beep에도 그대로 있는 문제**로 보여 공유드립니다.

A와 B가 **서로를 동시에** 열면 채널이 **두 개**(A→B, B→A) 생깁니다. 실코드를 확인한 범위에서
`nbeep-relay`·`nexa-beepd` 어디에도 **타이브레이크 규칙이 없습니다**.

**증상**: 세션이 이중으로 서고, 메시지가 두 번 흐르거나 순서가 갈릴 수 있습니다.

**clip이 채택한 규칙**(제안):

| # | 규칙 |
|:--:|---|
| TB-1 | 두 `PeerId`의 **바이트 사전순으로 작은 쪽이 initiator** |
| TB-2 | 큰 쪽은 **자기가 연 채널을 닫고**(`CloseCh`) 상대의 채널을 받는다 |
| TB-3 | 결정적이라 **추가 왕복이 없다** — 양쪽이 같은 답에 도달한다 |

> 서버 중재(서버가 하나를 고르게 하는 것)는 **서버에 의미를 부여**하게 되어 봉투 원리와 어긋납니다.
> 클라이언트 규약으로 두는 편이 낫다고 판단했습니다.

## 3. 🔴 지금은 아니지만 — 나중에 요청드릴 수 있는 것

| # | 항목 | 내용 | 지금 상태 |
|:--:|---|---|---|
| **I-2** | **한 RID에 기기 N대 등록** | `nexa-beepd`의 `rids: HashMap<Rid, ConnId>`가 **1:1**이라 뒤 등록이 앞을 덮습니다. clip은 "한 사용자의 여러 기기가 한 랑데부 지점에서 만나는" 안을 검토했다가 **이 제약 때문에 기기별 RID로 회피**했습니다. 채택하려면 `HashMap<Rid, Vec<ConnId>>` + `Open` 팬아웃이 필요합니다 | ☐ **요청 안 함**(회피 완료) |
| **I-3** | **오프라인 큐 = 컨텐츠 서버(ADR-0013 모드 ②)** | 릴레이는 *"버퍼가 아니라 파이프"* 라 **양쪽 동시 접속일 때만** 흐릅니다. clip의 기기 간 동기화도 같은 제약을 받습니다. 꺼진 기기가 나중에 받으려면 모드 ②가 필요한데 **beep에서도 미구현**(D-29 확정 대기)입니다 | ⏸ **beep 결정 대기** |
| **I-6** | **와이어에 앱/버전 태그** | 서버가 앱별 통계·상한을 갖게 하려면 `C2s::Register`에 태그가 필요합니다. ★ **clip은 요청하지 않습니다** — 격리는 §1(도메인 분리)로 충분하고, 태그를 실으면 **서버가 앱 신원을 알게 되어** 봉투 원리가 한 겹 얇아집니다 | ✕ **요청 안 함** |

## 5. ★ 서버를 다시 배포해야 하나? — 항목별

> **결론**: **§1·§2·§4는 서버 재배포가 필요 없습니다.** 클라이언트만 바뀝니다.

### 5-1. 왜 — 서버는 RID를 **계산하지 않는다**

실코드 확인(2026-08-26):

```rust
// crates/nexa-beepd/src/lib.rs:26
use nbeep_relay::{C2s, Rid, S2c, MAX_RIDS, OBS_MAGIC};
//                              ^^^ 타입만 · rid_for/rids_around 는 쓰지 않는다
```

`rid_for`·`rids_around`는 **클라이언트가 부른다**. 서버는 `C2s::Register`로 **받은 16바이트를 맵에 넣고**,
`C2s::Open`으로 **받은 16바이트를 찾을** 뿐이다(`rids: HashMap<Rid, ConnId>`).
서버가 가진 `rid_short`(lib.rs:152)는 **로그 표시용 포맷터**라 파생과 무관하다.

> ★ **그래서 도메인 문자열을 바꿔도 서버는 아무것도 모른다** — 값이 달라진 16바이트가 올 뿐이다.

### 5-2. 항목별 영향

| 항목 | 서버 코드 | 서버 **재배포** | 클라이언트 |
|---|:--:|:--:|:--:|
| **§1-1** RID 도메인 문자열(주석 추가 포함) | 변화 없음 | ✕ **불필요** | 재빌드·배포 |
| **§1-2** Noise `prologue` | 변화 없음(종단 암호는 서버를 통과할 뿐) | ✕ **불필요** | 재빌드·배포 |
| **§2** glare 타이브레이크 | 변화 없음(클라이언트 규약) | ✕ **불필요** | 재빌드·배포 |
| **§4** 코드 주석 | 주석만 | ✕ **불필요** | — |

### 7-2. beep의 glare 현황 — 실코드

clip 전달문은 *"beep 릴레이에 규칙이 없다"* 고 했다. **릴레이 계층(`nbeep-relay`·`nexa-beepd`)에는 없다 — 맞다.**
다만 beep은 **앱 계층에 가드 하나**를 갖고 있다(`crates/nexa-beep/src/app.rs` `AppEvent::Inbound` 처리):

```rust
if self.conversations.contains_key(&peer) {
    return; // 이미 이 상대와 대화 중(아웃바운드 세션 존재) — 중복 인바운드 무시
}
```

| 상황 | 결과 |
|---|---|
| 한쪽만 열었다 | 정상(가드 무관) |
| A가 연 뒤 B가 늦게 열었다 | B의 아웃바운드가 A에 도착 → A는 이미 대화 중 → **드롭** → B는 Closed 관측 → 백오프 재시도(이미 A→B 세션이 있으니 B 쪽은 인바운드로 대화 중) — 수렴 |
| **양쪽이 동시에 열었다**(진짜 glare) | 둘 다 아웃바운드가 먼저 성립 → **둘 다 상대 인바운드를 드롭** → 둘 다 자기 아웃바운드가 상대에게 버려져 Closed → **양쪽 백오프 재시도** — 비결정적이라 다음 회차에 다시 겹칠 수 있다 |

즉 beep의 가드는 **"둘 중 하나가 이긴다"가 아니라 "둘 다 죽고 다시 한다"** 다. 채널 이중 성립은 막지만 수렴은 운에 맡긴다.
clip 규칙(**PeerId 사전순 작은 쪽 = initiator · 큰 쪽은 자기 채널을 닫고 상대 채널을 받는다**)은 이 자리에서
`peer < self.me` 비교 한 줄로 결정적 수렴을 만든다 — 서버 무변경 · LAN 경로에도 같은 규칙 적용 가능.
**채택 여부는 X-11(사용자 결정)** — 채택 시 clip과 같은 규칙으로 두어야 앱 간 브리지(§1-3)를 열 때도 안전하다.

### 7-4. 와이어 변경 시 고지 절차

`nbeep-relay`의 **`C2s`/`S2c` 메시지 · kind 번호 · 상수(`DEFAULT_RELAY_PORT`·`MAX_FRAME`·`RELAY_CHUNK`·`OBS_MAGIC`·`MAX_RIDS`·`CARD_MAX`) · 핸드셰이크 순서**를 바꾸는 커밋은:

# 20 · ADR-0007 — 다중 기기 신원 (UserId 1:M PeerId)

> **상태: ✅ Accepted** · 제안·확정 2026-08-08 · 결정자 Sangyong Bae
> **확정 사항(08-08)**: **Q-1 = 주 기기 전용 + 오프라인 복구 시드**([§9](#9--userid-개인키-보관--주-기기-전용--오프라인-복구-시드-q-1-확정)) · **기록 복호 능력은 분리**([§9-1](#9-1--저장-기록-복호-능력은-분리한다-q-1-부속-확정)) · **기기 관리 화면 규격**([§9-2](#9-2-기기-관리--화면과-동작))
> **사용자 요구(2026-08-08)**: *"여러 PC가 하나의 사용자로 묶여서 메시지를 같이 받고 송수신 이미지/파일을 공유 — 일반적인 메신저처럼."*
> *"1개 UserId에 다수 PeerId를 연결하는 1:M 구조를 만들고, 마치 그룹을 만드는 것처럼 UserId로 보내면 다수 PeerId로 전송하면 행위는 비슷하게 설계 가능하지 않나."*
> ⚠️ 이 ADR은 **[DR-18](10-decision-record.md)(노드 모델)의 개정 제안**이다 — **폐기가 아니라 선택 계층으로 얹는다.**
> 관련: [08 ADR-0002](08-adr-0002-discovery-transport.md)(Noise·TOFU) · [09 ADR-0003](09-adr-0003-transport-abstraction.md)(`PeerId`) · [17 ADR-0005](17-adr-0005-history-at-rest.md)(저장 키) · [05](05-requirements.md) FR-G/FR-S

## 1. 배경 — 처음 질문은 "릴레이(서버 모드)로 되나"였다

**답은 아니다.** 릴레이는 **"닿는가"** 를 푸는 계층이고, **"같은 사람인가"** 와 **"이력을 공유하는가"** 를 풀지 않는다. 현재 설계 그대로 v2 릴레이를 붙여도 PC 2대는 여전히 **서로 다른 두 노드**다.

| 벽 | 내용 | 근거 |
|---|---|---|
| **① 신원이 기기에 묶여 있다** | `PeerId` = 기기가 최초 실행 시 자체 생성한 정적 공개키. 릴레이는 `Locator`만 바꾸는 교체 지점이라 이 판정에 영향이 **없다**. [08 TOFU](08-adr-0002-discovery-transport.md)의 *"같은 이름, 다른 지문 → 다른 사람"* 에 그대로 걸린다 | [09 §3](09-adr-0003-transport-abstraction.md) · [08 §4](08-adr-0002-discovery-transport.md) |
| **② 이력을 보관할 주체가 없다** | 릴레이가 평문을 못 보므로(DR-7·FR-R-3) **구조적으로 서버 보관이 불가능**하다. 게다가 저장 마스터 키가 **기기 신원 키에서 파생**되어 기록 파일을 복사해 줘도 다른 기기가 못 연다 | [17 §3·§8](17-adr-0005-history-at-rest.md) |

> **릴레이가 실제로 기여하는 것은 하나 — 오프라인 큐.** 꺼져 있던 기기가 나중에 봉투를 받아 가려면 보관소가 필요하고 그건 로컬 직접 모드로 못 한다([09 §6](09-adr-0003-transport-abstraction.md) `capabilities()`). 즉 릴레이는 **필요조건이지 충분조건이 아니다.**

## 2. 핵심 인식 — "그룹처럼"은 **전송 계층에서만** 참이다

팬아웃 재사용은 **실제로 성립한다.** [FR-G-3](05-requirements.md)가 이미 *"v1 그룹 전송은 구성원별 팬아웃, UI에서 하나의 스레드로 묶는다"* 로 못 박아 뒀으니, 발신 코드를 `수신자 = PeerId 집합` 하나로 일반화하면 **1:1·그룹·UserId가 전부 같은 함수**를 탄다.

**그러나 신원 계층에서 그룹과 UserId는 성질이 정반대다.**

| | **그룹**(FR-G-1~4) | **UserId** |
|---|---|---|
| 구성 주체 | **내가 남을** 묶는다 | **내가 나를** 묶는다 |
| 성격 | **로컬 개념** — 합의 불필요 | **상대가 믿어야 하는 주장** |
| 틀렸을 때 | 손해는 나만 본다 | **상대의 메시지가 잘못된 곳으로 간다** |
| 구성원 제외 | 내 로컬 편집으로 끝 | **상대에게 전파되고 검증**되어야 한다 |
| 나 자신 | 포함하지 않는다 | **반드시 포함**해야 대화가 갈리지 않는다 |

### ⚠️ 검증을 빼면 열리는 구멍

| # | 공격 | 결과 |
|---|---|---|
| **A-1** | 공격자가 자기 `PeerId`를 **피해자의 UserId에 속한다고 발표** | 피해자에게 가는 메시지·파일이 공격자에게도 팬아웃된다 — **읽기 권한을 스스로 부여** |
| **A-2** | 남의 기기를 자기 UserId에 끼워 넣어 발표 | 목록 위장·피싱. "이 사람의 기기"라는 표시가 거짓이 된다 |
| **A-3** | 폐기된(도난) 기기가 **옛 서명 목록을 재생** | 이미 지운 기기가 계속 수신한다 — 롤백 공격 |

> 이건 [R-1(신뢰 앵커 부재)](05-requirements.md)의 **새로운 표면**이다. 그룹에는 없던 문제이고, 이 ADR의 대부분은 여기에 대한 답이다.

## 3. 결정

| # | 결정 |
|---|---|
| **① UserId = 사용자 장기 키** | 각 기기 키를 UserId 키로 **서명**해 기기 목록을 구성한다. 목록에 없는 기기의 "같은 사용자" 주장은 **거부**한다 |
| **② 팬아웃은 그룹 전송을 재사용** | 발신 경로를 `수신자 = PeerId 집합`으로 일반화. 1:1은 원소 1개짜리 집합, 그룹은 구성원 집합, UserId는 기기 집합 |
| **③ TOFU·SAS 대상이 UserId로 올라간다** | 기기 지문이 아니라 **사용자 지문**을 핀한다 |
| **④ 선택 계층이다** | 기본은 **DR-18 그대로**(노드 모델). 기기 묶기는 사용자가 원할 때만 |
| **⑤ v1은 타입 자리만** | 구현은 v2. 단 [§7](#7-v1에-지금-넣는-것--제약-4건)의 4건은 지금 넣는다 |

### ③이 주는 부수 이득 — 지금의 아픈 점 하나가 사라진다

현재 [08 TOFU 규칙](08-adr-0002-discovery-transport.md)은 지문이 바뀌면 **기본 차단 + 경고**다. 그래서 **재설치·기기 교체가 사칭과 구별되지 않는다.** UserId 서명 체인이 있으면 새 기기가 서명을 달고 오므로 **경고 없이 자연 편입**된다. DR-18 유지로는 얻을 수 없는 이득이다.

## 4. 기기 목록(DeviceList) — 개념 규격

```
UserId(장기 키) ──서명──► DeviceList {
                             user_pub,
                             devices [ { device_pub, role, caps, added_at } ],   ← role = primary | secondary
                             revoked [ { device_pub, revoked_at } ],
                             version,            ← 단조 증가
                             sig                 ← UserId 키의 서명
                          }
```

### 검증 절차 (수신 측)

| 단계 | 내용 |
|---|---|
| 1 | 상대 기기와 **`Noise_XX` 성립** — 그 기기의 정적 공개키를 확정한다([08 §4](08-adr-0002-discovery-transport.md)) |
| 2 | 상대가 제시한 `DeviceList`의 **`sig`를 `user_pub`로 검증** |
| 3 | 1에서 확정한 기기 키가 **`devices`에 있고 `revoked`에 없는지** 확인 |
| 4 | `version`이 **이미 본 최대값 이상**인지 확인([§5](#5-폐기revocation와-롤백-방지)) |

> **소유 증명은 양방향이다.** 목록은 UserId 키가 그 기기를 인정한다는 증거이고, Noise 핸드셰이크는 그 기기가 개인키를 쥐고 있다는 증거다. **둘 다 있어야** A-1·A-2가 막힌다.

### ⚠️ 표시 이름은 서명 대상이 아니다

기기 **표시 이름을 목록에 넣지 않는다.** 넣으면 이름을 바꿀 때마다 **주 기기의 재서명 + `version` 증가**가 필요해지고(보조 기기는 자기 이름조차 못 고친다), 목록 변경 알림([§9-2](#9-2-기기-관리--화면과-동작))이 이름 변경으로 오염된다.

이름은 **각 기기가 세션에서 스스로 알린다**(FR-D-9와 같은 취급). **이름은 신원이 아니므로**(FR-S-2) 서명할 이유가 없고, 사칭 시도는 어차피 **목록 검증**에서 걸린다.

`role`(primary/secondary)은 반대로 **반드시 서명 대상**이다 — 주 기기가 누구인지는 [§9](#9--userid-개인키-보관--주-기기-전용--오프라인-복구-시드-q-1-확정)의 이중 주 기기 방지에 직결된다.

### 관통 원리 적용 — 이 계층의 봉투와 내용 ([10 §0](10-decision-record.md))

| 봉투(볼 수 있는 것) | 내용(볼 수 없는 것) |
|---|---|
| UserId 지문 · 기기 공개키 · 목록 버전 · 서명 | 대화 · 첨부 · 기록 |

**발견 패킷([08 §2](08-adr-0002-discovery-transport.md))에는 UserId 지문과 목록 버전만 싣는다** — 목록 본체는 세션 성립 후 교환한다. 발견 패킷 ≤512B 예산을 지키고, 발견을 여전히 **"미검증 힌트"** 로 유지하기 위해서다.

## 5. 폐기(revocation)와 롤백 방지

**그룹 구성원 제외는 내 로컬 편집이면 끝이지만, 도난당한 노트북은 상대 쪽에서 걸러져야 한다.** 이걸 빼면 결함이 아니라 사고다.

| 규칙 | 내용 |
|---|---|
| **단조 증가** | `version`은 목록이 바뀔 때마다 증가. **감소하는 목록은 거부** |
| **최대값 기억** | 각 상대에 대해 **본 적 있는 최대 `version`** 을 저장한다 → A-3(옛 목록 재생) 차단 |
| **묘비(tombstone)** | 폐기된 기기는 목록에서 **지우지 않고 `revoked`에 남긴다**. 지우면 "모르는 기기"가 되어 재등록될 수 있다 |
| **세션 거부** | 폐기된 기기 키로 오는 핸드셰이크는 거부하고 **사용자에게 알린다**(조용히 끊지 않는다) |
| **전파의 한계** | 상대가 오프라인이면 폐기를 **모른다.** 다음 접촉 시 반영된다 — **즉시성은 보장하지 않는다**고 UI에 명시(NFR-S-5) |

## 6. 팬아웃으로 풀리지 **않는** 것 세 가지

| # | 항목 | 내용 |
|---|---|---|
| **1** | **자기 자신에게 보내기** | 그룹에 없는 개념이다. 내 다른 기기에도 **사본(sender copy)** 을 보내야 대화가 갈리지 않는다. 팬아웃 함수는 재사용되지만 *"수신자 집합에 내 기기 포함"* 이라는 규칙이 새로 필요하다 |
| **2** | **파일 승인 상태** | [ADR-0004](11-adr-0004-quarantine.md)는 fail-closed라 기기마다 자기 `.beepq` 격리소를 갖는다. **A에서 승인해 실체화한 파일이 B에서도 실체화되지는 않는다.** "일반 메신저처럼"에서 어긋나는 지점이므로 **v2에서 기기별 승인으로 확정**하고 UI에 표시한다 |
| **3** | **과거 이력** | 팬아웃은 **지금부터**만 해결한다. 새로 묶은 기기는 대화가 비어 있다. [17 §3](17-adr-0005-history-at-rest.md)의 래핑 키에 **사용자가 쥐는 백업 키**를 추가하면 길이 열리지만 **별개 설계**다([X-7](TODO.md) · [§7](#7-v1에-지금-넣는-것--제약-4건) V1-4가 그 준비). ⚠️ **`UserId` 키로는 열지 않는다**([§9-1](#9-1--저장-기록-복호-능력은-분리한다-q-1-부속-확정)) |

## 7. v1에 지금 넣는 것 — 제약 4건

**구현은 v2지만, 모델에 자리를 안 남기면 v2에서 메시지 포맷과 저장 포맷을 다시 만든다.** [09 §1](09-adr-0003-transport-abstraction.md)이 릴레이에 대해 편 논증과 같은 구조다.

| # | 제약 | 없으면 무엇이 뒤집히나 |
|---|---|---|
| **V1-1** | **`UserId` 타입 자리를 만든다.** v1은 `UserId == PeerId` 1:1. **대화 스레드·기록·차단 목록의 키를 `UserId`로** 둔다 | 스레드 키가 `PeerId`면 v2에서 **대화 기록 전체가 기기별로 쪼개진 채** 남는다 — 병합 마이그레이션이 필요해진다 |
| **V1-2** | **발신 경로를 `수신자 = PeerId 집합`으로 일반화** | 1:1 전용 경로가 따로 있으면 팬아웃을 **두 벌** 만들게 된다 |
| **V1-3** | **메시지에 `sender_device` 필드** + 논리 시퀀스 | 어느 기기가 보냈는지 없으면 sender copy와 원본을 구분·중복 제거할 수 없다. 시퀀스는 [09 §6](09-adr-0003-transport-abstraction.md)에 **이미 v1**이라 그대로 재사용된다 |
| **V1-4** | **저장 마스터 키를 기기 키에서 직접 파생하지 않고 한 겹 래핑** | 나중에 **백업 키**로 다시 감싸기만 하면 되고 **데이터 재암호화가 불필요**하다([17 §3](17-adr-0005-history-at-rest.md) "승격 전환"과 같은 논리). 직접 파생이면 **전 기록 재암호화** |

> **비용은 타입 하나와 필드 하나다.** 지금은 거의 공짜이고, v2에서는 마이그레이션이다.

## 8. DR-1(설정 0개)과의 충돌 — 성립한다

기기 추가는 필연적으로 **페어링이라는 설정 행위**다. 다만 DR-1이 금지한 것은 *"서버 주소 입력·계정 생성·상대 등록"* 이지 모든 상호작용이 아니다.

| 항목 | 판정 |
|---|---|
| **기본 경로는 여전히 노드 모델**(DR-18) — 묶지 않아도 제품은 완전하다 | ✅ DR-1 유지 |
| 내 기기끼리는 어차피 같은 LAN에서 **자동 발견**된다 → 페어링 = **SAS 1회 대조 후 승인** | ✅ 계정·서버 주소 없음 |
| 다만 **UI에 "내 기기" 개념이 새로 생긴다** — 이건 인정하고 감수한다 | ⚠️ 대가 |

> [19 ADR-0006 §1](19-adr-0006-manual-endpoint.md)·[06 §6](06-network-stack.md)과 같은 논리다 — **기본이 완전한 제품**이고 그 위는 선택.

## 9. ✅ UserId 개인키 보관 — **주 기기 전용 + 오프라인 복구 시드** (Q-1 확정)

> **사용자 확정 2026-08-08.** 서버가 없어서 Signal(서버가 기기 목록을 관리)·Matrix(SSSS 백업) 방식을 그대로 쓸 수 없다.

### 후보

| 안 | 방식 | 판정 |
|---|---|:--:|
| A. 모든 페어링 기기에 복제 | 페어링 시 SAS 후 전달 | ✗ **되돌릴 수 없다** — 아래 |
| **B. 주 기기 전용 + 복구 시드** | 개인키는 주 기기 1대에만. 시드는 오프라인 보관 | **✅ 채택** |
| C. 임계 서명(n-of-m) | 과반 기기가 동의해야 목록 변경 | ✗ 기기 2대에서 수학이 성립하지 않고(`2-of-2`=영구 잠김 / `1-of-2`=A와 동일) 구현이 무겁다(DR-5) |

### ⚠️ A를 버린 진짜 이유 — 폐기 경쟁에서 공격자가 이긴다

"무한 기기 추가"보다 심각한 것은 **폐기 권한**이다. [§5](#5-폐기revocation와-롤백-방지)의 롤백 방지 규칙 때문에 **`version`이 높은 목록이 이기는데**, A에서는 도난당한 기기도 서명할 수 있다:

```
나:     노트북 폐기        → version 5 서명
공격자: 내 기기 전부 폐기   → version 6 서명
상대:   version 6을 믿는다   ← 공격자가 이긴다
```

**복구 수단이 없다.** 신원을 버리고 새로 만드는 수밖에 없고, 그건 [TOFU](08-adr-0002-discovery-transport.md)상 상대에게 **"지문 변경 → 기본 차단"** 으로 보인다 — 실질적으로 **다른 사람이 되는 것**이다.

### ✅ 결정 — B의 규격

| 개념 | 규칙 |
|---|---|
| **주 기기(primary)** | `UserId` 개인키를 보유한 **유일한 기기.** 기기 추가·폐기 서명은 **여기서만** 일어난다 |
| **보조 기기** | 서명된 **기기 인증서만** 보유한다. 통신·대화·파일은 **전부 정상 동작**한다(개인키가 필요한 순간은 목록 변경뿐) |
| **복구 시드** | `UserId` 개인키의 시드. **다중 기기를 처음 켤 때 1회 표시**하고, 이후 주 기기에서 재표시 가능. 사용자가 **오프라인으로 보관**(종이·비밀번호 관리자) |
| **승격** | 시드를 입력한 기기는 **주 기기가 된다.** 주 기기 분실 시의 복구 경로 |
| **양도(handoff)** | 주 기기 교체는 개인키를 새 기기로 옮기고 **원본에서 즉시 zeroize**([17 §6](17-adr-0005-history-at-rest.md) 5) — 정상 교체 경로 |
| **탈취 복구** | 보조 기기를 잃으면 주 기기가 **더 높은 `version`으로 폐기 서명**한다. 공격자는 서명할 수 없으므로 **경쟁 자체가 성립하지 않는다** |
| **시드 저장** | 주 기기 안에서는 [17 §4](17-adr-0005-history-at-rest.md) 세그먼트로 암호화 보관. **평문으로 디스크에 두지 않는다** |
| **⚠️ 이중 주 기기** | 시드 승격 후 원래 주 기기가 살아 있으면 **둘 다 서명할 수 있다.** 승격 시 *"이전 주 기기를 폐기하라"* 고 유도하고, 목록·UI에 **어느 기기가 주 기기인지 항상 표시**한다 |
| **고지** | 시드 표시 화면에 **"이 시드를 가진 사람은 당신의 기기를 추가·폐기할 수 있습니다"** 를 명시(NFR-S-5) |
| **최악의 경우** | 주 기기도 시드도 없으면 **신원 재생성밖에 없다** — 상대에게 지문 변경으로 보이고 기록도 따라가지 않는다. 이 사실을 미리 알린다 |

### DR-1(설정 0개)과의 관계

**시드는 다중 기기를 켠 사용자에게만 나온다.** 기본 사용자는 평생 보지 않는다 — [19 §1](19-adr-0006-manual-endpoint.md)·[06 §6](06-network-stack.md)과 같은 논리(기본이 완전한 제품, 그 위는 선택).

> **감수하는 마찰**: *"노트북에서 새 PC를 추가하려는데 데스크톱을 켜야 한다."* 실재하는 불편이고, **시드로 승격하면 우회된다**(대신 시드 보관 책임이 실재한다). 이 절충을 UI에 그대로 설명한다.

## 9-1. ✅ 저장 기록 복호 능력은 **분리한다** (Q-1 부속 확정)

> **사용자 확정 2026-08-08.**

[17 §3](17-adr-0005-history-at-rest.md)이 래핑 구조가 되면서 `UserId` 키를 래핑 후보로 쓸 수 있게 됐지만, **쓰지 않는다.**

| | 묶는 경우 | **✅ 분리(채택)** |
|---|---|---|
| `UserId` 키의 역할 | 서명 + **전 기록 복호** | **서명 전용** |
| 키 탈취 시 | 과거 기록 전체가 열린다 — 폭발 반경 2배 | **과거 기록은 열리지 않는다**(그 기기 것 제외) |
| 기기 이전·백업 | 바로 열린다 | **사용자가 쥐는 별도 백업 키**로 [X-7](TODO.md)에서 설계 |

> **서명 능력과 복호 능력은 다른 권한이다.** 나중에 합치는 것은 가능하지만 **분리하는 것은 불가능**하므로 지금 분리해 둔다.
> ⇒ [17 §3](17-adr-0005-history-at-rest.md)의 래핑 키 후보는 **기기 키 · OS 보안 저장소 · 사용자 암호 · (v2)백업 키** 넷이며 **`UserId` 키는 포함하지 않는다.**

## 9-2. 기기 관리 — 화면과 동작

> [§4](#4-기기목록devicelist--개념-규격)~[§9](#9--userid-개인키-보관--주-기기-전용--오프라인-복구-시드-q-1-확정)가 **프로토콜**을 정했다면 여기는 **사용자가 실제로 만지는 것**이다. 목록에 서명 능력이 생긴 이상 **관리 화면 없이는 이 기능을 켤 수 없다** — 폐기할 방법이 없는 도난 기기는 설계 결함이다.

### 관리 대상은 둘이고, 권한이 다르다

| 대상 | 누가 서명하나 | 내가 할 수 있는 것 |
|---|---|---|
| **내 기기 목록** | **내 `UserId` 키**(주 기기에서만) | 추가 · 폐기 · 주 기기 양도 · 이름 변경 |
| **상대 기기 목록** | 상대의 `UserId` 키 | **읽기 전용.** 검증 결과를 보는 것뿐 — 내가 남의 기기를 지울 수는 없다 |

> 이 구분을 UI에서 흐리면 *"상대 기기를 내가 차단했는데 왜 계속 오지"* 가 생긴다. **차단은 기기가 아니라 사람(`UserId`) 단위**다 — 기기 단위 차단은 상대가 새 기기를 추가하면 곧바로 우회되므로 **의미가 없다.**

### 내 기기 화면

| 표시 항목 | 이유 |
|---|---|
| 기기 이름(호스트명 기본 · 변경 가능) | 식별([§4](#4-기기목록devicelist--개념-규격) — 서명 대상 아님) |
| **역할 배지 — 주 기기 / 보조** | 이중 주 기기 방지([§9](#9--userid-개인키-보관--주-기기-전용--오프라인-복구-시드-q-1-확정)) |
| **"현재 기기"** 표시 | 실수 폐기 방지 |
| 기기 지문(짧은 형태) | 대조 |
| 추가된 시각 · **마지막 접속 시각** | **낯선 기기 탐지** — A-1을 사용자가 알아채는 경로 |
| 목록 `version` · 마지막 변경 시각 | 동기 상태 확인 |

### 동작 규칙

| # | 규칙 | 이유 |
|---|---|---|
| **1** | **폐기는 주 기기에서만.** 보조 기기에서는 버튼을 숨기지 말고 *"주 기기에서 가능합니다"* 로 **비활성 표시** | 숨기면 기능이 없는 줄 안다([19 §1](19-adr-0006-manual-endpoint.md)과 같은 감각) |
| **2** | **현재 기기는 자기를 폐기할 수 없다** | 자기 발 쏘기. 대신 **"이 기기를 신원에서 분리"**(자기 인증서 폐기 후 독립 노드로 복귀)를 별도 동작으로 두고, **주 기기 목록에는 남아 있으므로 주 기기에서도 폐기해야 완결**임을 표시 |
| **3** | **주 기기는 폐기 전에 양도해야 한다** | 서명 권한이 사라지면 목록이 영영 잠긴다 |
| **4** | **폐기는 되돌릴 수 없다**(묘비 보존) → **확인 마찰**을 둔다. 기본 버튼은 항상 **"취소"** | [11 ADR-0004 §4](11-adr-0004-quarantine.md) 등급별 마찰과 같은 원칙 |
| **5** | 폐기 후 **"상대가 반영하는 시점은 다음 접촉"** 임을 결과 화면에 명시 | [§5](#5-폐기revocation와-롤백-방지) 전파 한계 — 조용히 넘어가면 안전하다고 오해한다 |
| **6** | 목록 변경은 **내 다른 기기에 알림** | 주 기기 탈취를 본인이 알아채는 경로 |

### ★ 상대 쪽 알림 — A-1에 대한 유일한 심층 방어

**상대의 기기 구성이 바뀌면 그 대화창에 시스템 라인 한 줄을 남긴다.** 예: *"홍길동이 기기를 추가했습니다 (2대 → 3대)"*

서명 검증([§4](#4-기기목록devicelist--개념-규격))은 **"권한 있는 자가 추가했는가"** 만 판정한다. **주 기기가 탈취당한 경우엔 그 검증을 통과한다.** 그때 사용자 쪽에 남는 유일한 신호가 이 한 줄이다.

| 항목 | 규칙 |
|---|---|
| 형태 | 대화 스레드의 **시스템 라인**(팝업·배지 아님 — 소음을 만들지 않는다) |
| 강조 | **SAS 대조 이후에 추가된 기기**는 *"아직 대조되지 않음"* 을 함께 표시 |
| 끌 수 있나 | **끌 수 없다.** 보안 신호이지 알림 설정이 아니다 |

### 기기 추가(페어링) 흐름

```
주 기기에서 "기기 추가"
  → 같은 LAN에서 발견된 후보 표시(아직 어떤 UserId에도 속하지 않은 노드)
  → 고르면 양쪽 화면에 SAS 표시 → 육안 대조 → 승인
  → 주 기기가 새 기기 키를 목록에 넣고 서명(version+1)
  → 새 기기에 인증서·목록 전달 → 이후 서로 sender copy 수신
```

- **원거리 기기**는 [19 수동 엔드포인트](19-adr-0006-manual-endpoint.md)로 주소를 넣고 같은 절차를 탄다. 원격 신뢰 등급이라 **SAS는 이미 필수**(FR-S-24)라 규칙이 겹치지 않는다.
- 페어링에는 **항상 SAS가 필수**다. 내 기기끼리라 생략하고 싶어지지만, 생략하면 **페어링 순간의 MITM이 곧 A-1**이 된다.

### 계측([13 §6](13-code-design-standards.md))

`ActionKind`에 **`DeviceAdd` · `DeviceRevoke` · `PrimaryHandoff` · `SeedShown` · `SeedRestore`** 를 추가한다. 레저에는 **행위 종류·시각·결과만** 남고 기기 이름·지문 평문은 남기지 않는다(솔티드 해시).

## 10. 예산·성능 영향 (DR-5)

| 항목 | 영향 | 통제 |
|---|---|---|
| 세션 수 | 상대 기기 수 × 내 기기 수만큼 Noise 세션 | 그룹 팬아웃과 **같은 성질** — 새 비용 축이 아니다 |
| **파일 전송** | 같은 파일이 **기기 수만큼 링크에 나간다** | ⚠️ NFR-B-10(링크속도 70%) 관점에서 **UI에 명시**. 기기 간 재배포 최적화는 **하지 않는다**(v2에서도 — 복잡도가 이득을 넘는다) |
| 상태 | 기기 목록·본 최대 version·묘비 | 작다. 저장 세그먼트에 포함([17 §4](17-adr-0005-history-at-rest.md)) |
| 발견 패킷 | UserId 지문 + 버전만 추가 | ≤512B 예산 안([08 §2](08-adr-0002-discovery-transport.md)) |

## 11. 결과 (Consequences)

### 긍정
- **"일반 메신저처럼"이 성립한다** — 여러 PC가 한 사람으로 접히고 메시지·파일을 같이 받는다.
- **재설치·기기 교체가 사칭 경고를 띄우지 않는다**([§3](#3-결정) ③) — 현재 TOFU의 아픈 점 해소.
- 발신 경로가 **1:1·그룹·다중 기기 하나의 함수**로 수렴한다(FR-G-3 재사용).
- V1-4가 [17 §8](17-adr-0005-history-at-rest.md)의 **기기 이전·E2E 백업**으로 가는 문도 같이 연다.

### 부정 · 감수
- **신뢰 앵커 문제가 한 겹 커진다** — 이제 UserId 키가 새로운 단일 실패점이고, **주 기기가 그 단일 지점**이다([§9](#9--userid-개인키-보관--주-기기-전용--오프라인-복구-시드-q-1-확정)). 복구 시드로 회복 경로를 두었을 뿐 **사라지지 않는다**.
- **DR-18의 단순함을 일부 잃는다** — "PC 1대 = 노드 1개"라는 한 문장 설명이 "기본은 그렇고, 묶으면 다르다"로 길어진다.
- 파일이 기기 수만큼 중복 전송된다([§10](#10-예산성능-영향-dr-5)).
- 파일 승인이 **기기마다 따로**다([§6](#6-팬아웃으로-풀리지-않는-것-세-가지) 2) — 사용자 기대와 어긋나므로 표시가 필요하다.

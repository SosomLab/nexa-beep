# 35 · ADR-0014 — 파일 선택은 시스템 기본 다이얼로그로 (✅ Accepted · D-30 확정)

> **상태**: ✅ **Accepted — D-30 사용자 확정(2026-08-18) = 권고안 채택**:
> Windows(`IFileOpenDialog`)·macOS(`NSOpenPanel`)는 시스템 기본 다이얼로그 직접
> 어댑터(`FileDialogPort` 뒤 · DR-21), **Linux는 자체 피커 유지**. DR-6(자체
> 렌더링)의 경계 = "앱 내부 표면은 자체 · OS 소유 표면(파일 선택)은 OS"로 획정.
> 구현은 후속 슬라이스(Windows 어댑터 = 이 PC · mac 어댑터 = mac PC 몫).
> 발단 = 사용자 지적(08-13):
> *"직접 작성한 파일 다이얼로그가 사용하기 불편하다. 파일 선택은 OS 특유의 UX를
> 유지하면서 시스템 기본 다이얼로그를 쓰는 게 좋겠다."*
>
> 관련: [DR-6 자체 렌더링](10-decision-record.md) · [DR-16 동작=OS 네이티브](14-control-ux-architecture.md) ·
> [DR-21 외부 기술은 포트 뒤에](13-code-design-standards.md) · [05 NFR-B 예산](05-requirements.md)

## 1. 현행 — 자체 탐색 피커의 실태

`Role::Picker` 별도 창 + `TreeView` 재사용. **사용처 4곳**:

| # | 용도 | 진입 | 형태 |
|---|---|---|---|
| P-1 | **백업 폴더 선택**(M2-5a) | 설정 → 백업 | 탐색형(폴더만) |
| P-2 | **백업 파일 선택**(복원) | 설정 → 복원 | 탐색형(`.nbk`) |
| P-3 | **프로필 이미지 선택**(M3-17) | 프로필 → Choose… | 탐색형(이미지 확장자) |
| P-4 | 갤러리 샘플(데모) | 갤러리 Choose | 목록형 |

**불편의 실체**(사용자 지적을 구체화) — 자체 피커에 없는 것:

- **즐겨찾기·바로가기** — 바탕화면·다운로드·문서·최근 항목·핀 고정 폴더
- **주소창 직접 입력·경로 붙여넣기** · 파일명 검색
- **클라우드 자리표시자**(OneDrive 온디맨드 등) — 셸만 아는 상태 표시
- 미리보기·정렬·보기 전환 · 접근성(스크린 리더) · 사용자의 **손에 익은 동선**

이건 "우리 피커를 더 만들면 되는" 목록이 아니다 — **OS 셸 네임스페이스**(가상
폴더·클라우드·최근 문서)는 앱이 재현할 수 없는 OS 영역이다.

## 2. 긴장 — DR-6과 정면 충돌인가?

| 원칙 | 내용 | 이 결정과의 관계 |
|---|---|---|
| **DR-6** | 모든 렌더링 자체 구현 · OS 위젯 금지 | ⚠ 표면 충돌 — 단 DR-6의 목적은 **"앱 화면"의 플랫폼 간 동일성** |
| **DR-16** | 시각=macOS / **동작=OS 네이티브** | ✅ 지지 — 파일 선택 **동선**이야말로 OS 관례의 핵심 |
| **DR-21** | 외부 기술은 포트 뒤에 | ✅ 그대로 적용 — `FileDialogPort` |
| **NFR-B** | 산출물 ≤10MB · 런타임 의존 0 | 어댑터 선택에 따라 통과 가능(§4) |

**판정 제안** — 파일 다이얼로그는 "앱 UI"가 아니라 **앱↔OS 셸의 경계**다.
선행 사례가 명확하다: **전부 자체 렌더링하는 브라우저(Chrome·Firefox)조차 파일
선택만은 네이티브**를 띄운다. DR-6에 예외를 뚫는 게 아니라 **경계를 획정**하는
것: *"창 안은 우리 그리고, OS 네임스페이스를 여는 문(파일 선택·저장)은 OS 것을
쓴다."* 보안 부수 효과도 있다 — OS 다이얼로그는 "사용자 의도 기반 권한 부여"
지점이라 향후 샌드박스 환경(macOS 공증 강화 등)에서도 안전한 편에 선다.

## 3. 설계 — `FileDialogPort` (DR-21)

```text
nbeep-plat::filedialog
  trait FileDialogPort {
      /// 파일 열기(필터: 표시명 + 확장자 목록). 결과는 이벤트로 복귀(비동기).
      fn pick_file(&self, req: PickReq) -> PickTicket;
      /// 폴더 선택(백업 폴더).
      fn pick_folder(&self, req: PickReq) -> PickTicket;
  }
  // 어댑터: Win = IFileOpenDialog(COM) · mac = NSOpenPanel · Linux = §4-3
```

- **비동기 필수** — 네이티브 다이얼로그는 블로킹이다. UI 스레드에서 부르면 winit
  루프가 얼어붙는다(M4-5 imgdec 워커화와 같은 뿌리) → **워커 스레드에서 호출 +
  `AppEvent::Picked{purpose, path}` 복귀**(M2-8 문법 재사용). Windows COM은 그
  워커에서 `CoInitializeEx(STA)`.
- **부모 창 지정** — 소유자 HWND/NSWindow를 넘겨 진짜 모달로(M3-16이 못 한
  부모 비활성화를 OS가 해 준다).
- **기존 자체 피커는 삭제하지 않는다** — ① Linux 폴백(§4-3) ② 갤러리 데모(P-4)
  ③ 네이티브 호출 실패 시 폴백(fail-open to custom).
- **무해화 불변** — 선택 결과는 경로일 뿐. 프로필 이미지는 여전히 imgdec(R-5)
  경로, 수신 게이트(DR-13)와 무관.

## 4. 구현 수단 비교 — 🔴 결정 필요

### 4-1. Win/mac: 직접 어댑터 (권고 ✅)

| | 내용 |
|---|---|
| Windows | `IFileOpenDialog` COM — ole32/shell32는 **OS 표준 DLL**(런타임 의존 0 유지 · MotW 어댑터와 같은 계열) · 폴더 = `FOS_PICKFOLDERS` |
| macOS | `NSOpenPanel` — objc 직접 메시지(NSSound·quarantine 어댑터 선례 있음) |
| 근거 | 이 저장소는 이미 OS API 직접 호출 문법이 자리 잡았다. 크기·의존 통제 완전 |

### 4-2. 대안: `rfd` 크레이트 (MIT — DR-12 통과)

전 OS를 감싸 개발이 빠르다. 단 **Linux에서 GTK3 링크가 기본**(런타임 의존 발생 —
NFR-B-3 위반) → `xdg-portal` 피처를 골라야 하는데 그러면 zbus 의존 체인이 크다.
Win/mac만 쓰고 Linux는 제외하는 부분 채택도 가능하나, **직접 어댑터 대비 이득이
크지 않다**(감쌀 API가 창 하나 분량).

### 4-3. Linux — 시스템 "기본 다이얼로그"가 없다

| 후보 | 평가 |
|---|---|
| **xdg-desktop-portal**(D-Bus `FileChooser`) | 표준(GNOME/KDE/Flatpak) · 단 D-Bus 클라이언트 필요(zbus 체인 또는 수제 구현 — 무겁다) |
| zenity/kdialog 외부 실행 | 의존 0(exec) · 설치 안 된 배포판 있음 · 프로세스 경계 관리 |
| **자체 피커 유지(폴백)** | v1 현실해 — Linux 실기가 아직 없고(2-PC는 Win↔mac), 데스크톱 환경 파편화 대응은 v1.5+로 미룬다 |

**권고**: v1 = **Win/mac 네이티브 + Linux 자체 피커 유지**. Linux portal은 실기
가능해질 때 별도 슬라이스(v1.5)로.

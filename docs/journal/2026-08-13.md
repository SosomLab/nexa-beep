## 구성원 초대(Suggest) + 방별 초대 정책 — 부분 가시성 검토 완결 (main)

**사용자 질문 검토** — "A가 B·C 초대, B가 D 초대 → C만 D를 못 보는 분기?" ·
"한 명이라도 미연결이면 초대 Fail?"

**결론([31 §4-1](../31-adr-0012-shared-group-chat.md) 신설)** —

1. **분기 없음**: 구성원 초대를 열어도 명부 갱신 주체는 소유자뿐(`Suggest` 요청 경유)
   → D 편입 = 소유자 명부 v+1 → **전원 배포**. C의 구버전 시점은 배포 지연일 뿐
   (대기+자동 연결·버전 번호로 수렴).
2. **초대 Fail 처리 안 함**(확정): 서버리스에서 일시 오프라인은 일상 — fail-fast는
   그룹 생성을 좌절시킨다. 명부 즉시 확정 + 전달 상태(대기/전달/수락) 표시가 정직.
3. C↔D 상호 미연결은 명부와 무관한 **전송 한계**(FR-G-4 표시 · 발신자 보관 재동기 ·
   릴레이 GS-2가 근본 해소 — 사용자 인지("릴레이 이후엔 없을 것")와 일치).

**구현(사용자 확정 3건)** —

- **구성원 초대 = 기본 기능**: `SGroupMsg::Suggest{uid, members}`(kind 7) — 구성원이
  소유자에게 요청, 소유자가 정책 확인 후 명부 반영·전원 배포·신규자 초대. 정책 off
  시차 요청은 스레드에 거절 고지(조용히 버리지 않음). 소유자 오프라인 = 요청 대기
  (자동 연결 — 멤버십 동결 한계와 같은 축).
- **방별 정책 `member_invite`**: roster에 필드 신설 — ★ **P-11 확장 영역 첫 사용**
  (`ext` 첫 바이트 bit0 · 빈 확장 = 기본 허용 = 구버전 호환 · 포맷 변경 없음 검증).
  방별 변경 = 그룹 행 우클릭(소유자) "소유자만 초대로 전환 ↔ 구성원 초대 허용으로
  전환" = roster v+1 배포.
- **전역 설정** `group.member_invite`(그룹 카테고리 · **Switch · 기본 허용** · 4언어)
  — **새 방 생성 시 기본값으로 상속**(생성 시점 복사 · 이후는 방별 정책이 진실).
- 그룹 메뉴 소유자/비소유자 분기: 소유자 = 이름 변경·초대/제외·정책 토글·해산 /
  구성원 = (정책 on) 선택 N명 초대·그룹 나가기.

## 서버 모드 방향 설계(32) + `recv_any`의 Group 누락 (main · `398f6ff`·`1cd0963`)

### [32 ADR-0013](../32-adr-0013-server-modes.md) — 세 모드는 기능 누적이 아니다

사용자 요청(**방향성만** — 구현은 v1 이후 별도 저장소 DR-9). 세 모드를 "릴레이 + 저장 + 관리"라는
기능 누적으로 보면 반드시 샌다. 정확한 정의는 **"서버가 무엇을 아는가"의 세 단계**이고, 기능을
더할 때 물어야 할 질문은 *"서버의 봉투에 무엇이 추가되는가"* — 답이 "내용"이면 설계가 틀린 것이다.

불변식 **S-0~S-3**에서 핵심은 **방향이 반대**라는 점이다: 서버가 없으면 연결은 계속되고
(fail-open **to LAN**), 서버가 있어도 데이터는 안 열린다(fail-closed **on data**). 흐리면
"장애 시 평문 폴백" 같은 최악의 절충이 나온다.

정면으로 다룬 충돌 — 릴레이는 **R-18(영구 재식별자)을 서버로 확대**한다(전 세계 접속이 한 점에
모인다) → **회전 RID**. 부수 효과로 **R-4 스팸도 막힌다**(모르는 사람은 내 RID를 계산 못 한다).
모드②는 **다중 기기(ADR-0007)가 선행 조건**이고 [20 V1-4](../20-adr-0007-multi-device-identity.md)
한 겹 래핑이 여기서 값을 한다 — 순서를 뒤집으면 서버가 신원 권위가 된다. 모드③ 조직 서명은
**TOFU를 대체하지 않는다**(SAS 등급 미부여 = 조직 MITM 차단) · 에스크로는 옵트인 + 상시 고지 +
소급 불가로 **"몰래"가 불가능한 구조**.

### ★ §5 그룹 결합 — 구조적 문제 하나를 찾았다

사용자 추가 요청으로 [31 ADR-0012](../31-adr-0012-shared-group-chat.md)와 엮었다.
[G-3](../31-adr-0012-shared-group-chat.md)의 **pairwise 팬아웃**은 LAN에서 옳지만 릴레이에서는
**N배 업링크**다:

| 상황 | 발신자 업링크 |
| --- | --- |
| LAN · 30명 · 10MB | 300MB (수 초) |
| **릴레이 · 30명 · 10MB** | **300MB (가정용 업로드 약 2분)** |

**텍스트는 무관하고 파일에서 터진다.** 모드②의 **"1회 업로드 + N개 키 봉투"**(본문은 콘텐츠 키로
한 번, 그 키만 구성원별로 감쌈)가 업링크를 O(1)로 만든다 — E2E는 그대로. **이게 모드②의 가장 강한
존재 이유**로 보인다(다른 PC 이어쓰기보다 먼저 체감된다).

그밖에 GS-1~4(서버가 푸는 그룹 한계 4개)와 각각의 **"넘으면 안 되는 선"**(서버는 roster를
보관·배포만 하고 **만들지 못한다**), 새 위험 = **서버는 그룹 그래프를 본다**(내용 몰라도 누가 한
방인지 드러난다 — 완전 은닉 불가를 문서·UI에 적는 쪽을 택했다). 선행 제약 **P-9~P-11**을
[TODO M5-1g](../TODO.md)에 부착했다.

### `recv_any`가 새 `Group` 스트림을 안 봤다

`81dc877`이 `StreamId::Group`(4번째)을 추가했는데 `recv_any`의 큐 소진 목록은 **하드코딩 3종
배열** 그대로였다. 큐에 쌓인 Group 프레임을 아무도 안 빼가 `MAX_QUEUED`를 잠식하고 펌프는
와이어를 계속 기다린다 — **오늘 아침 고친 Backpressure와 같은 뿌리다.**

`StreamId::ALL` 상수로 구조화해 **고칠 곳을 한 곳으로** 만들었다(스트림을 늘려도 빠뜨릴 수 없다).

> ★ **테스트 fake에 수신 타임아웃을 넣은 게 이번의 배움이다.** 처음 회귀 테스트를 짜고 버그를
> 되살려 봤더니 **실패가 아니라 행**이 났다(큐에 갇힌 프레임 → 와이어 무한 대기 → 300초 타임아웃).
> **행은 신호가 아니라 침묵**이라 회귀 테스트로 쓸모가 없다. fake가 타임아웃을 지키게 하니
> **0.20초 만에 FAILED**로 바뀌었다.

## ADR-0012 Accepted + 공유 그룹 G1~G3 — 한 방 대화 개통 (main)

**D-28 완결(사용자)** — §1 방향 전체 ✅("바로 구현") · §2 재동기 주체 = **송신자** ✅
(설정 `group.resync_keep` — CatGroup 신설 · 50/200/1000+직접 입력 · 대기 큐 상한에
즉시 배선) · §3 동보 그룹 = **숨김** ✅.

**구현 조정(정직 기록)** — ADR 원안의 roster **서명은 세션 인증으로 대체**: 배포를
소유자의 인증 Noise 세션 직접으로 한정하면 "소유자가 보냈다"가 세션이 보증한다.
신원 키가 X25519(서명 불가)라 서명 인프라는 DR-20과 함께 — 중계·오프라인 검증이
필요한 G4+/v2에서 얹는다. GroupUid도 해시 파생 대신 **무작위 32B**(같은 근거 —
세션 인증 모델에서 값 위조는 무의미).

**G1 — 코어·와이어·저장**

- `nbeep-core::sgroup` — `GroupUid`·`Roster`(encode/decode + `accepts_update`: 같은
  uid·같은 소유자·버전 증가만 — 구버전 재생·소유자 바꿔치기 거부 테스트) ·
  `SGroupMsg` 6종(Invite/Accept/Decline/Roster/Msg/Leave · kind 1B · 미지 무시).
  ★ **P-11**([32 §8]) 선제 — roster 끝에 정책 확장 영역(`ext_len u16` · 현재 0):
  `history_on_join` 등이 들어와도 포맷 변경이 아니다.
- `StreamId::Group`(=3) 신설(mux 큐 4개).
- `groups.seg` **v2** — 공유 레코드(`local_id·roster·mine(Owner/Joined/Invited)`) ·
  v1 파일 관용 읽기 · `upsert_shared`(수용 규칙 강제)·`set_mine`·`remove_shared`.
  로컬 id 공간 공유(`alloc_id`) — UI·스레드 키는 기존 `GroupId` 그대로(최소 침습).

**G2 — 초대·수락**

- 그룹 만들기(다중 선택 → 이름 모달) = roster v1(owner=나·구성원 정렬) 저장 +
  **전원 `Invite` 발송**. 미연결 구성원 = `pending_invites` 대기 + 자동 연결(성립 시
  명부 먼저 flush — 본문보다 앞서야 수신측이 방을 안다).
- 수신측: **발신자 = roster.owner** 확인(세션 인증) + 내가 명부에 있을 때만 →
  Invited 저장 + **수락/거절 카드**(AlertWidget `with_choice` — Enter=수락·Esc=거절).
  수락 = Joined + `Accept` 통지("목록에서 열기") · 거절 = `Decline` + 소유자가 명부
  제외 재배포.

**G3 — 방 대화·명부 운영**

- 방 발신 = 명부(나 제외) **Msg 팬아웃**(Group 스트림 · seq = 기존 Sequencer 공유) ·
  미연결 = 본문 대기+자동 연결(보관 상한 설정) · FR-G-4 라인 유지.
- 방 수신 = 명부 구성원 발신만 수용(fail-closed) · dedup = 기존 `(기기, seq)` +
  세션 경계 리셋 — **P-10 충족**(중복 키 삼중항은 uid가 와이어에 있어 파생 가능) ·
  **발신자 라벨 풍선**(`ChatLine::with_from` — 카카오톡류) · 방 unread 배지(그룹 행
  우측 알약 + 주 창 제목 합산) · 방 열면 해제.
- 명부 운영(소유자만 — G-6): 추가 = 신규자 Invite + 기존자 Roster 배포 · 제외 =
  제외자에게도 마지막 1회 · 개명 = v+1 배포 · 해산 = "구성원 = 나뿐" 명부 배포(전원이
  자기 제외를 앎) · 탈퇴(비소유자) = Leave → 소유자 재배포 · **제외/해산 수신 = 방
  자동 닫힘 + 고지**.
- 목록 그룹 섹션 = **공유 그룹만**(Invited 제외 — 카드로만 · 동보 숨김 확정 반영).
- chat-live 테스트 단말: Group 스트림 관찰 로그(초대·본문 — 수락 UI 없음 명시).

## GUI 실행 가능 세션 판정 — 3-OS (main · `e230e58`)

**사용자 요청** — 실행 상태를 보고 GUI 가능 여부를 판단하고, 불가능하면 콘솔에 경고 후 종료.
원격 PowerShell·SSH 포함.

그전에는 **못 여는 자리에서 그냥 죽었다.** 릴리스는 `panic = "abort"`라 `Exited (134)`(SIGABRT)에
"시스템 UI 폰트 없음" 한 줄이 전부였다. 무인자가 창이 된 뒤로(`ad7dbfa`) **원격 셸에서 무심코
친 `nexa-beep`이 바로 이 경로**라 더 중요해졌다.

### 관측과 판정을 나눴다

`nbeep-plat::gui` — OS API를 부르는 `observe()`와 사실만 보는 순수 함수 `decide(os, facts)`.
판정이 순수라 **3-OS × 세션 종류 전부를 맥에서 테스트**한다. 조건부 컴파일 코드는 반대편을
실행해 볼 수 없다는 게 이 저장소의 반복된 함정이라, 그 축을 아예 테스트 가능하게 만들었다.

| OS | 신호 | 주의 |
| --- | --- | --- |
| Windows | `GetProcessWindowStation` 이름 | 대화형은 `WinSta0` 뿐. **RDP도 `WinSta0`라 통과** — 원격이라고 막으면 되는 걸 막는 것이다 |
| macOS | `CGSessionCopyCurrentDictionary()` NULL 여부 | `launchctl managername`과 같은 판정을 **서브프로세스 없이** |
| Linux·BSD | `$DISPLAY`/`$WAYLAND_DISPLAY` | `ssh -X`는 DISPLAY를 채운다 → **SSH 여부보다 DISPLAY가 먼저** |
| 전부 | UI 폰트 존재 | 세션이 되어도 폰트가 없으면 못 연다. 사유를 나눈 이유 = 할 일이 다르다(폰트를 깔면 된다) |

신호를 못 얻으면 **막지 않는다** — 오탐으로 멀쩡한 실행을 막는 쪽이 더 나쁘다. 단 SSH가
확실하면 막는다. 의존은 0(extern 선언만). exit 코드는 **3**(2는 이미 "알 수 없는 인자").

## 재대화 메시지 증발 + 끊김 시 스레드 소실 — dedup 세션 리셋·스레드 대피 (main)

**실기(사용자)** — ① `/quit` 후에도 계속 대화가 다시 열린다 ② 터미널에서 챗을 보내도
GUI 배지가 안 오른다(전송 증발) ③ 받았던 메시지도 안 보인다. (+ 대기 중 `/quit`은
직전 수정으로 ✅ 동작 확인)

**원인 3갈래** — 서로 다른 원인이 겹쳐 "메신저가 안 된다"로 보였다:

1. **② = seq 리셋 × DedupIndex 기기 수명 기억.** CLI는 대화마다 `Sequencer::new()`
   (seq 1부터), GUI의 `DedupIndex`는 앱 수명 — 2번째 대화부터 `(기기, seq)`가 이미
   본 값이라 **조용히 중복 폐기**. GUI 재시작(오늘 여러 번) → GUI 발신도 같은 원리로
   장수 터미널에서 폐기될 수 있는 대칭 구조. M2-4의 "재시작 복원(resume_after)"이
   영속(M2-5b) 없이는 못 도는 갭이 실기로 드러난 것.
2. **③ = `Closed`가 대화를 통째로 삭제.** `Conversation`이 세션 채널(out_tx)과
   스레드(lines)를 한 몸으로 들고 있어 세션 죽음 = 스레드 소실 — **DR-26**("대화
   상태는 뷰와 분리·상대별 유지") 위반. 끊김·재연결이 잦은 실기에서 즉시 체감.
3. **① = GUI 자동 재연결(ⓑ) × chat-live 상주 accept의 조합**(각자는 설계대로).
   CLI `/quit`은 "의도적 종료"인데 와이어에 그 신호가 없어 GUI는 장애 끊김으로 보고
   5초 후 재연결 → 터미널이 수락 → 대화 재시작. **버그 아님 — 설계 공백**(정중한
   종료 신호). D-23의 N-1~N-4(M2-4b 제어 메시지)에 `Bye` 자리 검토로 등록.

**수정**:

- **`DedupIndex::reset_device`**(core) — **새 세션 성립 = 그 기기 기억 리셋**. 옛
  세션 메시지의 재생은 Noise 세션 키가 원천 차단하므로 중복 창의 소임(재전송·다중
  경로)은 세션 안에서만 유효 — 경계 리셋은 안전성을 줄이지 않는다. 테스트 +1
  (재시작 seq 수용·다른 기기 비영향).
- **스레드 대피소 `parked_lines`**(app) — `Closed`가 세션 채널을 지울 때 lines만
  대피, `install_conversation`이 되찾아 병합(대피 우선 · 경합 교체도 이력 유지).
  `conversations` 존재 여부 = "세션 살아있음" 술어로 쓰는 기존 지점들(목록 점·
  activate·재연결·인바운드 중복 무시)은 그대로 성립한다 — 그래서 필드 분리가 아니라
  대피소 방식(최소 침습).

## chat-live 대기 중 /quit 불통(Windows) — 공유 stdin 채널로 해소 (main)

**실기(사용자)** — chat-live가 **대화 중에는 입력이 되는데, 상대를 기다리는 동안엔
`/quit`이 듣지 않는다**(안내 문구는 되는 것처럼 말한다).

**원인 — Windows에는 raw 터미널이 미구현이라 대기 루프가 stdin을 아예 안 읽는다.**
`RawTerm`은 unix 전용(termios · Windows는 R-16 콘솔 핸들러와 함께 별도 슬라이스로
미뤄둔 자리)이라 `is_raw()=false` → 대기 루프의 비-raw 분기가 "파이프·CI엔 볼 키가
없다"며 sleep만 돌았다 — **Windows 대화형 콘솔도 같은 분기로 떨어진 것**. 대화 중
입력이 됐던 건 run_interactive의 비-raw 폴백(블로킹 줄 읽기)이 따로 있어서인데,
이쪽은 반대로 **세션이 끊겨도 Enter를 칠 때까지 갇히는** 문제가 있었다(같은 날 실기
"[종료] 세션 끊김 후 /exit를 쳐야 했다"의 원인).

**수정 — 전담 스레드 하나가 stdin을 줄 단위로 읽어 채널에 넣고, 대기·대화 루프가
같은 채널을 번갈아 소비한다**(`stdin_lines()` — 각자 직접 read하면 서로 줄을 뺏는다):

- 대기 루프: 100ms 타임아웃 폴로 채널 소비 — `/quit`/`/exit`/`/q` = 종료 · 그 외
  입력 = 안내 재출력. **연결 폴링은 계속 돈다**(블로킹 read를 스레드로 밀어낸 이유).
- 대화 루프(비-raw): 같은 채널 + 타임아웃 폴 — **세션 사망·종료 신호를 즉시 본다**
  (Enter 없이 대기로 복귀 — 부수 수정).
- **EOF 해석 분리**(`IsTerminal`): 사람 터미널의 EOF(Ctrl+Z+Enter) = 종료 의사 /
  파이프·컨테이너(stdin 없음·`docker -d`) = 명령 경로가 없을 뿐 — **연결 대기 유지**
  (그전 동작 보존 · 컨테이너 상주 회귀 방지).
- unix raw 경로는 무변경. HELP_WAITING에 Windows EOF(Ctrl+Z+Enter) 병기.

## WIME-6 실기 재현 — 조합 중 Enter가 전송까지 나가던 것 수정 (main)

**실기(사용자 · WIME 체크리스트 진행)** — WIME-1(대화 조합·자소 백스페이스) ✅ ·
WIME-5(목록↔대화 전환) ✅ · **WIME-6 실패: 조합 중 Enter가 확정 + 곧장 전송**.

**원인 — Windows IME는 조합을 끝낸 키를 앱에 또 준다.** macOS는 조합 중 Enter를
IME(marked text)가 삼켜 Commit만 남지만, Windows는 **Commit 직후 같은 Enter의
KeyboardInput이 별도로 도착**한다. 기존 가드(`ime_composing` 중 차단)는 Commit이
플래그를 먼저 내리므로 이 잔향을 못 막는다 — mac에서 검증한 경로가 Windows 이벤트
순서에서 깨진 것(한/영과 같은 유형 — WIME 체크리스트가 정확히 이걸 잡으라고 있었다).

**수정 1차** — `ime_cleared_ms`(조합 종료 시각): 종료 직후 <120ms의 Enter/Esc 키다운을
1회성으로 삼킴(조합 Enter = 확정만, 2단 전송).

**★ 후속(같은 날) — 사용자 확정으로 Enter는 통과가 정답이 됐다.** 재실기에서 "확정만
되고 Enter를 또 눌러야 전송"이 불편하다는 피드백: **조합 확정+전송이 한 번에**가 원함
(Windows 메신저 관례 — 카카오톡류 · **chat-live 콘솔도 conhost IME가 확정+개행을 한 번에
처리해 이미 이 동작** · DR-16 "동작 = OS 네이티브"). 최종 = **Enter 잔향은 일부러 통과**
(Commit이 버퍼에 먼저 → Enter가 전송 = 동시) · **Esc 잔향만 차단**(조합 취소가 화면
닫기로 새는 건 의도일 수 없다). 애초 실기 보고의 실체는 "전송이 나가서"가 아니라
**조합 중이던 글자가 잘린 채(`홍길ㄷ`) 나가서**였는데, Commit이 Enter보다 먼저 버퍼에
합류하므로 통과시켜도 잘림은 없다 — 잘림은 마지막 음절을 다 치기 전에 Enter를 누른
타이핑 타이밍이었다. mac은 IME가 키를 삼켜 확정만 되는 2단 — OS별 관례 차이 그대로 둔다.
501 green · clippy 0 · rustdoc 0.

## `--chat-live`가 떠돌이 연결 하나에 죽던 것 (main · `9961a55`)

**어쩌다 발견** — 사용자가 준 컨테이너 명령이 적합한지 확인하려고 전제를 점검하다가,

```
[실패] 핸드셰이크: 세션 링크가 닫힘      → exit 0
```

핸드셰이크 실패가 곧 프로세스 종료였다. **광고를 계속 띄우는 단말이 포트 스캐너·헬스체크·
오연결 하나로 죽는 건 말이 안 된다.** 대기를 루프로 바꿔 실패한 연결만 버리고 계속 기다린다.
대화가 끝난 뒤에도 대기로 돌아간다 — 상대가 나갔다고 내가 종료할 이유가 없다.

### 뒤에 두 번째 결함이 있었다

## "이미 시도 중" — 연결 래치가 안 풀리는 구멍 (main · `1f01d59`)

**증상**(사용자 실기) — 목록에서 더블클릭해도 대화가 안 열리고 상태바에
`연결 중… ★테스트단말 (이미 시도 중)`만 계속. 앞선 Backpressure 건과 함께 보고됐다.

### 원인 = 넣은 키와 뺀 키가 다르다

`start_connect`는 **클릭한 상대**(목록 행의 `PeerId`)로 래치를 넣는데, `Outbound` 핸들러는
**핸드셰이크로 밝혀진** `session.peer()`로 뺐다. 평소엔 같지만 **다를 수 있다** — 수동 주소
폴백(`manual_addrs`)은 *주소*로 붙기 때문이다. 그 주소의 상대가 신원을 새로 만들면 성립
세션은 다른 `PeerId`이고, 클릭한 쪽 키는 래치에 **영원히** 남는다. 그 행은 재시작 전까지
다시 열리지 않는다.

**전제 실측** — 컨테이너는 **실행마다 신원이 바뀐다**(`me=58a34b5a` → `5f283d14`).
즉 컨테이너를 재기동한 뒤 옛 행을 클릭하면 곧바로 이 상태다. 사용자 상황이 정확히
그랬다: 세션이 죽고(= 같은 날 잡은 Backpressure 버그) 컨테이너가 재기동된 뒤였다.
**두 버그가 겹쳐 하나처럼 보였다.**

### 고침 — `HashSet`을 타입으로 끌어냈다

`ConnectLatch`(begin/finish/contains/clear). `finish(intent, actual)`이 **둘 다** 해제한다 —
그게 이 타입의 존재 이유고, 문서주석에 왜인지를 박아 뒀다. `AppEvent::Outbound`에
`intent`(클릭한 상대)를 실어 보낸다. 수동 등록 경로는 래치를 안 쓰므로 `intent: None`.

테스트 3건 — **실패 재현**(`clearing_by_actual_only_strands_the_clicked_peer`) ·
회귀 방지(`clearing_by_intent_releases_the_clicked_peer`) ·
실패 경로(`connect_failure_releases_the_latch`). **495 green**.

## ★ 파일 전송이 2MiB에서 매번 끊기던 버그 — mux Backpressure (main · `0fe5073`)

**증상**(사용자 실기 — Docker 리눅스 → 맥, 2.96MB) — 송신이 2.1~2.2MiB까지 진행하다
`[종료] 세션 끊김`. 덤으로 "도커가 죽었다"도 같이 보고됐다.

**재현·계측** — 같은 구성으로 재현되고, 수신측 로그가 결정적이었다: **수신은 32KiB에서
멈췄는데 송신은 2.2MiB까지 갔다**(TCP 버퍼가 그만큼 먹은 것). 삼켜지던 `Err(_)`를 임시로
찍어 보니 **`SessionError::Backpressure`**. 2MiB = 32KiB 청크 × `MAX_QUEUED`(64) — 정확히 일치.

### 원인 = 스트림별 폴링 × 큐 상한

펌프는 한 바퀴에 `recv(Chat)` → `recv(Control)` → `recv(File)`을 돈다.
`recv(Chat)`은 **Chat 프레임이 올 때까지 와이어를 계속 읽으며** 도착하는 File 프레임을 큐에
쌓는데, 정작 File은 한 바퀴에 **하나만** 빼간다. 들어오는 쪽이 빠지는 쪽보다 빠르니 큐는
단조 증가하고, 64를 넘는 순간 fail-closed로 세션을 끊는다.

★ **틀린 것은 코드가 아니라 전제였다.** mux 문서주석은 "정상 트래픽에서 한 스트림만 수십
프레임 밀리는 상황은 프로토콜 위반에 가깝다"고 적어 뒀는데, **M4 파일 전송이 바로 그
"정상적으로 한 스트림을 몰아치는" 트래픽**이다. M2-3에서 맞던 가정이 M4에서 깨진 것을
아무도 되돌아보지 않았다.

### 고침 — 상한을 올리지 않고 큐가 생기는 구조를 없앴다

`MuxSession::recv_any()` 신설 — **"다음에 온 것"을 스트림 표시와 함께** 준다. 펌프가 실제로
원하던 의미다(펌프는 "특정 스트림의 다음 것"을 기다릴 이유가 없다). 큐를 만들지 않으므로
이 실패 양식 자체가 사라진다. CLI([cli/chat.rs](../../crates/nexa-beep/src/cli/chat.rs))·
GUI([app.rs](../../crates/nexa-beep/src/app.rs)) **두 펌프 모두** 같은 버그였고 함께 교체했다.
`MAX_QUEUED` 남용 방어는 `recv()`에 그대로 남는다.

테스트 3건 — **실패 재현**(`per_stream_poll_overflows_on_one_sided_flood`) ·
**회귀 방지**(`recv_any_survives_one_sided_flood` — 상한 4배 홍수에도 순서 보존) ·
큐 우선 소진(`recv_any_drains_queue_before_wire`).

## kitty 키보드 프로토콜 누수 — 터미널 복원 3중 방어 (main · R-16 계열)

**증상(사용자 실기)** — CLI 채팅을 쓰고 난 pane에서 Ctrl+C가 인터럽트 대신 `9;5u`로
찍힘. `reset`으로 수동 복구. 원인 = `RawTerm`이 켠 **kitty 확장 키 리포팅**(`ESC[>1u`
— Shift+Enter 구분용)이 프로세스가 죽은 뒤에도 남음. **상태는 셸이 아니라 터미널
에뮬레이터에 있어서** `exec zsh`로도 안 돌아온다.

**구멍 2개** —

1. **대화 루프의 시그널 부재**: 대기 구간(`wait_with_quit`)은 핸들러+폴링이었지만,
   **연결 후 대화 루프는 블로킹 raw**였고 `--chat-connect`/`--chat-live` 경로는
   핸들러 설치 지점도 지나지 않았다 → 대화 중 Ctrl+C = 시그널 기본 동작 즉사 =
   `Drop` 생략 = kitty 잔존.
2. **릴리스 `panic = "abort"`**(크기 예산 P2) — 패닉 시 되감기가 없어 가드 `Drop`이
   원리적으로 못 돈다.

**처방(3중 방어)** —

1. **대화 루프 = 폴링 + 종료 플래그**(`wait_with_quit`과 같은 패턴): `shutdown::install`
   + `enter_polling` + 매 틱 플래그 확인 · `Ok(0)`(타임아웃)/`Err`(EINTR) = 계속.
   Ctrl+C가 어느 구간에서 와도 **정리 경로(Drop → 복원)를 지나서** 나간다.
2. **전역 복원 레지스트리 + `restore_now()`(멱등)**: 진입 시 원본 termios를 전역
   1슬롯에 등록, Drop·훅 어느 쪽이 먼저 불러도 한 번만 복원(`ESC[<u` pop + tcsetattr).
3. **패닉 훅**(프로세스 1회 설치): `panic = "abort"`여도 **훅은 abort 전에 돈다** —
   거기서 `restore_now()`.

한계(정직하게): `SIGKILL`(kill -9)·터미널 강제 종료는 어떤 프로그램도 못 막는다 —
그때는 `printf '\e[<u'` 또는 `reset`(이번에 쓴 방법)이 정답.

**검증** — PTY(`script`) 실측: `[>1u` push → SIGINT → `[종료]` → **`[<u` pop**이
종료 출력에 실재. 테스트 +1(`restore_now` 멱등·비-TTY 안전) · **489 green** ·
clippy 0 · rustdoc 0.

### ④ 버그 — 수동 등록 상대가 대화창을 닫으면 목록에서 사라진다

원인 = 목록이 **발견 테이블(PeerTable)만** 읽는다. 다른 서브넷 상대는 ANNOUNCE가 안
닿아 테이블에 없고, 대화창이 열려 있는 동안만 보였다. 세션은 살아 있어서 파일 제안이
오면 승인 창은 떴다(사용자 관찰 그대로).

- **`extra_peers`**(비발견 상대 이름 스냅샷) — `install_conversation`에서 테이블에 없으면
  등록, `refresh_rows`가 테이블과 **병합**(발견이 나중에 닿으면 테이블이 이긴다 · paths=0).
- **`manual_addrs`** — 성공한 수동 주소를 기억(`AppEvent::Outbound.via_addr` 신설).
  세션이 끊긴 뒤 목록에서 다시 클릭하면 `connect`(주소록) 실패 시 **수동 주소로 폴백**
  재연결. `peer_title`도 비발견 상대 이름을 안다.

### ② 인바운드 세션이 대화창을 자동으로 열지 않는다

그전엔 상대가 IP 등록만 해도 내 쪽 창이 열렸다(단일 모드 목록 화면·별도 창 모드).
이제 **어느 모드든 창을 뺏지 않는다** — 목록 행 + 상태바 "연결됨: {이름} — 목록에서
열기"만. 여는 것은 언제나 사용자.

### ③ 읽지 않은 메시지 — 배지·개수·마지막 확인 시각·제목 카운트

- `unread`/`last_read` 상태 신설 · **기준 = 그 대화 뷰가 지금 화면에 있는가**(`chat_visible`).
- 수신 텍스트·수신 파일 라인 도착 시 `note_incoming` — 뷰가 보이면 확인 시각만 갱신,
  아니면 **+1 + 상태바 + 주 창 제목 "Nexa Beep — 새 메시지 N"**(작업 표시줄·독에서 보임).
- 목록 행: 신뢰 칩 왼쪽에 **강조색 배지(개수 · 99+ 상한)** + 그 왼쪽에 **"확인 HH:MM"**
  (마지막으로 뷰를 보고 있던 순간 — `fmt_hm` 공개해 대화창과 같은 표기 · 24h 설정 준수).

`WindowLevel::AlwaysOnTop`(winit) — 다른 창에 가려지지 않고 바로 입력.

## 세션 기본 포트 47200 + 설정 영속·포트 생략 입력·상태바 표시 (main · DR-19 후속)

**왜** — 발견이 닿지 않는 곳(다른 서브넷·라우터 너머)에서는 수동 등록(DR-19)이 유일한
길인데, 수신 포트가 매 실행 임의로 바뀌면 **넣을 주소를 알 수 없어 수동 등록 자체가
성립하지 않는다**(08-13 실측). 처방 = 예측 가능한 기본 포트 + 실제 포트의 상시 표시.

**설계** — 사용자 확정(08-13) **ⓐ 하나로 묶기**: 설정 `net.session_port` 하나가
**내가 듣는 포트이자 주소 입력에서 포트를 생략했을 때 거는 포트**다(조직이 같은 값을
쓰면 IP만으로 서로 붙는다). 둘로 나누면 설정만 늘고 다르게 쓸 이유가 없다.

1. **`nbeep-net`**: `DEFAULT_SESSION_PORT = 47200` · `bind_session_listener` — 선호
   포트 우선, **점유 시 임의 폴백**(같은 PC 다중 인스턴스에서 두 번째가 죽으면 안 된다
   — DR-4) · `LocalDirect::spawn_on(.., preferred_port)` + `tcp_port()`(실제 값 노출).
   `spawn`은 기본 포트 위임. **실소켓 테스트 3건**(빈 포트 = 그 포트 · 점유 = 임의
   폴백 · 0 = 처음부터 임의).
2. **주소 입력 포트 생략**(`nbeep-ui::addr_prompt`): `normalize_endpoint(s, default_port)`
   — `10.60.218.157` → `:47200` 자동 부착 · 명시 포트는 유지 · 대괄호 없는 v6은
   추측하지 않고 거부. 검증=정규화 한 함수(판정이 갈리지 않는다). 위젯이
   `default_port`를 들고 힌트도 그 값으로 표시. 테스트 6건(+설정값 반영 1).
3. **설정 항목**: `net.session_port`(CatNetwork 신설 · RadioInput "기본(47200)"+직접
   입력 · i18n 4언어). 값 검증은 소비처 관용 파싱(`session_port_from` — 무효·0·범위
   밖 = 47200), ADR-0011 §4-3 원칙 그대로.
4. **호출부 6곳 배선**: GUI 2곳(부팅·신원 복원) = 설정값 / CLI 4곳(manual·probe·
   chat-connect·chat-live) = **0(임의)** — 테스트 도구가 같은 PC GUI의 기본 포트를
   뺏으면 안 된다. 신원 복원 경로는 `respawn_transport` 헬퍼로 추출(포트 변경과 공용).
5. **핫 스왑**(설정 hot-swap 원칙): `apply_settings`에 `net.session_port` 배선 —
   전송 재시작(성립한 대화 세션은 개별 소켓이라 유지 · 발견 목록은 재공지로 회복) ·
   폴백을 조용히 하지 않는다(점유면 상태바에 "임의 포트 N으로 듣는 중" 명시).
6. **상태바 우측 상시 표시** — `수신 :47200`(실제 바인딩 값 · 상태 문구가 덮지 않게
   클립 분리). 사람이 상대에게 알려줄 값이라 항상 보여야 한다.

## imgdec 픽셀 상한 상향 — 수신 이미지 미리보기 거부 실기 버그 (main)

**무엇이 문제였나** — Windows 실기에서 수신 JPEG(`XGDY9331.JPG`)의 격리함 썸네일·스레드
인라인 미리보기가 뜨지 않았다. 해당 파일을 imgdec에 직접 넣어 **exit 3(디코드 거부)** 확정.

**원인** — 해상도. 이 사진은 2198×2198 = **483만 px**인데 `PIXELS_MAX = 2048²(419만 px)`가
fail-closed로 거부했다. 이 상한은 **프로필 이미지(256KiB) 기준**으로 잡은 값인데,
M4-5ⓑ 수신 파일 미리보기(원본 1MiB)가 같은 상한을 재사용하면서 어긋났다 —
JPEG은 압축률이 높아 561KiB로도 12MP가 흔해서, 4MP 상한이면 요즘 폰 사진 대부분이
거부된다. 4번 스크린샷의 아바타 이니셜("터미") 폴백도 같은 상한이 유력.

**처방** — `PIXELS_MAX` **2048² → 4096²(16,777,216 px)**.

- RGBA 일시 메모리 64MiB — **격리 자식 프로세스 한정**(3초 kill 유지)이라 본체 예산(NFR-B)과 무관.
- 원본 1MiB·변 8192·시간 상한(부모 kill)·fail-closed 구조는 전부 그대로.
- 상수 주석에 "왜 4MP가 모자랐나"를 남겨 재발(상한 하향 회귀) 방지.

**검증**

- 경계 테스트 2건 신설(`nbeep-imgdec`): `phone_photos_within_pixel_cap`(2198² — 실기
  거부 실물 해상도 · 4000×3000 = 12MP · 정확히 4096²) / `oversized_still_rejected`
  (4097×4096 · 변 8193 · 퇴화 0). **481 green**(+2 · 작업 트리의 포트 작업 진행분 9건 포함 실측).
- **종단 실측**: 2198×2198 PNG 수제 생성 → 릴리스 `nbeep-imgdec --max-side 256`에
  파이프 → **exit 0 · `NIMG` + 256×256** 정상 출력(수정 전 동일 입력 = exit 3).

**주의** — 배포본(v0.1.4)의 동봉 imgdec은 구 상한이다. **다음 태그부터 반영**.
문서 정합: [05 R-5](../05-requirements.md) 상한 표기 2048²→4096² 정정.

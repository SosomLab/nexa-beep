## kitty 키보드 프로토콜 누수 — 터미널 복원 3중 방어 (main · R-16 계열)

**증상(사용자 실기)** — CLI 채팅을 쓰고 난 pane에서 Ctrl+C가 인터럽트 대신 `9;5u`로
찍힘. `reset`으로 수동 복구. 원인 = `RawTerm`이 켠 **kitty 확장 키 리포팅**(`ESC[>1u`
— Shift+Enter 구분용)이 프로세스가 죽은 뒤에도 남음. **상태는 셸이 아니라 터미널
에뮬레이터에 있어서** `exec zsh`로도 안 돌아온다.

**구멍 2개** —

1. **대화 루프의 시그널 부재**: 대기 구간(`wait_with_quit`)은 핸들러+폴링이었지만,
   **연결 후 대화 루프는 블로킹 raw**였고 `--chat-connect`/`--chat-live` 경로는
   핸들러 설치 지점도 지나지 않았다 → 대화 중 Ctrl+C = 시그널 기본 동작 즉사 =
   `Drop` 생략 = kitty 잔존.
2. **릴리스 `panic = "abort"`**(크기 예산 P2) — 패닉 시 되감기가 없어 가드 `Drop`이
   원리적으로 못 돈다.

**처방(3중 방어)** —

1. **대화 루프 = 폴링 + 종료 플래그**(`wait_with_quit`과 같은 패턴): `shutdown::install`
   + `enter_polling` + 매 틱 플래그 확인 · `Ok(0)`(타임아웃)/`Err`(EINTR) = 계속.
   Ctrl+C가 어느 구간에서 와도 **정리 경로(Drop → 복원)를 지나서** 나간다.
2. **전역 복원 레지스트리 + `restore_now()`(멱등)**: 진입 시 원본 termios를 전역
   1슬롯에 등록, Drop·훅 어느 쪽이 먼저 불러도 한 번만 복원(`ESC[<u` pop + tcsetattr).
3. **패닉 훅**(프로세스 1회 설치): `panic = "abort"`여도 **훅은 abort 전에 돈다** —
   거기서 `restore_now()`.

한계(정직하게): `SIGKILL`(kill -9)·터미널 강제 종료는 어떤 프로그램도 못 막는다 —
그때는 `printf '\e[<u'` 또는 `reset`(이번에 쓴 방법)이 정답.

**검증** — PTY(`script`) 실측: `[>1u` push → SIGINT → `[종료]` → **`[<u` pop**이
종료 출력에 실재. 테스트 +1(`restore_now` 멱등·비-TTY 안전) · **489 green** ·
clippy 0 · rustdoc 0.

## 2-PC 실기 피드백 6건 — 수신 UX·비발견 상대·모달·--port·텍스트 에디터 (main)

### ④ 버그 — 수동 등록 상대가 대화창을 닫으면 목록에서 사라진다

원인 = 목록이 **발견 테이블(PeerTable)만** 읽는다. 다른 서브넷 상대는 ANNOUNCE가 안
닿아 테이블에 없고, 대화창이 열려 있는 동안만 보였다. 세션은 살아 있어서 파일 제안이
오면 승인 창은 떴다(사용자 관찰 그대로).

- **`extra_peers`**(비발견 상대 이름 스냅샷) — `install_conversation`에서 테이블에 없으면
  등록, `refresh_rows`가 테이블과 **병합**(발견이 나중에 닿으면 테이블이 이긴다 · paths=0).
- **`manual_addrs`** — 성공한 수동 주소를 기억(`AppEvent::Outbound.via_addr` 신설).
  세션이 끊긴 뒤 목록에서 다시 클릭하면 `connect`(주소록) 실패 시 **수동 주소로 폴백**
  재연결. `peer_title`도 비발견 상대 이름을 안다.

### ② 인바운드 세션이 대화창을 자동으로 열지 않는다

그전엔 상대가 IP 등록만 해도 내 쪽 창이 열렸다(단일 모드 목록 화면·별도 창 모드).
이제 **어느 모드든 창을 뺏지 않는다** — 목록 행 + 상태바 "연결됨: {이름} — 목록에서
열기"만. 여는 것은 언제나 사용자.

### ③ 읽지 않은 메시지 — 배지·개수·마지막 확인 시각·제목 카운트

- `unread`/`last_read` 상태 신설 · **기준 = 그 대화 뷰가 지금 화면에 있는가**(`chat_visible`).
- 수신 텍스트·수신 파일 라인 도착 시 `note_incoming` — 뷰가 보이면 확인 시각만 갱신,

- 목록 행: 신뢰 칩 왼쪽에 **강조색 배지(개수 · 99+ 상한)** + 그 왼쪽에 **"확인 HH:MM"**

## imgdec 픽셀 상한 상향 — 수신 이미지 미리보기 거부 실기 버그 (main)

**무엇이 문제였나** — Windows 실기에서 수신 JPEG(`XGDY9331.JPG`)의 격리함 썸네일·스레드
인라인 미리보기가 뜨지 않았다. 해당 파일을 imgdec에 직접 넣어 **exit 3(디코드 거부)** 확정.

**원인** — 해상도. 이 사진은 2198×2198 = **483만 px**인데 `PIXELS_MAX = 2048²(419만 px)`가
fail-closed로 거부했다. 이 상한은 **프로필 이미지(256KiB) 기준**으로 잡은 값인데,
M4-5ⓑ 수신 파일 미리보기(원본 1MiB)가 같은 상한을 재사용하면서 어긋났다 —
JPEG은 압축률이 높아 561KiB로도 12MP가 흔해서, 4MP 상한이면 요즘 폰 사진 대부분이
거부된다. 4번 스크린샷의 아바타 이니셜("터미") 폴백도 같은 상한이 유력.

**처방** — `PIXELS_MAX` **2048² → 4096²(16,777,216 px)**.

- RGBA 일시 메모리 64MiB — **격리 자식 프로세스 한정**(3초 kill 유지)이라 본체 예산(NFR-B)과 무관.
- 원본 1MiB·변 8192·시간 상한(부모 kill)·fail-closed 구조는 전부 그대로.
- 상수 주석에 "왜 4MP가 모자랐나"를 남겨 재발(상한 하향 회귀) 방지.

**검증**

- 경계 테스트 2건 신설(`nbeep-imgdec`): `phone_photos_within_pixel_cap`(2198² — 실기
  거부 실물 해상도 · 4000×3000 = 12MP · 정확히 4096²) / `oversized_still_rejected`
  (4097×4096 · 변 8193 · 퇴화 0). **481 green**(+2 · 작업 트리의 포트 작업 진행분 9건 포함 실측).
- **종단 실측**: 2198×2198 PNG 수제 생성 → 릴리스 `nbeep-imgdec --max-side 256`에
  파이프 → **exit 0 · `NIMG` + 256×256** 정상 출력(수정 전 동일 입력 = exit 3).

**주의** — 배포본(v0.1.4)의 동봉 imgdec은 구 상한이다. **다음 태그부터 반영**.
문서 정합: [05 R-5](../05-requirements.md) 상한 표기 2048²→4096² 정정.

## Auto 속도 실측값 표시 — 설정 행 하단 정보 줄 (main · Windows PC)

**요청(사용자)** — 설정 Files의 Upload/Download limit "Auto (50% of peak)"에
대해 *"Auto로 측정된 값을 하단 설명에 보여줘. 자주 갱신할 필요는 없어보이고
성능에 영향이 없는 수준에서 갱신해주면 돼!"*

**문제** — 측정값이 GUI에 없었다. 진짜 계측기(`RateMeter`)는 **세션 액터
스레드의 지역 변수**(페이싱이 거기서 돌므로 맞는 자리)고, app의
`send_meter`/`recv_meter` 필드는 **한 번도 관측을 받지 못해 peak=0**(상태바
라벨이 늘 하한 256KiB/s를 보여 준 이유이기도 하다).

**처방 — 완료 이벤트에 실측을 실어 GUI 집계기로**:

- `RateMeter::note_peak(bps)` 신설(core) — 이미 계산된 속도를 peak 후보로.
  바이트 흐름을 못 보는 집계기용(더 큰 값만 남는다 — 회귀 테스트 동반).
- `XferSendDone`에 `peak_bps` 추가 — 액터의 **관측 최고**(평균은 대기가 섞여
  링크 능력을 과소 평가 — rate.rs 문서의 그 이유). GUI는
  `note_peak(peak.max(avg))` — 프로브 크기 미만 소파일은 창이 안 닫혀 peak=0일
  수 있어 평균이 하한.
- 수신은 액터에 계측기가 없다 — `XferDone`의 `avg_bps`가 유일한 실측(보수적
  하한)으로 `recv_meter`에 반영.
- **표시 = 기존 노트 채널**(`set_row_note` — 값 불변이면 무효화 생략): 1초 주기
  `refresh_approval_ui`에 태워도 **비용 0**(peak는 전송 완료 때만 변한다 —
  "성능에 영향 없는 수준" 요구를 채널 성질로 충족). 전송 완료 이벤트에서도
  즉시 갱신.
- **문구는 두 축의 진실을 따른다**: 발신 Auto = "실측 최고 X → 자동 목표 Y"
  (Y = 50%·하한 적용) / 수신 Auto = "실측 최고 X · **상한 무주장** — 발신자가
  절반으로 양보"(M4-11 `advertised_cap` 원칙 — 수신 Auto는 목표가 없다).
  실측 전 = "실측 전 — 하한 256KiB/s에서 시작"(발신). Auto 아니면 줄 제거.

재링크).

## 초과 사진 선택 시 2단계 깜빡임 제거 — push 보류 + 세대 번호 (main)

**실기(사용자)** — 큰 사진 선택 시 상대가 "옛 내장 그림(원숭이) → 실사진"
2단계를 봤다. 원인 = 깔때기 push가 축소본 워커보다 **먼저** 나가 사진 없는
프레임(내장 키만)이 1단계로 실렸다(직전 커밋의 "자기 치유 순서"의 대가).

- **push 보류** — `wire_pending` 동안 `push_profile` 전체 보류, 완료 이벤트가
  Full을 **한 번에** 민다(그 사이 바뀐 텍스트 필드도 동승). 실패해도 push는
  나간다(사진만 빠지고 텍스트·키 폴백은 닿아야 한다 + 경고 유지).
- **세대 번호(`wire_gen`)** — 워커는 파일을 안 쓰고 **바이트로 복귀**, 메인이
  세대 일치 확인 후에만 `me.wire.png`를 쓴다. 사진 A 워커 도는 중 B로 바꾸면
  A 결과는 조용히 폐기 — **낡은 축소본이 새 선택을 덮는 경합 자체가 없다**
  (파일 쓰기·판정 = 메인 단일 지점). 중복 스폰 가드(13 §12-1) 동반.

## 프로필 사진 256KiB 초과 "조용한 생략" 종결 — 와이어 축소본 + 두 필드 동시 송수신 (main)

**증상(실기·스크린샷)** — 본인 프로필은 실사진인데 **상대에게는 직전에 선택했던
내장 아바타(뱀)** 가 보였다. 사용자 추가 관측: "PNG 스티커는 전파되는데 JPG
사진만 안 된다" — **포맷은 무관, 범인은 크기다**(실측: 스티커 PNG 66,745B ≤
상한 / 사진 JPG **574,963B > `PROFILE_IMAGE_MAX` 262,144B**).

**원인 사슬** — ① `my_profile_frames_scoped`가 상한 초과 사진을 **조용히 생략**
(`filter(b.len() <= MAX)` — 경고 없음) → ② `image_shared=false`가 되고, 내장
아바타 키 조건 `share_basic && !image_shared`가 참이 돼 **옛 내장 키를 대신
광고** → ③ 상대는 뱀. 본인 미리보기는 로컬 디코드(상한 무관)라 정상으로 보여
발견이 늦었다.

**수정 3겹(사용자 확정 — "두 필드 동시 송수신 + Custom 우선 + NULL 엄격")**

1. **와이어 축소본(근본)** — imgdec에 `--encode-png` 모드 신설(인코딩도 imgdec
   몫 — 본체는 이미지 인코더도 링크하지 않는다 · R-5 결): 원본이 상한 초과면
   워커에서 256px PNG(`data/profiles/me.wire.png`)를 굽고 프레임은 그 파일을
   싣는다. 완료 = `AppEvent::WireAvatar` → **Full push 재전파**(자기 치유 순서 —
   변경 직후 깔때기 push엔 키만 나가고, 축소본이 준비되면 실사진이 따라간다).
   부팅에서도 보장(기존 초과 사진 사용자 자기 치유). **실측: 문제의 574KB JPG →
   256×256 PNG 102,922B**(상한 이내). encode 입력 상한 16MiB(원본 폰 사진 대비 ·
   픽셀 상한 4096²는 동일 — 할당 폭탄 방어 유지) · 왕복 회귀(비트 동일).
2. **두 필드 동시 송신** — 내장 키 조건에서 `!image_shared` 제거: 사진과 키가
   **항상 함께** 실린다. 사진이 어떤 이유로든 빠져도 수신측 폴백이 명확하고,
   "옛 키가 사진을 대변하는" 통로 자체가 사라진다.
3. **수신 사진 우선** — `image_keep`+내장 키 동시 도착 시 내장이 사진을 덮던
   승계 구멍 수정(공유 사진이 살아 있으면 그 그림이 이긴다 · 키는 폴백).

**NULL 엄격** — `image_path` 변경·비움 시 옛 축소본 즉시 삭제(안 지우면 철회가
안 나간다). 축소 실패는 **조용히 넘기지 않는다** — 상태바 경고("사진이 256KiB
초과인데 축소 생성 실패 — 전송되지 않습니다").

**교훈** — *조용한 생략은 언젠가 "왜 상대에게 옛 그림이 보이지?"로 돌아온다.*
빠뜨릴 수 있는 경로에는 ① 폴백을 명시적으로 싣고(두 필드 동시) ② 실패를 소리
내게 한다. 그리고 **상관관계(PNG는 되고 JPG는 안 됨)는 원인(크기)이 아니다** —
실측 두 파일의 바이트 수가 판정을 끝냈다.

**검증** — 655 green(imgdec 왕복 회귀 포함) · clippy 0 · rustdoc 0 · 실물 JPG
인코드 실측 통과.

## 대화창 명령 2차 확정 — 첫 글자 `/`는 무조건 비전송 (main)

**사용자 확정(08-16 2차)** — "trim 필요 없고 무조건 첫 글자가 `/`로 시작하는
경우만. **첫 글자가 `/`로 시작하는 모든 입력은 전달 대상이 아님**." 종전 규칙의
예외 3종(`//` escape · 한 줄 한정 · `/` 단독 통과)을 **전부 폐지**했다.

- 판정 = trim 전 원본의 **첫 글자 하나**(앞 공백 = 메시지 — 종전과 동일).

  경로가 아예 없다(안 보냈음이 안내로 보인다).
- `/` 단독·`/   ` = Unknown 안내(비전송) · 미지 이름 = fail-closed 그대로.
- 회귀: `any_leading_slash_is_never_sent`(어떤 형태든 Text/Empty로 새면 실패) ·
  멀티라인 비전송. app.rs의 구 escape 주석 2곳 정리.

## 대화 화면 개편 — 말풍선·타임스탬프·멀티라인 입력·클립보드 (`feat/m3-chat-input`)

사용자 요청이 실기 확인과 함께 연쇄로 들어왔다(입력 UX 5건 → 시각 표시 → 말풍선 확정안).
설계가 진행 중 두 번 상향됐다: *분 단위 구분선* → **개별 풍선 시각 + 날짜 중앙 알약**(구분선 취소).

**스레드 — 말풍선.** 수신 = 좌측 / 발신 = 우측(accent). *"풍선을 사용자정의 컨트롤로 만들어야
하나"* 검토 결론 = **아니오** — 컨트롤은 포커스·자체 이벤트를 갖는 재사용 단위인데 풍선은 둘 다
없고 상태는 `ChatLine`이 소유한다. `controls` 상속(포커스 링·도움말 "?")은 과잉 — **렌더
프리미티브**로 위젯 안에 둔다. 풍선 폭 2/3 상한 자동 줄바꿈(공백 우선·문자 폴백) ·
**픽셀 스크롤 전환**(가변 높이 블록엔 행 단위가 안 맞는다) + 오버레이 스크롤바(설정·갤러리 문법).

**시각 표시.** 기록은 **밀리초 원본**(`at_ms`) + 표시용 지역 벽시계(`WallTime` — ui는 OS
시간대를 모르니 호스트가 plat에서 변환 주입 · DR-21). 풍선 옆 시각은 **같은 발신자·같은 분
묶음의 마지막에만**(카카오톡 관례) · 날짜가 바뀌면 **중앙 알약**("2026-08-10 (월)" — 요일은
Zeller). 설정 2종 신설: `chat.time_24h`(끄면 `PM 7:02`) · `chat.date_format`(`2026-08-10`/`8/10`).

**입력창.** Shift+Enter 줄바꿈 — **최대 4줄 표시, 초과는 캐럿 추종 스크롤**(+스크롤바) ·
캐럿 높이 = **글자 실측**(과대 표시 수정) · 상하 여백 동일(세로 중앙) · **마우스 드래그 선택**
(paint가 줄별 문자 경계 x를 캐시 — 이벤트 시점엔 폰트를 잴 수 없다) · 라인 단위 Home/End ·
멀티라인 Up/Down · Ctrl+A/C/X/V.

**★ plat 실물 2건.**
- `clipboard` 신설 — Windows CF_UNICODETEXT를 **Win32 직접 호출**(런타임 의존 0 유지).
  mac/linux는 objc·디스플레이 서버 연동이 필요해 의도된 보류(M3-1b) — `None`/`false`로 정직.
- `clock::LocalTime`(연월일시분초) + ★ **Windows 지역 시각 실물**(FILETIME→
  `SystemTimeToTzSpecificLocalTime`) — **기존 Windows는 UTC 폴백이었다**(타임스탬프를 보여주는
  순간 드러났을 결함을 선제 수정). UTC 폴백도 civil-from-days로 날짜까지 정확히.

**단체 대화 대비(후속 확정)** — 수신 풍선 위 **송신자 이름 행**(`ChatLine.from` · 빌더
`with_from`). 같은 송신자 연속 묶음은 첫 풍선에만(카카오톡 관례) · 1:1은 헤더가 식별하므로
생략(None). 그룹 대화 뷰(M5)가 이름만 주입하면 그대로 동작한다.

**★ app의 잠복 결함 2건이 함께 드러났다.** ① Key 이벤트가 항상 `shift:false`로 라우팅되고
있었다 — Shift+Enter·Shift+선택이 구조적으로 불가능했던 상태. 수식키 추적을 추가하고 실제
상태를 전달. ② **←/→가 키 매핑 목록에 없어서** 대화 입력의 캐럿 이동 자체가 안 됐다(위젯
핸들러는 있는데 이벤트가 도달하지 않음 — "Home/End도 동작해야" 지적의 진짜 원인 후보).

## 격리함 UX 정비 · 설정 포커스 버그 · 툴바 직접 등록 · 갤러리 현행화 (`feat/ui-quarantine-gallery`)

같은 PC에서 GUI+CLI를 함께 돌리는 테스트에서 **테스트단말(다른 노드)이 수신한 파일이 내

아직 실행마다 새로 생성되므로(영속 = M2-5·D-18) 그 전까지는 채널로 가른다 — **재시작 후에도

**④ 설정 화면 — Face 입력이 검색창으로 새던 버그(사용자 실기 스크린샷).** 원인 2중:

## 파일 전송을 대화 스레드 항목으로 — 진행률·완료 기록 잔존 (`feat/m4-xfer-thread`)

사용자가 M1-4b 수정 직후 시나리오 A로 파일 송수신을 실기 확인하고 3건을 지적했다:
**"전송된 파일 정보를 볼 수 없다 · 송수신 진척도가 안 보인다 · 완료 후에도 대화창에 남게 해달라."**
맞는 지적이다 — 기존 진척 줄(08-09)은 **헤더의 일시 표시**(`Option` 하나)라 완료 순간 사라지고,
대화 저장소(`Conversation.lines`)에는 파일 전송이 아예 기록되지 않았다. 상태바 문구가 유일한
흔적인데 다음 상태 문구가 오면 덮인다.

**구현.**

| 변경 | 내용 |
|---|---|
| `ChatBody` 신설 | 스레드 줄 본문을 `Text(SafeText) \| Xfer(XferLine)` 2종으로 — 전송 항목 = 파일명·크기·상태 |
| 상태 기계 | `승인 대기 → 진행(누적 바이트) → 완료(부가 설명) / 실패(사유)`. **종결 상태는 불변** — 완료 기록은 갱신 대상에서 제외되고 새 전송은 새 항목으로 쌓인다 |
| `update_xfer_in` | **가장 오래된 미종결 항목**(방향 일치)을 갱신. ★ 처음엔 뒤에서 찾게 짰다가 설계 중 스스로 뒤집었다 — **오퍼 큐가 FIFO**라 대기 2건일 때 앞 건의 거절이 뒤 항목에 붙는다 |
| 렌더 | `나:/상대: [파일] 이름 (크기) · 상태` + 진행 중 우측 소형 막대(발신 accent/수신 ok — 목록 막대와 같은 문법). 이모지 대신 텍스트 라벨(시스템 폰트 글리프 부재 대비) |
| app 배선 | **저장소+뷰 동시 갱신**(DR-26 — 뷰 닫아도 유지·재열기 복원). 전이 지점 8곳: 오퍼 발신·수신(대기)/수락(진행 0)/청크(진행)/발신 완료/수신 완료(**격리됨 · 위험 등급** 표기)/거절·취소·시간 초과·실패(사유) |
| 파일명 무해화 | 원격 제공 값이라 스레드 표시 전 `sanitize_message` 통과(RLO 등 — 스레드 타입 규약 유지) |

**설계 판단 2건.**
- **자동 거부(정책)는 스레드에 남기지 않는다** — 무인증 상대의 스팸 오퍼가 대화 기록을
  오염시키면 그 자체가 공격면이다(FR-S-46 취지). 묻지도 않은 것은 기록도 하지 않는다.
- 헤더의 일시 진척 줄은 **유지** — 다중 파일 배치 합계(2/5 파일)는 배치 단위 정보라
  항목별 진행과 역할이 다르다.

**검증** — ui **148 green**(+5: 수명 주기·FIFO 2건 대기·방향 격리·종결 불변·최신 스냅) ·
워크스페이스 **376 green** · clippy 0 · 릴리스 1.06MB. GUI 실기(승인 대기 표시→진행 막대→완료
잔존→재열기 복원)는 사용자 확인 대기.

## M1-4b — R-21 수정: 주소록을 후보 목록으로 (`fix/m1-4b-addr-candidates`)

사용자가 시나리오 A(GUI `--window --live` + `--chat-live 테스트단말`)를 Windows에서 실기로 돌려
**"목록에는 뜨는데 클릭하면 `연결 실패: Unreachable`"** 을 확인했다 — 아래 감사가 예고한
*"클릭했는데 대화창이 안 열렸다면 그게 이 결함"* 그대로다. 회귀인지 물어서 먼저 판정했다:
`local.rs`·`udp.rs`의 마지막 변경은 08-08(맥에서 실증 성공한 그 커밋)이라 **코드 변경이 아니라
R-21의 재현**이다. 맥에서 가려졌던 이유는 v6 관측이 주소록에 기록되는 조건이 성립하지 않아서다.

**구현 — 권장안 ⓒ(주소 후보 목록 순차 시도).**

| 변경 | 내용 |
|---|---|
| `PeerAddrs` 신설 | 상대별 후보 목록 — 관측 순 보관·중복 제거·**상한 8**(초과 시 가장 오래된 후보부터 밀어냄) + `preferred`(마지막 성공 주소) |
| 시도 순서 | **성공 경로 → v4(관측 순) → v6(관측 순)**. v4를 앞세우는 근거 = 수신 TCP가 현재 v4 전용. **v6 단독 환경은 v4 후보가 없으므로 자연히 v6로 간다**(ⓑ "v6 제외"가 버리는 FR-D-7을 지킨다) |
| `connect` | 후보 순차 시도 + 성공 주소 승격. 잠금은 스냅숏·승격 순간에만(연결 대기 중 보유 금지) |
| `add_endpoint` | 호스트명 해석 결과가 여럿이면 **같은 원리로 v4 우선 순차 시도** — 첫 항만 쓰던 기존 코드는 v6 우선 해석 환경에서 같은 비대칭이 재발한다(DR-19 경로에도 R-21이 숨어 있었다) |

**회귀 테스트 6건** — 핵심은 감사가 못박은 조건 그대로: **"주소록에 죽은 v6가 섞여 있어도
연결이 성립하는가"**(루프백 실소켓만 사용 — 멀티캐스트·권한 불요라 CI 가능). 나머지 =
v6가 나중에 관측돼도 v4 우선(구 코드의 "덮어쓰기" 시점 재현) · 승격 경로 최우선 ·
중복 제거·상한 · 순차 폴백 · 전멸 시 `None`.

**실측(Windows 11 x64, 이 PC).**

| 시나리오 | 결과 |
|---|---|
| 헤드리스 2노드 `--live-echo 25` 동시 기동 | 양방향 왕복 성공 · **연결 실패 0**(어제는 왕복 2회 후 6~7회 연속 실패) |

| 게이트 | 워크스페이스 **371 green**(+6) · clippy 0 · fmt ✅ |

기본값 상이)을 4타깃 검증표와 함께 풀어야 해서 별도 작업으로 남는다(수신이 v4 전용인 현실은

## Windows 런타임 실측 감사 — 실물 네트워크 종단 성공 + 🔴 R-21 발견 (`docs/win-runtime-audit`)

앞선 "Windows 온보딩"이 **빌드·테스트 게이트**(365 green·fmt·clippy)를 확인했다면, 이번은
**실제로 띄워서 돌려 본** 기록이다. 게이트가 green이어도 런타임은 다른 이야기였다 —
**Windows에서 실물 네트워크 종단이 처음 성공했고, 동시에 P0 결함 하나를 찾았다.**

경위: 세션 내내 `저장소 최신화 → 빌드 → 실행`을 반복하며 macOS 쪽에서 올라오는 커밋을
Windows에서 따라 실행했다. 그 과정에서 나온 실측을 한곳에 정리한다.

### 1. ★ R-21 — 발견은 IPv6로 말하는데 TCP는 IPv6를 듣지 않는다

**증상.** 헤드리스 2노드(`--live-echo`)로 종단을 돌리면 **왕복 2회 성공 후 이후 연결이 전부 실패**한다.
양쪽 노드에서 동일하게, 재현율 100%다.

```
[A] CLIENT got reply from e03d688c: 에코: 안녕! 실물 세션이야   ← 성공
[A] CLIENT got reply from e03d688c: 에코: 안녕! 실물 세션이야   ← 성공
[A] 연결 실패(e03d688c): Unreachable                          ← 이후 6회 연속
[B] SERVER recv from 91cde453: 안녕! 실물 세션이야             ← B도 2회 성공 후
[B] 연결 실패(91cde453): Unreachable                          ← 7회 연속
```

**원인 — 두 곳이 맞물린다.**

| 위치 | 내용 |
|---|---|
| [udp.rs:182-185](../../crates/nbeep-net/src/udp.rs) | 광고를 **3중 발송** — v4 멀티캐스트 · v4 브로드캐스트 · v6 멀티캐스트 |
| [local.rs:47](../../crates/nbeep-net/src/local.rs) | 수신 TCP가 `TcpListener::bind("0.0.0.0:0")` — **IPv4 전용** |
| [local.rs:69-70](../../crates/nbeep-net/src/local.rs) | 주소록이 `SocketAddr::new(o.from.ip(), …)` 를 **insert** — 마지막 관측 IP로 **덮어쓰기** |

즉 v6 링크로컬(`fe80::…%12`)이 마지막으로 기록되는 순간부터 `connect`가 **아무도 듣지 않는 주소**를
향한다. 초반 2회가 성공한 이유는 기동 직후 HELLO가 v4로 먼저 도착하기 때문이고, 이후 v6 광고가
꾸준히 들어오면서 실패가 **고착**된다(회복 안 됨).

**소켓 수준 확증** — 사용자가 실행 중이던 시나리오 A 2프로세스를 조회해 코드 추정이 아님을 확인:

| 프로세스 | TCP 수신 | UDP 발견 |
|---|---|---|
| 21128 (`--window --live`) | `0.0.0.0:29000` — **v4만** | `0.0.0.0:47100` + **`:::47100`** |
| 19884 (`--chat-live TestDev`) | `0.0.0.0:29003` — **v4만** | `0.0.0.0:47100` + **`:::47100`** |

20초 관찰 동안 두 프로세스 사이 **ESTABLISHED 0건**(양쪽 Listen 유지).
단 시나리오 A는 사람이 목록을 클릭해야 연결이 시작되므로 이것만으로 실패 단정은 못 한다 —
**클릭했는데 대화창이 안 열렸다면 그게 이 결함**이다.

**★ 판단 — 설계 문서는 이 계층을 이미 경고했지만, 경고와 다른 이유로 터졌다.**
[06 §3-4](../06-network-stack.md)는 *"IPv6 링크로컬은 스코프 ID가 주소의 일부다. 이걸 빠뜨리면 연결이 안 된다"*
라고 적었다. 그런데 실제 원인은 스코프 ID가 아니라 **주소 계열 비대칭**(발견은 듀얼스택, 전송은 v4 전용)이었다.
경고가 있던 자리에서 **다른 이유로** 같은 증상이 났다는 점이 교훈이다 — 계층별로 "어느 주소 계열을 쓰는가"를
**한 곳에서 결정**하지 않으면 발견과 전송이 조용히 갈라진다.

**수정 방향 3안** → **M1-4b**로 등록. 권장은 ⓒ.

| 안 | 내용 | 평가 |
|---|---|---|
| ⓐ | 수신을 듀얼스택으로(`[::]` + `IPV6_V6ONLY=false`) | **R-7 대상** — 이 옵션 기본값이 OS마다 다르다. 4타깃 검증표 동반 필요 |
| ⓑ | 주소록에서 v6 제외 | 가장 작지만 **FR-D-7**(링크로컬 직결 발견)과 충돌 — v6만 있는 환경을 버린다 |
| ⓒ | **주소를 후보 목록으로 보관해 순차 시도**(v4 우선·성공 경로 승격) | [06 §4](../06-network-stack.md) 폴백 사다리 취지에 부합. **권장** |

회귀 테스트 조건: **주소록에 v6가 섞여 있어도 연결이 성립하는가.**

### 2. Windows 실물 네트워크 — 종단 첫 성공 (R-7 부분 해소)

문서 [26](../26-run-and-manual-test.md)의 실측은 맥·Docker 기준이라 **Windows 칸이 비어 있었다.** 이번에 채웠다.

| 검증 | 결과 |
|---|---|
| 소켓 기동(`--discover-probe`) | ✅ 바인딩·멀티캐스트 조인 정상(오류 0) |
| 상호 발견(프로브 2개) | ✅ `Hello`·`Announce`·`Goodbye` 전부 관측 · v4(`192.168.72.1`) + v6 링크로컬 |
| GUI 발견 광고(`--window --live`) | ✅ `나-4c13c4c8` 로 광고 · 12초에 v4 30건 + v6 14건 |
| **종단**(헤드리스 2노드) | ✅ **발견 → TCP → Noise → 암호화 메시지 → 에코 왕복** |

**광고 주기 실측** — v6 14건/12초 ≈ **860ms**, v4는 정확히 그 2배(멀티캐스트+브로드캐스트 둘 다 수신).
GUI `--live` 경로는 `announce_ms=800`. 즉 **노드당 초당 약 3.75패킷**이 나가고, 그중 브로드캐스트분은
**참여하지 않는 호스트의 네트워크 스택까지 깨운다**. S1·S3가 사다리가 아니라 **항상 병렬 발송**인 구조라
E-8(100대)에서 다시 볼 값 — 타이밍은 [26 §8](../26-run-and-manual-test.md)대로 D-8b 전 잠정치다.

> `--live-echo`가 GUI를 상대로는 아무것도 출력하지 않는데, 이는 결함이 아니라 **GUI가 사람 입력을
> 기다리는 쪽이라 자동 응답하지 않기 때문**이다(프로브로 GUI가 정상 광고 중임을 별도 확인).

### 3. Windows MotW 미적용 — 실측 근거 (M4-3 잔여)

새로 생긴 `--quarantine-demo`로 4단계 게이트를 돌렸다. **게이트 자체는 정상 동작**한다.

```
① 판정: risk=Data (확장자=Data · 매직=Data/unknown) 불일치 경고=false
② 격리 저장: …\c723f2f4b0b32996.beepq (211B)      ← 콘텐츠 주소 파일명·.beepq 보존
③ 상태: Inspected(Unavailable) (마찰 상승=true)     ← 스캐너 미배선 → 안전하게 저하
④ 실체화: …\sample.txt · 표식=Ok(Unsupported)      ← ⚠️ 표식 미적용
```

③은 정상이다 — [state.rs:44](../../crates/nbeep-safe/src/state.rs)가 *"검사 못 했으면 `Unavailable`,
`Failed` 상태를 만들지 않는다"* 로 **실패 대신 마찰 상승**을 택한 설계이고 그대로 동작했다.

④는 실제로 미적용이다. 실체화 파일을 직접 열어 **`Zone.Identifier` ADS가 없음**을 확인했다
(스트림 `:$DATA` 37B 하나뿐). 원인은 [quarantine.rs](../../crates/nbeep-plat/src/quarantine.rs)가
macOS `com.apple.quarantine`만 구현하고 그 외는 `#[cfg(not(target_os = "macos"))]`로
`Unsupported`를 반환하기 때문 — 주석 6행에 *"Windows(MotW)·`IAttachmentExecute`는 실기 검증과 함께 별도"*
로 **의도된 보류**라 명기돼 있으므로 사고가 아니다.

다만 **영향은 남는다** — DR-13이 *"복원 후에도 MotW/quarantine 유지"* 를 요구하고
[18 §2](../18-build-and-test.md)가 이를 안전 회귀 항목으로 올려두었는데, **현재 그 속성은 macOS에서만
성립한다.** DR-3(4타깃 기능 차등 없음) 기준으로 v1 전에 메워야 할 칸이고, Windows PC가 합류한
지금은 "실기 필요"가 아니라 "지금 가능"이다.

### 4. 예산 실측 추이 (Windows · 전부 같은 PC·같은 창 크기 800×600·배율 1.0)

세션 동안 커밋이 올라올 때마다 유휴 메모리를 측정했다. **폰트 mmap 전후가 갈림길이다.**

| 시점 | 유휴 RSS | Private | 비고 |
|---|---|---|---|
| SP-1 빈 창 | 16.4 MB | 4.2 MB | 기준선 |
| 피어 목록 위젯 | 28.5 MB | 17.1 MB | 폰트 `fs::read` 힙 로드 |
| +IME 활성화 | **30.7 MB** | 17.4 MB | 🔴 **NFR-B-1(30MB) 초과** |
| **폰트 mmap 후** | **16.2 MB** | **4.3 MB** | ✅ **−14.6MB** — 게이트의 54% |
| 최신(`19af9f2`) | 16.3 MB | 4.2 MB | 컨트롤 8종·무해화 추가 후에도 유지 |

**두 가지가 확인됐다.**

① **[19차 예고한 Windows 재실측 완료](2026-08-08.md)** — mmap 효과가 맥(−51MB)뿐 아니라
Windows에서도 결정적이다(−14.6MB). Private 감소분 13.0MB가 맑은 고딕 `malgun.ttf` 12.84MB와
거의 정확히 일치해 **원인·효과가 수치로 닫혔다.**

② ★ **압박은 기능이 아니라 폰트 하나였다** — mmap 이후 Private 4.2MB는 **SP-1 빈 창과 같다.**
그 사이 피어 목록·대화 화면·컨트롤 8종·`Identity`(snow 링크)·무해화가 전부 들어왔는데
**자체 점유 메모리는 사실상 늘지 않았다.** 예산 여유는 생각보다 크다.

③ **IME/TSF는 줄일 수 없는 고정 비용** — `MSCTF.dll`(1.36MB) + `textinputframework.dll`(1.28MB) =
**2.64MB**가 `set_ime_allowed` 시점에 매핑된다. OS 공유 DLL이라 최적화 대상이 아니고,
FR-U-7(IME)이 P0인 이상 **한글 입력의 고정 비용**으로 받아들여야 한다.
⇒ NFR-B-1을 RSS로 재는 한 **우리가 통제할 수 없는 증가**가 계속 섞인다. Private/Commit 기준 병기를
검토할 값어치가 있다(현재 Private 4.2MB = 예산의 14%).

**릴리스 크기 추이**: 0.30 → 0.44 → 0.57 → 0.75 → 0.91 → **1.05MB**(게이트 10MB의 10.5%).
⚠️ 이 PC(rustc 1.97.1)는 기록된 값보다 **일관되게 약 0.10MB 작게** 나온다(4회 연속 동일 방향).
게이트 판정에는 무영향이나, 크기 비교 시 **툴체인 차이를 감안**해야 한다.

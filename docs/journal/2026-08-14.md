## 최근 이미지 목록 증발 — 영속 구멍 2개 (main · 실기)

**실기** — 이미지 3개 등록 → 재시작 → 최근 목록 전부 증발. 구멍이 **두 겹**이었다:

1. **저장 안 됨**: 피커 경로가 위젯 변경 보고를 `let _ = pv.take_changes()`로
   버리고 경로만 수동 저장 — `profile.image_recent`가 저장 자체가 안 됐다 →

   버림도 제거(변경을 안 만드는 자리에서 남의 변경을 삼킬 위험).
2. **로드 안 됨**: `SettingsState::set_by_name`은 "아는 키만" — `profile.image_recent`가
   HIDDEN_KEYS에 없어 **부팅 로드에서 미지 키로 무시**(저장을 고쳐도 재시작이면
   증발). ★ **`ui.win_x/y/w/h`(창 위치 기억)도 같은 구멍** — 함께 HIDDEN_KEYS 등록.

**교훈** — "화면 밖 영속 키"는 저장(known_pairs = 전체)과 로드(set_by_name = 아는
키만)의 **대칭이 깨져 있다**. 새 숨은 키는 HIDDEN_KEYS 등록이 저장의 절반이다.

## 툴바 기본 32px + 48px 옵션 추가 (main · 사용자 요청)

**왜 지금인가** — 08-14에 툴바 오른쪽 프로필 버튼이 **내 아바타**를 아이콘으로 쓰게
되면서(`refresh_toolbar_avatar`), 그 자리가 **12간지 그림이 가장 작게 축소되는 지점**이
됐다. 24px에서는 160px 자산이 1/6로 줄어 형태가 뭉개진다. 08-09에 32→24로 내렸던
결정을 **아이콘이 글리프에서 그림으로 바뀐 사정**으로 되돌린다.

**고친 곳 — 기본값이 두 군데였다**

| 파일 | 변경 |
| --- | --- |
| `nbeep-ctl/controls/toolbar.rs` | `DEFAULT_ICON` 24 → **32** |
| `nbeep-ui/settings.rs` | `RADIO_DEFAULTS`의 `ui.toolbar_size` `"24"` → `"32"` · 옵션에 `"48"` 삽입 |
| `nbeep-core/i18n.rs` | `Msg::Tb48` = `48×48` 신설(4개 언어 공통 표기) |

★ **한 곳만 고치면 화면과 실제가 갈린다** — 컨트롤의 `DEFAULT_ICON`은 "설정을 아직
안 읽었을 때"의 크기이고, `RADIO_DEFAULTS`는 "설정 화면이 어느 항목을 선택 상태로
그릴지"다. 둘이 어긋나면 화면은 24를 가리키는데 툴바는 32로 서는 상태가 된다.

**결과 치수**(논리 px · 호스트가 DPI 배율을 곱한다)

| 아이콘 | 툴바 높이 = icon+16 | 슬롯 폭 = icon+8 |
| --- | --- | --- |
| 16 / 24 | 32 / 40 | 24 / 32 |
| **32(새 기본)** | **48** | **40** |
| **48(신규)** | **64** | **56** |
| 64 | 80 | 72 |

**⚠️ 기존 사용자는 24가 유지된다** — 설정 영속(ADR-0011)이 저장된 값을 그대로 읽는다.
새 기본은 `settings.cfg`에 이 키가 없는 **신규 프로필에만** 적용된다(의도 — 저장된
사용자 선택을 업그레이드가 덮지 않는다는 기존 계약).

**검증** — 워크스페이스 **564 green** · clippy 0 · 3인스턴스 재기동(main 47200 · A 29701 ·
B 29702 · 셋 다 exe mtime 동일 확인). 옛 값을 말하던 주석 4곳도 정정.

**부수 함정(기록)** — 앞선 `sed` 실행의 `cd`가 셸에 남아 상대 경로 빌드·복사가 하위

## 프로필 Choose… 묵은 포커스 — Enter 이중 처리 · 포커스 링 잔존 (main)

**실기 보고(사용자 · 2건이 한 원인)** — ① Display name에서 Enter를 치면 **위의
Choose… 버튼이 눌린다**(피커 재오픈) ② 텍스트박스로 포커스를 옮겨도 Choose…의
**포커스 링이 남는다**. 사용자 자가 진단 그대로: *"Choose 누른 뒤 편집해도
Choose가 포커스를 가진 게 문제"* — 정확했다.

**원인** — `ProfileWidget`은 이벤트를 모든 자식에게 **브로드캐스트**하는데,
`MouseDown` 배타 포커스 갱신이 **텍스트박스 3개만** 대상이었다. Button·Switch는
클릭 시 스스로 포커스를 갖고(`base.focused = true`), **포커스 상태에서
Enter/Space = 클릭/토글**로 처리한다. 그래서 Choose…를 한 번 누르면 그 뒤
텍스트박스를 클릭해도 버튼 포커스가 해제되지 않아 — 같은 Enter가 텍스트박스
확정(정상)과 **버튼 클릭(이중)** 양쪽에서 처리됐다. 참고: 갤러리는 처음부터
**전 컨트롤 배타 포커스**였다 — 프로필만 배선이 부분 복사된 "두 번째 구현" 계열.

**Q(사용자): 텍스트박스가 Enter를 직접 안 잡는 건가?** — 잡는다(`committed` →
`take_committed` 확정 보고). 문제는 전파가 아니라 **브로드캐스트 + 묵은 포커스**로
같은 이벤트가 형제에게도 배달된 것.

**처방** — `MouseDown` 배타 포커스 갱신에 **Choose… 버튼 + 공개 토글 3종 포함**
(클릭된 컨트롤만 포커스 보유). Switch도 같은 구멍이었다(토글 클릭 → 필드 Enter =
재토글 가능성).

**검증** — 회귀 테스트: Choose… 클릭(피커 요청 소비) → 이름 필드 클릭 → **버튼
포커스 해제 단언** → Enter → **피커 재요청 없음 + `profile.display_name` 확정
보고** 단언. 워크스페이스 green.

**교훈** — 브로드캐스트 전달 구조에서는 **포커스 단일성(배타)**이 이중 처리를
막는 유일한 문이다. 컨테이너마다 손으로 배선하는 한 같은 구멍이 반복된다 —

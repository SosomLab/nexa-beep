## M3-21 구현 — 프로필 변경 전파(push 깔때기 + image_keep 경량 유형 + 카드 pull) (main)

**사용자 확정(구현 지시)** — ① 전파 유형 다양화하되 **정보량이 작으니 되도록
묶어 한 번에** ② 추가뿐 아니라 **제거(숨김)도 전파** ③ 카드 열 때 **능동 pull**.
push 대상 질문(같은 망만? 수동 등록도?)에는 **연결된 세션 전부(수동 등록 포함)**
로 답함 — 세션이 성립한 상대는 이미 프리페치로 내 프로필을 받아간 상대라 push는
"준 정보의 최신화"일 뿐이고, 경로로 가르면 옛/새 정보가 경로별로 갈라진다.
훗날 경로별 차등이 필요하면 응답 구성 게이트(push·pull 공용 지점)에서 푼다.

**구현**:

- **와이어**: `ProfileMsg::Info`에 `image_keep`(flags **bit5** · 값 필드 없음) —
  "공유 사진은 그대로, 네 캐시 유지". 같은 flags 바이트라 **레이아웃 불변**
  (구버전 오프셋 안전 · 바이트 수 동일 단언 테스트). 구버전 수신은 비트를 몰라
  철회로 읽는다(다음 Full/성립 프리페치에서 회복 — 전방 관용의 대가로 명문화).
- **유형 2종**(`ProfileScope`): `Full`(Info+사진 청크 — 성립 프리페치·Request
  응답·사진 영향 키) / `Info`(Info 한 프레임 — 텍스트·토글·아바타 키·보더 ·
  공유 사진 있으면 image_keep 마커 · **바이트를 읽지 않고 metadata로만 존재 판정**).
- **push 깔때기**: `apply_settings` 키별 arm이 아니라 **match 뒤 단일 지점**에서
  `profile_push_scope(key)` 판정 → `push_profile(scope)` = 연결된 전 세션에 재송신.
  기존 avatar arm의 재전송은 깔때기로 이관(이중 발송 제거). **끄는 변경도 같은
  응답에 "필드 부재"로 실려 상대 캐시가 지워진다**(철회 대칭 — 별도 철회 메시지
  없음). ★ 회귀 테스트 = **응답 구성이 읽는 키 전수가 깔때기에 있는지**(빠진 키 =
  전파 안 되는 키였던 구멍의 재발 방지) + 무관 키(ui.*) 미전파.
- **수신**: `image_keep`이면 `.img` 삭제 금지 + 이전 사진 경로·아바타 승계.
  청크 동반 응답은 언제나 `image_keep=false`(실물이 왔다).
- **pull**: `open_peer_info` = 세션 살아 있으면 `Request` 1회(캐시 먼저 표시) →
  응답·늦은 아바타 디코드 도착 시 `refresh_peer_info_card`(열려 있는 카드만
  내용 재조립 — `build_peer_info` 추출로 열기·갱신 공용).

## 목록 스크롤 튐 해소 — 갱신 시 스크롤 3택 + 갱신 주기 설정 (main)

**실기 보고(사용자 · 스크린샷 3장)** — 행 선택 → 아래로 스크롤 → **~1초 뒤
선택 행이 맨 위로 오도록 목록이 저절로 끌려온다**. 진단 그대로 "목록 갱신
이벤트와 엮여 위치가 이동"이었다.

**원인 2겹**:

1. `PeerListWidget::set_rows`(내용 교체)가 `clamp_scroll()`을 불렀는데, 이 함수에
   **캐럿 따라가기**(캐럿이 안 보이면 스크롤을 캐럿으로)가 들어 있었다 — 탐색용
   규칙이 갱신 경로에 얹혀, 갱신마다 뷰포트가 캐럿 행으로 스냅.
2. 발견 비컨(800ms)마다 `poll_discovery`가 즉시 `refresh_rows` — 갱신 자체가
   과했다(스냅이 "1초쯤 뒤" 보이던 이유).

**처방(사용자 확정 — 3택 옵션 + 주기, "목록 보기" 설정 그룹)**:

- `clamp_top`(범위만 보정)과 `clamp_scroll`(+캐럿 따라가기) **분리** — 따라가기는
  사용자 탐색(캐럿 이동·타입어헤드)에서만.
- **`RefreshScroll` 3택**(`ui.list_refresh_scroll`): **현재 위치 유지(기본)** /
  선택 행을 맨 위에 / 맨 위로 이동. `set_rows`·`set_groups`가 이 정책을 따른다.
- **캐럿 상대 앵커** — 갱신·재정렬로 인덱스가 밀려도 캐럿은 인덱스가 아니라
  **상대(PeerId)** 를 따라간다(`re_anchor` — 선택 유지가 PeerId 키인 것과 같은 결).
- **갱신 주기 `ui.list_refresh_ms`(기본 1500ms)** — 발견발 재조립을 dirty 플래그로
  묶어 주기 도래 시 한 번에. 다른 경로(메시지·프로필·연결)는 여전히 즉시이며,
  어떤 경로든 재조립하면 기준 시각이 갱신된다(중복 재조립 자연 억제).
- 설정은 **Appearance ▸ 목록 보기** sub 그룹으로 두 항목을 묶었다(사용자 요청) ·
  hot-swap(즉시 적용) · 4언어.

### 먼저 확인한 것 — "아이콘 자리"가 생각보다 작다

## 프로필 Choose… 묵은 포커스 — Enter 이중 처리 · 포커스 링 잔존 (main)

**실기 보고(사용자 · 2건이 한 원인)** — ① Display name에서 Enter를 치면 **위의
Choose… 버튼이 눌린다**(피커 재오픈) ② 텍스트박스로 포커스를 옮겨도 Choose…의
**포커스 링이 남는다**. 사용자 자가 진단 그대로: *"Choose 누른 뒤 편집해도
Choose가 포커스를 가진 게 문제"* — 정확했다.

**원인** — `ProfileWidget`은 이벤트를 모든 자식에게 **브로드캐스트**하는데,
`MouseDown` 배타 포커스 갱신이 **텍스트박스 3개만** 대상이었다. Button·Switch는
클릭 시 스스로 포커스를 갖고(`base.focused = true`), **포커스 상태에서
Enter/Space = 클릭/토글**로 처리한다. 그래서 Choose…를 한 번 누르면 그 뒤
텍스트박스를 클릭해도 버튼 포커스가 해제되지 않아 — 같은 Enter가 텍스트박스
확정(정상)과 **버튼 클릭(이중)** 양쪽에서 처리됐다. 참고: 갤러리는 처음부터
**전 컨트롤 배타 포커스**였다 — 프로필만 배선이 부분 복사된 "두 번째 구현" 계열.

**Q(사용자): 텍스트박스가 Enter를 직접 안 잡는 건가?** — 잡는다(`committed` →
`take_committed` 확정 보고). 문제는 전파가 아니라 **브로드캐스트 + 묵은 포커스**로
같은 이벤트가 형제에게도 배달된 것.

**처방** — `MouseDown` 배타 포커스 갱신에 **Choose… 버튼 + 공개 토글 3종 포함**
(클릭된 컨트롤만 포커스 보유). Switch도 같은 구멍이었다(토글 클릭 → 필드 Enter =
재토글 가능성).

**검증** — 회귀 테스트: Choose… 클릭(피커 요청 소비) → 이름 필드 클릭 → **버튼
포커스 해제 단언** → Enter → **피커 재요청 없음 + `profile.display_name` 확정
보고** 단언. 워크스페이스 green.

**교훈** — 브로드캐스트 전달 구조에서는 **포커스 단일성(배타)**이 이중 처리를

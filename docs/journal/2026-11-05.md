## 3차 — RL-7 2단 기록 세그먼트 증분 append(코드 1건 · 기록 = 협업 세션)

> 원천 = 커밋 `f11561d` 본문. 1단(`2b64f67` 11-04 · 디바운스)이 쓰기 **횟수**를 20 → 2로 줄였지만 매 쓰기가 여전히 스레드 전량 재봉인·전량 쓰기였다(세션 O(n²) · `HISTORY_MAX` 2000줄 안). ADR-0005 §4가 처음부터 정한 "세그먼트 = 헤더 + 개별 봉인 조각" 구조로 간다.

### 실측 — 증분 append(협업 세션 · Win Debug · 헤드리스 2신원 rl-x → rl-y)

조건 = X가 Y에게 `send` 20줄을 **500ms 간격**(디바운스 quiet 300ms보다 길어 쓰기마다 따로 flush) + 이어서 `send_n=20`(한 틱 연타 20줄). 판정 = 양쪽 stderr의 `store/detail history_write` 줄 전수.

| 측정 | X(보낸 쪽) | Y(받은 쪽) |
| --- | --- | --- |
| `history_write` 횟수 | 22 | 22 |
| `mode=fresh` | **1**(첫 쓰기 187B = 안내 줄 포함) | **1**(첫 쓰기 187B) |
| `mode=append` | **21** | **21** |
| `mode=noop` | 0 | 0 |
| 줄당 `new_bytes`(500ms 간격 20회) | **78~79B**(한 줄 분량) | **81~82B** |
| 연타 20줄(`send_n`) | append 1회 1,331B(디바운스가 묶음) | append 1회 1,391B |
| 최종 `frames` | 22(압축 임계 32 미도달) | 22 |
| 쓴 평문 합계 — 증분 | **3,089B** | **3,209B** |
| 쓴 평문 합계 — 전량 재작성이었다면(Σ`plain_bytes`) | 23,462B | 24,212B |
| 비율 | **13.2%**(−86.8%) | **13.3%** |

- **ack로 인한 fresh = 0회** — 커밋 본문은 "ack·수신확인 → fresh"를 예상했으나, 보관 열(`history_kept` → `encode_kept`)에 Delivered 상태가 들어가지 않아 ack가 접두를 바꾸지 않는다. 20줄 전부 append로 끝났다(앱 dump의 X 스레드에 보낸 줄 40줄 정상).
- **커밋 본문 예상 정정**(개발 세션 확인 11-05) — `f11561d` 본문의 "ack → fresh"는 틀린 예상이었다. 보관 코덱이 Delivered 상태를 싣지 않으므로 ack가 접두를 바꾸지 않는 것이 정상이다. fresh가 나는 경우 = 첫 쓰기 · v1 이관 · 보관 열 안의 이미 쓴 줄이 바뀐 경우 · 2000줄 밀림 · 32프레임 압축(수신확인이 여기에 드는지는 실측 안 함).

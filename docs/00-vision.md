# 00 · 비전 — 왜 만드나

> **이 문서의 역할**: 이 프로젝트가 **왜 존재하는지**, 무엇으로 이겼다고 말할 수 있는지를 고정한다.
> 근거는 [03 경쟁 조사](03-competitive-landscape.md)(실측), 결정은 [10](10-decision-record.md), 요구사항 전개는 [05](05-requirements.md).
> **작성 2026-08-08.**

---

## 1. 문제 — 옆자리에 파일 하나 보내는 일이 아직도 어렵다

같은 사무실, 같은 네트워크, 3미터 거리. 그런데 파일 하나를 보내려면 대개 이런 선택지밖에 없다.

| 선택지 | 실제로 걸리는 것 |
|---|---|
| 클라우드 협업툴(Slack·잔디·카카오워크·네이버웍스…) | **계정·조직 가입·인터넷 연결**이 전제. 사내 자료가 **외부 서버를 왕복**한다. 폐쇄망에서는 아예 불가 |
| 서버형 사내 메신저(Output·Bopup·BigAnt·그룹웨어) | **서버 구축 · 계정 발급 · 운영 인력**이 전제. "지금 당장 두 사람이 대화"에는 쓸 수 없다 |
| 이메일·USB | 느리고, 흔적이 남고, USB는 보안 정책상 금지된 곳이 많다 |
| 기존 LAN 메신저 | 이 자리를 채우려던 제품들이 **20년째 정체**되어 있다([§2](#2-그-자리를-채우던-것들이-멈춰-있다)) |

**정작 필요한 건 하나다** — *"띄우면 서로 보이고, 바로 주고받는다."*
이건 기술적으로 어려운 요구가 아닌데, **그렇게 동작하는 현대적인 제품이 없다.**

## 2. 그 자리를 채우던 것들이 멈춰 있다

[03 경쟁 조사](03-competitive-landscape.md)에서 **37종**을 전수 조사한 결과 —

- **국내에는 제로 컨피그 P2P LAN 메신저가 사실상 없다.** 국산 제품군은 전부 서버형 그룹웨어 메신저로 수렴했고, 그 빈자리를 **일본산 IP Messenger**가 20년 넘게 대신하고 있다. 국내 사용기의 호평 사유는 **대용량 파일·폴더 전송 속도**, 불만은 **구식 UI · 모바일 없음 · Windows 중심**이었다.
- **현대적 크로스플랫폼은 둘뿐이고, 둘 다 런타임에 얹혀 있다.** Squiggle(.NET 9 + Avalonia)과 LocalSend(Flutter + Rust). Qt(BeeBEEP·LAN Messenger)·JVM(KouChat)도 마찬가지. **런타임 없는 네이티브 단일 바이너리는 아무도 하고 있지 않다.**
- **오픈소스 진영의 다수가 정지 상태다.** LAN Messenger는 플랫폼별 버전조차 어긋나 있고(Win 1.2.39 / mac·Linux 1.2.37), KouChat은 2016년, BeeBEEP은 2023년 1월이 마지막이다.
- **상용 LAN 메신저 다수가 아직도 "WinPopup 대체품"을 마케팅 문구로 쓴다** — Windows Messenger service가 사라진 지 20년인데도. **이 수요는 20년째 제대로 채워지지 않았다.**

## 3. 우리가 만드는 것

> **Nexa Beep** — 실행하는 순간 같은 네트워크의 사람들이 목록에 뜨고, 바로 대화하고 파일을 주고받는,
> **런타임 없는 단일 바이너리** 메신저. Windows·macOS·Linux에서 **같은 화면**으로.

### 세 개의 기둥

| # | 기둥 | 뜻 | 이걸 깨는 기능은 채택하지 않는다 |
|---|---|---|---|
| **1** | **실행 = 참여** | 서버 주소·계정·상대 등록이 **전부 없다**. 첫 실행부터 대화까지 설정 화면이 0개 | 계정 생성, 서버 주소 입력 요구, 사전 등록 |
| **2** | **가볍다** | 런타임 의존 없는 네이티브. 최소 크기·최소 메모리·**장기 상주 누수 0** | 무거운 프레임워크·과잉 의존성 |
| **3** | **안전하다** | 종단 암호화 + **받은 파일은 승인 전까지 실행될 수 없다** | 평문 전송, 자동 실행·자동 열기 |

세 기둥은 서로 긴장 관계다. 그 긴장을 어떻게 풀었는지가 이 프로젝트의 실체다([§6](#6-정직하게-어려운-것)).

### 관통 원리 — "봉투만 본다"

세 기둥을 실제로 지탱하는 것은 **계층마다 반복되는 규칙 하나**다.

> **어떤 계층도 자기 일에 필요한 만큼만 보고, 내용은 보지 않는다.**
> 릴레이는 목적지만, 발견 패킷은 존재만, 격리물은 메타만, 저장 세그먼트는 헤더만, 계측은 횟수만, 로그는 상태만.

계층별 봉투/내용 대조표는 [10 §0](10-decision-record.md). **새 기능을 설계할 때 첫 질문은 "이 계층의 봉투는 무엇인가"** 다.

### 노드 모델 — PC 1대 = 노드 1개

"사용자"라는 개념을 도입하지 않는다. **기기가 곧 참여 단위**다(DR-18). 계정·디렉터리·기기 연결이 전부 사라지므로 "실행 = 참여"가 성립하고, 같은 사람의 노트북과 데스크톱은 **목록에 둘로 뜨는 것이 정상**이다. 대가는 [§6 V-7](#6-정직하게-어려운-것).

| **S-4** | 4타깃(Win x64/ARM64·macOS·Linux) 산출물이 **예산 게이트를 전부 통과** | CI 게이트 |

## 6. 정직하게 어려운 것

비전 문서에 리스크를 적는 이유는, 나중에 이 항목들이 **"예상 못 한 문제"로 둔갑하는 것을 막기 위해서**다.

| # | 긴장 | 우리 답 |
|---|---|---|
| **V-1** | **제로 컨피그 ↔ 암호화** — 사전 등록이 없으면 신뢰 앵커가 없고, 신뢰 앵커가 없으면 최초 접촉 MITM을 원천 차단할 수 없다 | TOFU 기본 + 지문 확인 선택. **정체성을 깨는 보안은 제품을 없애는 보안**이라 공유 비밀을 기본값으로 삼지 않는다 → ADR-0002 |
| **V-2** | **자동 발견 ↔ 실제 사내망** — 클라이언트 격리·VLAN이 멀티캐스트를 조용히 버린다 | 6단계 폴백 사다리 + **실측 후 설계**([06](06-network-stack.md)) |
| **V-3** | **자체 렌더링 ↔ 개발 비용** — 4타깃 UI를 직접 그리는 건 비싸다 | **정정(08-08 · [12](12-asset-reuse.md))**: `ctl` 14종은 HWND 모델이라 재사용 불가. `nexa-gui` 인프라 1,187 LOC 이식 + 시각 규약 계승으로 **경계 설계만 검증된 상태로 시작**한다 — **위젯 세트는 신규 구현**이므로 완화되나 해소되지 않는다 |
| **V-4** | **자체 렌더링 ↔ 보안** — 이미지 디코더를 직접 다루면 파서 취약점이 곧 RCE | 격리 디코드 + 재인코딩본만 표시([04 §5](04-safe-transfer.md)) |
| **V-5** | **무권한 실행 ↔ 저수준 네트워크** — L2 원시 소켓은 권한·드라이버를 요구해 포터블을 깬다 | 능력 등급 분리 — **T0(무권한)이 완전한 제품**([06 §6](06-network-stack.md)) |
| **V-6** | **누구나 즉시 발신 ↔ 스팸** | 1997년 국산 **소프트메신저**가 바로 이것으로 서비스를 종료했다. 방어를 **1차 범위**에 포함 |
| **V-7** | **노드 = PC ↔ 기기 이전** | 신원·기록이 기기에 묶이므로 **PC를 바꾸면 대화 기록이 따라가지 않는다**. 릴레이가 평문을 못 보니 서버 보관도 불가([17 §8](17-adr-0005-history-at-rest.md)). E2E 백업은 포스트 v1 — **이 한계를 UI에 미리 알린다** |

## 7. 하지 않는 것

범위를 지키는 것이 가벼움을 지키는 유일한 방법이다.

| 안 하는 것 | 이유 |
|---|---|
| 모바일 앱(1차) | 데스크톱 제로 컨피그를 완성하는 것이 먼저 |
| 음성·영상 통화 | 경쟁 7종 중 2종만 보유. 크기·복잡도 대비 효용이 낮다 |
| AD/Entra 연동 · GPO 배포 · 감사 로그 | 서버형 제품의 영역. 우리 정체성과 반대 방향 |
| 문서 CDR(Office/PDF 재구성) · 자체 백신 엔진 | 파서·엔진을 떠안으면 예산이 무너진다. **OS와 설치된 백신에 위임** |
| 클라우드 계정·동기화 | DR-1 위반 |
| GPL 코드 차용 | 라이선스(DR-12) — 참고 가능한 선행 제품은 MIT·Apache-2.0·공개 표준뿐 |

## 8. 누구를 위해

| 대상 | 상황 |
|---|---|
| **폐쇄망·망분리 조직** | 클라우드 협업툴을 못 쓴다. 그런데 서버를 새로 세울 여력도 없다 |
| **소규모 사무실·스튜디오·현장** | 5~30명. 그룹웨어를 도입할 규모가 아니다 |

| **IP Messenger 현역 사용자** | 익숙한 실용성은 유지하되 UI와 플랫폼 제약에서 벗어나고 싶다 |

# 21 · 신원 규격 — `PeerId` · `UserId` 생성과 유일성

> **성격: 규격 집성(spec) + 유일성 분석.** 새 결정을 내리는 문서가 아니라, [08 ADR-0002](08-adr-0002-discovery-transport.md)·[09 ADR-0003](09-adr-0003-transport-abstraction.md)·[20 ADR-0007](20-adr-0007-multi-device-identity.md)·[17 ADR-0005](17-adr-0005-history-at-rest.md)에 흩어져 있는 신원 규칙을 **"어떻게 만들고 · 무엇이 유일성을 보장하고 · 무엇은 보장하지 못하는가"** 관점으로 한 곳에 모은 것이다.
> 결정의 SSOT는 여전히 [10 결정 기록](10-decision-record.md)과 각 ADR이다. **이 문서가 새로 제기하는 것은 [§5 키 파일 복제 문제](#5--미해결--키-파일-복제clone-현재-설계에-답이-없다) 하나이며, 🔴 사용자 확정 대기**로 표시했다.

## 1. 두 식별자의 역할 분담

**하나로 합치면 안 되는 이유는 수명이 다르기 때문이다.** 기기는 교체·재설치되지만 사람은 그대로다.

| | **`PeerId`** | **`UserId`** |
|---|---|---|
| 무엇인가 | **기기(정확히는 신원 키 파일) 1개** | **사람 1명** |
| 값 | **X25519 정적 공개키 32B** | v1: `PeerId`와 같은 값 · v2: **서명 공개키 32B** |
| 누가 만드나 | 그 기기가 **최초 실행 시 스스로** | v2: 사용자가 **다중 기기를 켤 때** 주 기기에서 |
| 무엇이 여기에 붙나 | **연결 · 세션 · 경로 · 링크** | **대화 스레드 · 기록 · 차단 · TOFU/SAS(v2)** |
| 검증 방법 | **`Noise_XX` 핸드셰이크**(개인키 소유 증명) | v2: **`UserId` 키가 서명한 기기 목록** |
| 바뀌는 때 | 재설치 · 신원 초기화 · 기기 교체 | 사실상 바뀌지 않는다(그게 존재 이유) |
| 근거 | DR-8 · DR-18 · [09 §3](09-adr-0003-transport-abstraction.md) | DR-20 · [20](20-adr-0007-multi-device-identity.md) V1-1 |

> **한 줄 요약: 연결은 `PeerId`에, 대화는 `UserId`에 붙인다**([09 규칙 6](09-adr-0003-transport-abstraction.md)).
> v1은 두 값이 같아서 차이가 눈에 보이지 않지만, **타입은 지금부터 다르다** — 코드가 둘을 섞으면 컴파일이 실패한다([`identity.rs` 테스트 `peer_and_user_are_distinct_types`](../crates/nbeep-core/src/identity.rs)).

## 2. 설계 원칙 P-1 ~ P-8

| # | 원칙 | 왜 |
|---|---|---|
| **P-1** | **신원은 자체 생성한 공개키다.** 발급자·등록소·계정이 없다 | DR-1(제로 컨피그). 등록을 요구하는 순간 "실행 = 참여"가 깨진다 |
| **P-2** | **유일성은 조율이 아니라 난수로 얻는다** — 누구에게도 묻지 않고 만들고, 충돌은 확률로 배제한다 | 조율(중앙 발급·중복 검사)은 서버를 요구한다. [§4-1](#4-1-u-1-충돌-유일성--조율-없이-얻는-유일한-방법) |
| **P-3** | **하드웨어 식별자(MAC·시리얼·머신 GUID)를 신원으로 쓰지 않는다** | 비밀이 아니고 · 위조 가능하고 · 바뀌고 · 영구 추적자가 되고 · 권한을 요구한다. [§4-3](#4-3-u-3-왜-하드웨어에서-파생하지-않는가) |
| **P-4** | **이름은 신원이 아니다.** 표시 이름은 서명 대상도 아니고 병합 근거도 아니다 | FR-S-2 · [20 §4](20-adr-0007-multi-device-identity.md). 같은 이름·다른 키 = **다른 사람** |
| **P-5** | **발견은 주장, 세션은 증명.** 발견 패킷의 `PeerId`는 **미검증 힌트**이고, 신원은 핸드셰이크로만 확정된다 | [08 §2](08-adr-0002-discovery-transport.md). 발견 패킷에 서명을 넣어도 사칭을 못 막으므로 아예 인증하지 않고 "미검증"으로 표시한다 |
| **P-6** | **병합의 근거는 언제나 암호학적 증거다** — 같은 키의 여러 경로는 병합(FR-D-6), 다른 키는 별개 | 이름·IP·사용자 주장은 근거가 아니다 |
> ★ **경로가 바뀌어도 신원은 그대로다** — 사무실↔집 이동, 내부↔외부 전환은 **경로 목록이 늘 뿐 노드가 갈리지 않는다**. 신뢰는 **키**에 붙고 위험은 **경로**에 붙는 **두 축**이다 → [19 §5-1](19-adr-0006-manual-endpoint.md).
| **P-7** | **서명 능력 ≠ 복호 능력.** `UserId` 키는 **서명 전용**이며 저장 기록 래핑 키로 쓰지 않는다 | FR-S-36 · [20 §9-1](20-adr-0007-multi-device-identity.md). 나중에 합치는 건 가능하지만 **분리는 불가능**하다 |
| **P-8** | **신뢰는 키에만 쌓이고 절대 상속되지 않는다** — 이름이 같아도, 같은 IP여도 다른 키로 옮겨가지 않는다 | [`trust.rs`](../crates/nbeep-core/src/trust.rs) `trust_never_transfers_across_keys` |

## 3. `PeerId` 생성 — 지금 코드가 실제로 하는 일

### 절차

```
최초 실행
  → OS CSPRNG에서 X25519 정적 키쌍 생성        ← snow 기본 리졸버 = rand_core::OsRng
      (Windows BCryptGenRandom · macOS getentropy · Linux getrandom(2))
  → 공개키 32B가 곧 PeerId                      ← 파생·해시·절단 없음. 공개키 그 자체
  → 개인키는 로컬에만(NFR-S-1) · Debug 출력 마스킹
  → 신원 파일에 저장(§3-3)
```

| 항목 | 값 | 근거 |
|---|---|---|
| 알고리즘 | **X25519**(Curve25519 DH) | [08 §4](08-adr-0002-discovery-transport.md) `Noise_XX_25519_ChaChaPoly_BLAKE2s` |
| 난수원 | **OS CSPRNG** — `snow` 기본 리졸버가 `rand_core::OsRng` 사용 | 자체 난수 생성 금지(NFR-S-3) |
| 값 | 공개키 **32바이트 그대로** | 해시하면 Noise가 다시 원본 공개키를 요구해 **두 표현을 관리**하게 된다 |
| 구현 | [`Identity::generate()`](../crates/nbeep-crypto/src/noise.rs) → [`PeerId::from_bytes`](../crates/nbeep-core/src/identity.rs) | M2-1b |
| 엔트로피 | 실질 **~252비트**(X25519 클램핑) | 충돌 논의는 [§4-1](#4-1-u-1-충돌-유일성--조율-없이-얻는-유일한-방법) |

> ★ **`PeerId`는 지문이 아니라 공개키 그 자체다.** 문서에서 "지문(fingerprint)"이라고 부르는 것은 **같은 값의 다른 이름**이다(해시 한 겹이 없다). 32바이트를 그대로 쓰므로 **지문 충돌 공격이라는 범주가 아예 없다** — 충돌을 만들려면 X25519 공개키 자체를 충돌시켜야 한다.

### 3-1. 표시 — `short()`는 **보안 대조용이 아니다**

[`PeerId::short()`](../crates/nbeep-core/src/identity.rs)는 앞 4바이트를 hex로 찍는다(`deadbeef`). **목록·로그 가독성 전용**이다.

| 용도 | 쓸 수 있나 |
|---|---|
| UI 목록에서 항목 구별 · 로그 상관 | ✅ |
| **사람이 육안으로 상대 신원을 대조** | ❌ **금지** — 32비트는 생일 한계로 **2¹⁶ 시도면 충돌을 만들 수 있다.** 공격자가 앞 4바이트가 같은 키를 골라 만든다 |

**육안 대조는 안전번호(SAS) 하나뿐이다**(FR-S-4 · [`sas.rs`](../crates/nbeep-crypto/src/sas.rs) `safety_number`). 구현은 **양쪽 `PeerId`를 정렬해 BLAKE2s로 해싱**하는 Signal 안전번호 방식이다.

| | `short()` | `safety_number()` |
|---|---|---|
| 재료 | **내 키 앞 4바이트** | **양쪽 키 전체** + 도메인 태그 |
| 성질 | 표시용 라벨 | **두 사람이 같은 키 쌍을 보고 있는지**의 증거 |
| 세션 의존 | — | **없다** — 재접속해도 같은 값(`verify()` 영속과 짝) |
| 육안 대조 | ❌ | ✅ 유일한 수단 |

> ✅ **해소(08-08 M2-2b)** — 아래 분석에 따라 **60자리(5자리 12묶음 · Signal 규격)로 상향**했다. 다이제스트도 앞 8바이트가 아니라 **카운터 도메인 2회 해싱(64B) 전체**를 쓴다. 원 분석(보존):
> ⚠️ ~~자릿수 재검토 필요 — 12자리는 짧다.~~ MITM은 양쪽에 **서로 다른 키**를 보여주므로(`M1`을 Alice에게, `M2`를 Bob에게) *"`safety_number(A,M1)` == `safety_number(M2,B)`"* 가 되는 **쌍 하나만** 찾으면 대조를 통과한다. 두 변수를 모두 고른다는 것은 **생일 공격**이라는 뜻이고, 12자리(≈40비트)에 대한 작업량은 **약 2²⁰(≈100만 회 키 생성) — 노트북으로 수 분**이다. Signal이 60자리를 쓰는 이유가 이것이다.
> ⇒ **자릿수를 늘려야 한다**(다이제스트 앞 8바이트만 접는 현재 구현도 함께 확장). [§10 Q-21-5](#10-열린-질문). 아울러 [`sas.rs`](../crates/nbeep-crypto/src/sas.rs) 모듈 주석의 *"60비트 / 12자리"* 는 상수 주석의 *"12자리 ≈ 40비트"* 와 어긋난다 — **40비트가 맞다**.

### 3-2. 자기 자신 걸러내기

멀티캐스트는 자기 패킷을 되돌려준다. **정적 공개키로 자기 패킷을 걸러낸다**([08 §5](08-adr-0002-discovery-transport.md)) — 즉 자기 `PeerId`는 발견 목록에 절대 들어가지 않는다.

### 3-3. 어디에 저장되는가 — **여기서 "기기"의 정의가 정해진다**

| 배포 채널 | 위치 | 근거 |
|---|---|---|
| 포터블 | **실행 파일 옆 데이터 폴더** | DR-4 · FR-P-3 |
| 쓰기 불가 위치 | 사용자 데이터 폴더로 **폴백** | FR-P-3 |
| 보호 | **파일 + 파일 권한**(OS 자격 증명 저장소 아님) | 포터블(DR-4) · T0 무권한 요구. 강화는 v2 |

> ⚠️ **그래서 유일성의 단위는 하드웨어가 아니라 "신원 키 파일 1개"다.** DR-18의 *"PC 1대 = 노드 1개"* 는 **기본 사용 형태를 서술한 것이지 시스템이 강제하는 불변식이 아니다.** 이 구분이 [§4-2](#4-2-u-2-유일성의-단위는-하드웨어가-아니라-키-파일이다)와 [§5](#5--미해결--키-파일-복제clone-현재-설계에-답이-없다)의 출발점이다.

### 3-4. 재생성(신원 초기화)

사용자가 신원을 초기화하면 새 키쌍이 생기고 **상대에게는 "모르는 새 키"로 보인다**([08 §4](08-adr-0002-discovery-transport.md) 키 관리). v1에서는 이전 신뢰가 **상속되지 않는다**(P-8) — 이 마찰의 해소가 v2 `UserId`의 부수 이득이다([20 §3](20-adr-0007-multi-device-identity.md) ③).

## 4. ★ `PeerId` 장치별 유일성 — 현재 설계가 확보하는 방법

**요구는 "같은 값을 두 기기가 갖지 않는다"이고, 이 설계는 그것을 세 층으로 나눠 처리한다.**

| 층 | 질문 | 현재 답 | 강도 |
|---|---|---|:--:|
| **U-1** | 두 기기가 **우연히** 같은 값을 만드나 | 난수 32B — 확률적으로 배제 | ✅ **사실상 불가능** |
| **U-2** | 두 기기가 **고의로** 같은 값을 쓰나(사칭) | 개인키 없이는 핸드셰이크 실패 | ✅ **암호학적으로 차단** |
| **U-3** | 두 기기가 **키 파일을 복제**해 같은 값을 쓰나 | — | 🔴 **현재 답 없음** → [§5](#5--미해결--키-파일-복제clone-현재-설계에-답이-없다) |

### 4-1. U-1 충돌 유일성 — 조율 없이 얻는 유일한 방법

- 32바이트 무작위 값의 충돌은 **생일 한계상 2¹²⁶ 규모의 기기**가 있어야 유의미해진다. 지구상 기기 수(≈2³³)와 비교 대상이 아니다.
- **중요한 것은 확률 자체가 아니라 "이게 왜 유일한 선택인가"다.** 중앙 발급·중복 검사·DHCP식 임대는 전부 **조율자(서버)** 를 요구하고, 그건 DR-1을 깬다. **묻지 않고 만들고 확률로 배제하는 방식만이 제로 컨피그와 양립한다**(P-2).
- 전제 조건 하나 — **난수원이 진짜여야 한다.** OS CSPRNG를 쓰는 이유가 이것이다. ⚠️ 실무 위험은 **골든 이미지·VM 스냅샷에서 복원된 직후의 엔트로피 상태**인데, 우리는 키를 **최초 실행 시점**에 만들고 그 이후 재사용하므로 *"이미지에 이미 키가 들어 있는"* 경우가 더 현실적인 문제다 → 그것이 [§5](#5--미해결--키-파일-복제clone-현재-설계에-답이-없다).

### 4-2. U-2 유일성의 단위는 **하드웨어가 아니라 키 파일**이다

같은 값을 **주장**하는 것과 **사용**하는 것은 다르다.

| 상황 | 결과 | 판정 |
|---|---|---|
| 공격자가 남의 `PeerId`를 **발견 패킷에 실어 뿌린다** | 목록에 미검증 항목으로 뜰 수는 있으나, 연결하면 **`Noise_XX`에서 개인키를 증명하지 못해 실패**한다 | ✅ 막힌다(P-5) |
| 한 PC에서 **인스턴스 2개**(다른 OS 계정 / 포터블 + 설치본) | 키 파일이 둘이므로 **`PeerId`도 둘** — 네트워크에는 **서로 다른 두 노드**로 보인다 | ⚠️ **DR-18 위반이 아니라 정의상 정상.** 다만 "PC 1대 = 노드 1개"라는 설명과 어긋나므로 UI 문구는 이를 전제하면 안 된다 |
| USB 포터블을 **다른 PC로 옮겨 실행**(원본은 실행 안 함) | 신원이 따라간다 — **의도된 동작**([08 §4](08-adr-0002-discovery-transport.md)) | ✅ 정상 · 매체 분실은 신원 유출 위험으로 이미 명시 |
| 키 파일을 **복사**해 **양쪽에서 동시에 실행** | 같은 `PeerId`를 가진 두 실체가 동시에 산다 | 🔴 [§5](#5--미해결--키-파일-복제clone-현재-설계에-답이-없다) |

> **핵심 인식:** `Noise_XX`가 증명하는 명제는 *"상대가 이 개인키를 갖고 있다"* 이지 *"이 개인키를 가진 기기가 세상에 하나뿐이다"* 가 아니다. **사칭은 막지만 복제는 막지 못한다** — 개인키를 진짜로 갖고 있으니까.

### 4-3. U-3 왜 하드웨어에서 파생하지 않는가

MAC 주소·디스크 시리얼·머신 GUID로 기기 유일성을 잡는 방식은 **다섯 가지 이유로 전부 탈락**한다. (FR-S-2가 *"계정·IP·MAC은 신원이 아니다"* 라고 한 문장의 근거를 여기 펼친다.)

| # | 이유 | 설명 |
|---|---|---|
| **1** | **비밀이 아니다** | `PeerId`는 동시에 **Noise 정적 키**다. 공개 정보에서 파생하면 **개인키가 예측 가능**해져 암호가 통째로 무너진다. 이것 하나로 이미 결론이 난다 |
| **2** | **위조가 자유롭다** | MAC은 소프트웨어로 바꾼다. 위조 가능한 값으로는 사칭을 막을 수 없다 |
| **3** | **변한다** | NIC 교체·도킹·가상 어댑터·무선/유선 전환·MAC 랜덤화(모던 OS 기본값)로 값이 흔들린다. 신원이 흔들리면 대화·기록이 갈라진다 |
| **4** | **영구 추적자가 된다** | 하드웨어 ID는 사용자가 못 바꾼다 = **신원 초기화가 불가능**하다([§3-4](#3-4-재생성신원-초기화)). 무해한 LAN 메신저가 추적 장치가 된다 |
| **5** | **권한을 요구한다** | 일부 머신 ID 조회는 관리자 권한·플랫폼별 API를 요구한다 → **T0(무권한) 완전 동작**(DR-14 · R-6)이 깨진다 |

> ⚠️ 단 **로컬 힌트로 쓰는 것은 별개 문제다.** "이 데이터 폴더를 마지막에 쓴 기기가 지금 기기와 다르다" 같은 **밖으로 나가지 않는 판정**에는 쓸 수 있다 — [§5](#5--미해결--키-파일-복제clone-현재-설계에-답이-없다)의 후보 U-P3이 그 경우다. **신원으로 쓰는 것**과 **로컬 감지에 쓰는 것**을 혼동하지 않는다.

### 4-4. 지금 있는 방어 요약

| 기제 | 무엇을 잡나 | 위치 |
|---|---|---|
| 32B OS 난수 | 우연한 충돌 | [`Identity::generate`](../crates/nbeep-crypto/src/noise.rs) |

## 5. 🔴 미해결 — 키 파일 복제(clone). 현재 설계에 답이 없다

> **이 절만 새로 제기하는 내용이다.** [08 §4](08-adr-0002-discovery-transport.md)는 *"USB로 옮기면 신원도 따라간다"* 는 **이동(move)** 을 다뤘지만, **복사(copy) 후 양쪽 동시 실행**은 어느 문서에도 없다.

### 어떻게 발생하나 — 사고가 아니라 일상 경로다

| # | 경로 | 흔한가 |
|---|---|---|
| C-1 | 포터블 폴더를 **복사**해 두 PC에 배포(백업해 뒀다가 원본도 계속 사용) | ★★★ |
| C-2 | **골든 이미지·디스크 클론**으로 사내 PC 일괄 배포 — 이미지에 이미 신원 파일이 들어 있다 | ★★★ (기업 환경) |
| C-3 | **VM 스냅샷 복원 · 템플릿에서 VM 다중 생성** | ★★ |
| C-4 | 포터블 폴더를 **네트워크 공유·동기화 폴더**에 두고 두 사람이 실행 | ★★ ([17 §6](17-adr-0005-history-at-rest.md)이 이미 동기화 폴더 경고를 요구한다) |

### 무엇이 깨지나

| 계층 | 증상 |
|---|---|
| 발견 | **FR-D-6 다중 경로 병합**이 서로 다른 두 PC를 **한 노드로 병합**한다 — 설계상 "같은 키 = 같은 노드"이므로 규칙대로 동작한 결과다 |
| 세션 | 연결이 **어느 실체에 붙을지 비결정적**. 보낸 메시지가 어디로 갔는지 사용자가 알 수 없다 |
| 신뢰 | 양쪽 다 **진짜 개인키를 갖고 있어 TOFU·SAS를 정상 통과**한다. 검증으로는 절대 구분되지 않는다 |
| 메시지 | `sender_device` + 논리 시퀀스(V1-3)가 **두 실체에서 독립적으로 증가** → 중복 제거가 오작동 |
| 기록 | 저장 마스터 키의 래핑 키가 **기기 키 파생**([17 §3](17-adr-0005-history-at-rest.md)) → **복제본이 원본의 기록을 그대로 연다.** C-4에서는 남의 대화가 열린다 |
| v2 다중 기기 | 기기 목록의 **한 항목이 두 실체**를 가리킨다. 폐기해도 둘 다 죽고, 살려도 둘 다 산다 — 관리 단위가 무너진다 |

> **가장 나쁜 성질: 조용하다.** 어떤 계층도 오류를 내지 않는다. 전부 "설계대로" 동작하면서 결과만 틀린다.

### 후보 대응

| # | 방식 | 잡는 것 | 비용 | 평가 |
|---|---|---|---|---|
| **U-P1** | 발견 패킷에 **`instance` 난수 16B**(프로세스 기동 시 생성) 추가. 같은 `static_pubkey`인데 **`instance`가 다른 두 발신처가 동시에 관측되면 복제 경고** | C-1~C-4를 **같은 LAN에서** 탐지 | 패킷 +16B(현재 헤더 ≈54B + 이름, 상한 512B — **여유 충분**) · 로직 소 | **★ 권고.** 기존 `epoch`(기동 시각)만으로는 부족하다 — 재시작과 구별되지 않고, 클론된 두 VM은 시각까지 같을 수 있다 |
| **U-P2** | 세션 수립 시 **상대 `PeerId`가 내 `PeerId`와 같으면 즉시 종료 + 경고** | "내 신원과 대화하는" 명백한 복제 | **한 줄 비교** | **★ 권고.** 지금도 무조건 넣어야 하는 방어(자기 자신 연결 방지와 동일) |
| **U-P3** | 데이터 폴더에 **마지막 사용 기기의 로컬 지문(해시)** 을 기록 → 다르면 *"이동인가, 복제인가"* 를 사용자에게 질문(이동이면 그대로, 복제면 **새 신원 생성**) | LAN 밖·비동시 실행까지 | 중(플랫폼별 로컬 지문 · UX 1화면) | 선택. ⚠️ **하드웨어 값이 밖으로 나가지 않는다**는 조건 필수([§4-3](#4-3-u-3-왜-하드웨어에서-파생하지-않는가) 단서) |
| U-P4 | 서버 발급·중복 검사 | 전부 | — | ✗ **DR-1 위반.** 검토 대상 아님 |

> ✅ **확정(08-08 사용자 승인 — 추천안 수용)**: **U-P1 + U-P2를 v1에 넣는다.** U-P1은 와이어 포맷에 `instance` 16B로 반영(M1-3 `wire.rs` — 골든 테스트 고정), U-P2는 `NoiseSession` 수립 검사(`SessionError::SelfPeer`)로 구현 — **양쪽 테스트 완료**. 원 권고(보존):
> ~~권고: U-P1 + U-P2를 v1에 넣는다.~~ 둘 다 싸고, 넣지 않으면 **와이어 포맷 확정 이후에 필드를 추가**하게 된다(발견 패킷 포맷은 M0에서 고정 예정 — **지금이 거의 공짜인 마지막 시점**이다). U-P3는 v2로 미룰 수 있다.
> **정직한 한계**: U-P1은 **탐지**이지 **방지**가 아니다. 복제 자체는 파일 복사라서 앱이 막을 수 없고, 막으려 하면(하드웨어 잠금) DR-1·DR-4가 깨진다. **막을 수 없는 것은 알려 준다** — NFR-S-5와 같은 태도다.

## 6. `UserId` — v1 규격 (지금 코드에 있는 것)

| 항목 | 규칙 |
|---|---|
| 값 | **내 `PeerId`와 같은 32바이트**를 `UserId` 타입으로 재해석한다(1:1 · [20 V1-1](20-adr-0007-multi-device-identity.md)) |
| 생성 | **별도 생성 절차가 없다.** v1에는 `UserId` 키쌍이 존재하지 않는다 |
| 상대의 `UserId` | **세션에서 확정한 `PeerId`를 승격**해서 만든다 |
| ⚠️ 금지 | **발견 단계(미검증 힌트)에서 `UserId`를 만들지 않는다** — 대화·기록·차단이 붙는 키를 미검증 값으로 만들면 P-5가 깨진다. 승격 시점은 **핸드셰이크 성립 이후**뿐이다 |
| 무엇이 붙나 | **대화 스레드 · 기록 · 차단 목록** |
| 무엇이 안 붙나 | 연결·링크·경로(그건 `PeerId`) |
| 왜 별도 타입인가 | v1에서 값이 같아도 **컴파일러가 혼용을 차단**한다. [18](18-build-and-test.md)이 *"스레드 키에 `PeerId`를 쓰면 컴파일 실패"* 를 회귀 항목으로 잡고 있다 |

> **v1의 차단은 `PeerId` 단위로 동작한다**([`trust.rs`](../crates/nbeep-core/src/trust.rs) `block`) — 값이 같으므로 결과는 동일하지만, **의미상 차단은 사람(`UserId`) 단위**다(FR-S-38). v2에서 이 구분이 실체가 된다.

## 7. `UserId` — v2 규격 (생성 절차)

### 시드가 먼저다 — 키쌍을 만들고 시드를 뽑는 게 아니다

[20 §9](20-adr-0007-multi-device-identity.md)가 **복구 시드로 다른 기기를 주 기기로 승격**할 수 있다고 확정했으므로, **시드에서 개인키가 결정적으로 재생성되어야 한다.** 무작위 키쌍을 만들고 나서 시드를 붙이는 순서로는 이 요구를 만족할 수 없다.

```
다중 기기 활성화(주 기기에서)
  → OS CSPRNG로 시드 256비트 생성          ← 이 시드가 신원의 뿌리
  → 시드 ──결정적 KDF──► 서명 개인키
  → 서명 공개키 32B = UserId               ← 이 값이 상대가 핀하는 대상(FR-S-30)
  → 시드 1회 표시(오프라인 보관 안내) · 주 기기 안에서는 암호화 저장([17 §4])
  → 기기 목록에 주 기기를 넣고 version=1 서명
```

| 항목 | 규칙 | 상태 |
|---|---|---|
| 존재 시점 | **다중 기기를 켜기 전에는 존재하지 않는다.** 기본 사용자는 평생 만들지 않는다(DR-1) | 확정 |
| 개인키 보관 | **주 기기 1대에만**(FR-S-34) | ✅ 확정 |
| 서명 알고리즘 | Ed25519 추가 vs X25519 재사용(XEdDSA) | 📐 **Q-2 미정**(크기 예산 영향) |
| 시드 표기 | 한국어 단어 나열 · 이모지 · BIP39류 | 📐 **Q-1b 미정** |
| 용도 제한 | **서명 전용**(P-7 · FR-S-36) | ✅ 확정 |
| 유일성 | `PeerId`와 같은 논리 — 256비트 난수, 조율 없음([§4-1](#4-1-u-1-충돌-유일성--조율-없이-얻는-유일한-방법)) | 확정 |
| 복제 위험 | **시드를 가진 사람은 기기를 추가·폐기할 수 있다** → 이것이 R-10의 실체 | 고지 필수(FR-S-35) |

## 8. ★ v1 → v2 승격 시 `UserId` **값이 바뀐다** — V1-1이 실제로 사 준 것

**놓치기 쉬운 지점이라 명시한다.** v1의 `UserId`는 `PeerId` 바이트이고, v2의 `UserId`는 새로 만든 **서명 공개키**다. 값이 다르다.

| 누구의 `UserId`가 바뀌나 | 언제 |
|---|---|
| **내 것** | 내가 다중 기기를 켤 때 |
| **상대 것** | 상대가 다중 기기를 켜고 그 목록을 내게 제시할 때 |

### 그래서 V1-1은 마이그레이션을 **없애는** 게 아니라 **한 등급 낮춘다**

| V1-1이 없었다면 | V1-1이 있으니까 |
|---|---|
| 스레드 키가 `PeerId` → v2에서 **대화 기록이 기기별로 쪼개진 채** 남는다 → **레코드 병합 마이그레이션** | 스레드 키가 `UserId` → **식별자 한 컬럼을 옛값→새값으로 remap**하면 끝(별칭 표 유지) |

- **기록 본문 재암호화는 없다** — 마스터 키가 래핑 구조라 신원 변화와 무관하다([17 §3](17-adr-0005-history-at-rest.md) · V1-4).
- ⚠️ **단, 블라인드 인덱스는 확인이 필요하다** — 인덱스 토큰(HMAC)에 `UserId`가 섞여 있으면 승격 시 **재색인**이 필요해진다([17 §5](17-adr-0005-history-at-rest.md)). ⇒ **규칙 제안: 인덱스 토큰 재료에 `UserId`를 넣지 않는다.** M2-5 구현 시 확정 → [§10 Q-21-2](#10-열린-질문).
- TOFU 핀도 **`PeerId` 핀 → `UserId` 핀**으로 대상이 올라간다(FR-S-30). 이때 *"이미 SAS 대조한 기기"* 의 신뢰를 새 `UserId`로 어떻게 이어 줄지가 남는다 → [§10 Q-21-3](#10-열린-질문).

| I-9 | `short()` 값이 **신원 판정 코드 경로에 등장하지 않는다**(표시 전용) | ☐ M1-5 |

> **요약 세 줄**
> ① `PeerId` = **최초 실행 시 OS 난수로 만든 X25519 공개키 32B 그 자체**. 유일성은 **조율 없이 난수로** 얻고(P-2), 사칭은 **Noise 핸드셰이크의 개인키 소유 증명**이 막는다.
> ② 유일성의 단위는 하드웨어가 아니라 **신원 키 파일**이다. 하드웨어 파생은 [§4-3](#4-3-u-3-왜-하드웨어에서-파생하지-않는가) 다섯 이유로 전부 탈락한다.
> ③ 남은 구멍은 **복제**뿐이고, 현재 설계에 답이 없다 — **탐지(U-P1·U-P2)를 v1에 넣자**는 것이 이 문서의 유일한 제안이다.

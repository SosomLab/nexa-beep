## 2. ① 언어 · 툴체인

### 후보 비교

| 후보 | 런타임 0 | 바닥 크기 | 메모리 안전 | 4타깃 크로스 | 퍼미시브 생태계 | 저수준 소켓 | 판정 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| **Rust** | ○ | ◎ (수백 KB~) | **◎ (컴파일 타임 보장)** | ◎ (`--target` 1급 지원) | ◎ (MIT/Apache-2.0 지배적) | ○ | **✅ 채택** |
| C++ | ○ | ◎ | **✕ (수동)** | △ (툴체인·SDK 구성이 타깃마다 고통) | ○ | ○ | ✗ |
| Zig | ○ | ◎ | △ (안전하지만 보장은 아님) | **◎ (크로스 컴파일 최강)** | ○ | ○ | ✗ (아래 사유) |
| Go | **✕ (GC 런타임 내장)** | ✕ (8~15MB 바닥) | ○ | ◎ | ○ | ○ | ✗ |
| C# / .NET NativeAOT | △ (AOT여도 런타임 잔존) | ✕ (10MB+ 바닥) | ○ | △ | ○ | ○ | ✗ |

### 판정 근거

**Rust를 채택한다.** 네 가지가 결정적이다.

1. **메모리 안전성이 이 제품에서는 보안 요구사항이다.** 우리는 신뢰할 수 없는 **네트워크 패킷·이미지·아카이브**를 직접 파싱한다([05](05-requirements.md) FR-S-11/12, 리스크 **R-5**). C/C++로 이걸 하면 파서 버그 하나가 곧 RCE이고, 그 위험을 상쇄하려면 샌드박싱·퍼징에 별도 예산이 든다. **DR-7(E2E 암호화)을 내세우면서 파서에서 뚫리는 것은 자기모순이다.**
2. **런타임 0 + 작은 바닥 크기.** Go·.NET은 NFR-B-3(≤10MB)·NFR-B-5(런타임 의존 0)에서 즉시 탈락한다. [03 §6-4](03-competitive-landscape.md)에서 확인한 **경쟁 제품 전부가 런타임에 얹혀 있다**는 사실이 우리 차별화 축인데, 같은 선택을 하면 차별점이 사라진다.
3. **4타깃 크로스 컴파일이 실무적으로 검증되어 있다.** Zig의 크로스 컴파일이 더 매끄럽다는 점은 인정하지만, **언어·생태계 안정성**과 **암호화·유니코드·폰트 등 검증된 퍼미시브 라이브러리의 존재**에서 Rust가 앞선다. 우리는 암호를 직접 구현하지 않기로 했다(NFR-S-3).
4. **사내에 실증이 있다.** 형제 프로젝트 `nexa-dir2`가 **Rust + 커스텀 드로잉으로 단일 exe 3.65MB · 유휴 RSS 16.86MB**를 달성했다([03 §6-4](03-competitive-landscape.md)). NFR-B-1/B-3이 달성 가능하다는 **추정이 아닌 증거**이고, [Nexa Controls 14종](10-decision-record.md)이라는 재사용 자산도 Rust로 되어 있다.

> **탈락 사유 메모** — Zig는 "지금이 아니라서" 탈락이다. 언어가 안정되고 암호·텍스트 생태계가 자리 잡으면 재평가 대상이다. C++는 "빠르다"가 아니라 **"안전하지 않다"** 로 탈락했다. 이 제품에서는 그게 성능보다 중요하다.

## 3. ② 렌더링 백엔드 — DR-6의 실체

**"모든 렌더링을 직접 구현"** 을 어떻게 구현하느냐가 이 ADR의 진짜 쟁점이다.

| 안 | 방식 | 픽셀 동일성 | 크기·메모리 | 비용 | 판정 |
|---|---|:--:|:--:|:--:|:--:|
| **A. 플랫폼 네이티브 2D** | Win: GDI/DirectWrite · mac: CoreGraphics/CoreText · Linux: Cairo/X11 | **✕** — 텍스트 렌더·안티에일리어싱이 플랫폼마다 다르다 | ◎ (OS 인박스) | 백엔드 3벌 | ✗ **NFR-C-1 위반** |
| **B. 자체 CPU 래스터라이저 + 자체 텍스트 스택** | 픽셀 버퍼에 직접 그리고, 창에는 **버퍼만 전달**. 폰트 셰이핑·래스터화도 우리 코드 | **◎ — 정의상 동일** | ○ (CPU 렌더·GPU 미사용) | 텍스트 스택이 숙제 | **✅ 채택** |
| C. GPU (wgpu 등) | 그래픽 API 추상화 위에 렌더 | △ (드라이버 편차) | **✕** — 바이너리·상주 메모리 증가, GPU 컨텍스트 상시 보유 | 중간 | ✗ **NFR-B-1/B-3 위반** |

### B안 채택 근거

- **"동일 UI"(S-7 — 스크린샷으로 OS를 구분할 수 없어야 한다)를 만족하는 유일한 안**이다. A안은 겉모습은 맞출 수 있어도 **글자 모양이 갈린다** — 그리고 메신저는 화면의 대부분이 글자다.
- GPU는 상주형 트레이 앱에 과하다. `nexa-dir2`도 **"GPU 스왑체인 상시 보유 금지"** 를 명시했고, 같은 이유가 여기에도 적용된다(NFR-B-1).
- 플랫폼 계층이 **"창 + 픽셀 버퍼 전달 + 입력"** 으로 얇아진다 → 4타깃 이식 비용이 줄고 R-3(자체 렌더링 비용)이 완화된다.

### B안이 떠안는 숙제 (정직하게)

| 숙제 | 내용 | 대응 |
|---|---|---|
| **텍스트 스택** | 폰트 로딩 · 셰이핑(한글 조합·아랍어 등) · 글리프 래스터화 · 서브픽셀/힌팅 | 검증된 퍼미시브 라이브러리 조합. **직접 구현하지 않는다** — 여기는 재발명 금지 구역 |
| **시스템 폰트 접근** | OS마다 폰트 열거·매칭 방식이 다르다 | 플랫폼 계층에 격리. 폰트 **임베드는 크기·라이선스 문제**라 최후 수단 |
| **IME** (FR-U-7) | 한/중/일 조합 입력은 자체 렌더링의 가장 큰 함정 | **P0으로 못 박음.** 플랫폼별 IME 이벤트를 텍스트 편집 모델에 연결 |
| **접근성** (FR-U-8) | 스크린 리더가 우리가 그린 것을 모른다 | v2로 명시(리스크 R-9) |
| **고DPI** (FR-U-6) | 배율·다중 모니터 | 논리 좌표계 + 배율 변경 이벤트 처리 |
| **성능** | CPU 렌더로 60fps(NFR-B-12) | 가시 영역만 그리기 + 무효화 사각형 — `nexa-dir2`가 100k 행에서 검증한 방식 |

## 4. ③ 플랫폼 계층 — 창 · 입력 · IME

B안에서 플랫폼 계층이 할 일은 **창 생성 · 픽셀 버퍼 표시 · 입력/IME 이벤트 · 폰트 열거 · DPI**뿐이다. 이걸 어떻게 얻을지가 남는다.

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **P1. 직접 구현** | Win32(windows-rs) · AppKit(objc2) · X11/Wayland 직접 | 의존성 최소·완전한 제어. `nexa-dir2`의 Win32 코드 계승 가능 | **플랫폼 3벌 × IME·DPI·Wayland/X11 이중화** = 비용이 크다(R-3). Linux만 사실상 2벌 |
| **P2. 얇은 창 라이브러리** | 창·입력·IME만 담당하는 퍼미시브 크레이트 + 픽셀 버퍼 표시 | 4타깃 즉시 확보, IME·DPI·Wayland를 남이 유지보수 | 의존성 트리·크기 증가. 예산 영향 실측 필요 |
| **P3. 혼합** | **Windows는 직접 구현**(nexa-dir2 자산 재사용), mac/Linux는 P2로 시작 후 필요 시 대체 | 자산 재사용 + 초기 속도 | 경로가 둘이라 동작 차이가 생길 수 있다 |

> **결정: P2로 시작하고, 예산 실측 결과에 따라 P1으로 좁혀 간다**(2026-08-08 사용자 확정). 근거 —
> ⓐ 이 계층은 **UI의 겉모습에 영향을 주지 않는다**(픽셀은 우리가 그린다) → 나중에 바꿔도 화면이 바뀌지 않는다.
> ⓑ **IME·Wayland·고DPI**는 직접 구현 시 가장 오래 발목을 잡는 항목이고, R-3/R-9를 키운다.
> ⓒ 크기·메모리 영향이 게이트를 위협하면 그때 P1으로 내려간다 — **되돌릴 수 있는 결정**이다.
> ⓓ 반대로 언어·렌더링 방식은 되돌리기 어렵다. **되돌리기 쉬운 것은 나중에, 어려운 것은 지금** 정한다.

## 5. 결정 (Decision)

| **⑦ 구조** | 플랫폼 의존 코드는 경계 모듈에 격리하고 코어는 플랫폼 중립(NFR-C-3). macOS에서 일상 개발 + 4타깃 CI 검증(C-6) |

## 6. ★ 예산 검증 스파이크 — SP-1 (리스크 R-8)

> **스택은 확정했지만 예산 달성 여부는 아직 미검증이다.** [05](05-requirements.md) NFR-B-1/B-3을 "잠정"으로 표기한 빚을 여기서 갚는다.
> **M0 스캐폴딩(M0-1) 직후 다른 어떤 기능보다 먼저 실행한다** — 추정으로 예산을 확정하지 않는다([15 §2](15-dev-methodology.md)).

> **실측(2026-08-08 · `spike/sp1-budget`, macOS aarch64 · winit 0.30 + softbuffer 0.4)** — 상세 [journal](journal/2026-08-08.md).

| 항목 | 측정 대상 | 통과 기준 | **실측 결과** |
|---|---|---|---|
| **SP-1a** | 빈 창 **바이너리 크기** | 각 **≤ 3MB** | ✅ **0.40MB**(macOS) — 게이트의 13% |
| **SP-1b** | 빈 창 **유휴 RSS** | **≤ 15MB** | ⚠️ **phys_footprint 27MB**(헤드리스·미안정) — **실기 재측정 필요**. 대부분 macOS GUI 프레임워크 공통 비용(P1도 동일) |
| **SP-1c** | 텍스트 스택 증가분 | 위 절반 이내 | ✅ **실측 완료(08-08 · macOS arm64 · 동일 릴리스 프로필)** — 기준 bin 280KB 대비: **ab_glyph +99KB**(외부 4 · 전부 Apache/MIT) · fontdue +111KB(외부 8) · swash +774KB(외부 13 · **게이트 초과 탈락**). 3후보 모두 시스템 한글 폰트(AppleSDGothicNeo.ttc, TTC 인덱스) 로드·한글 래스터 성공. 🔴 **채택 확정 대기**(추천 = ab_glyph) — 상세 [journal 08-08](../docs/journal/2026-08-08.md) |
| **SP-1d** | **한글 IME** 4타깃 동작 | 조합 표시·확정·취소 | ⏳ 실기(`--window`) |
| **SP-1e** | 목록 60fps 500행 | 프레임 드롭 없음 | ⏳ 텍스트 스택·실기 |
| **SP-1f** | **의존성 트리·라이선스** 전수 | 퍼미시브 100% | ✅ **퍼미시브 100%**(LGPL 표기 1건은 OR-선택형→MIT/Apache). 의존성 수 Win **15**/mac **32**/Linux **75** |

**부분 판정** — **크기 차원 R-8 해소**(0.40MB ≪ 10MB). 메모리는 실기 재측정 대상이나 **GUI 프레임워크 공통 비용**이라 스택 교체로 해결되지 않는다. **P1 vs P2의 진짜 축 = 의존성 수(Linux 75) vs 직접 구현 코드량(R-3)** 으로 좁혀졌다.

**후속** — ⓐ ✅ **P2 채택 확정**(2026-08-08 사용자 — winit+softbuffer, [10 §3 원장](10-decision-record.md)) ⓑ 실기 SP-1b/d/e 후 [05 NFR-B-1](05-requirements.md)에 **플랫폼별 메모리 지표**(macOS=phys_footprint) 단서 추가 ⓒ 게이트를 위협하면 NFR 정정(과거 값 삭제 금지 — [16 §2-5](16-doc-git-conventions.md)). Linux·Windows 코드 경로는 `cargo check` 크로스 검증 완료(08-08).

## 7. 결과 (Consequences)

### 긍정

- **[03 §6-4](03-competitive-landscape.md)의 빈 자리를 정확히 차지한다** — 경쟁 제품 전부가 런타임 의존인데 우리만 네이티브 단일 바이너리.
- 메모리 안전이 **R-5(파서 RCE)** 를 구조적으로 낮춘다 — 보안 요구(FR-S-*)와 언어 선택이 같은 방향을 본다.
- 픽셀 버퍼 방식이라 **S-7(OS 구분 불가)** 이 설계상 보장된다.
- `nexa-dir2` 자산(Nexa Controls 14종 계약 · Win32 창 코드 · 예산 게이트 CI 방식)을 **같은 언어로** 재사용할 수 있다 → **D-11**이 실효를 갖는다.

### 부정 · 감수하는 것

- **UI 개발 비용이 크다**(R-3). 툴킷을 쓰면 며칠인 것을 몇 주에 만든다. DR-6이 요구한 대가다.
- **접근성이 늦는다**(R-9) — v2.
- **텍스트 렌더링 품질**이 OS 네이티브 대비 낮을 수 있다. 대신 **일관된다** — 이 트레이드오프를 명시적으로 선택한다.
- Rust 컴파일 시간·학습 곡선.
- 이미지 디코드를 별도 프로세스로 돌리면(FR-S-12) **프로세스 관리 복잡도와 메모리**가 늘어난다 — SP-1b에 반영해 측정한다.

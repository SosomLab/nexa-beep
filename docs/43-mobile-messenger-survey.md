# 43 · 모바일 지원 인스턴트 메신저 조사 — 전송·신원·플랫폼 제약

> **목적** — [00 비전](00-vision.md)이 *"모바일 앱(1차 범위 밖)"* 으로 미뤄 둔 축을 **기술 검토용 자료**로
> 채운다. 데스크톱 경쟁 조사는 [03](03-competitive-landscape.md)(37종)에 있고, 이 문서는 **"모바일까지
> 가는 순간 무엇이 달라지는가"** 만 본다.
>
> ⚠️ **이 문서는 개발 계획이 아니다.** 구현은 별도 프로젝트 또는 같은 저장소의 다른 패키지가 될 수 있고,
> 그 결정은 아직 없다(2026-08-25 기준 · 사용자 확정 = "전체적인 개념 설계와 기술 검토가 목적").
>
> ⚠️ **출처 성격** — 제품 사실관계는 공개 문서·저장소 기준의 **정리**이고, 버전·정책은 바뀐다.
> 채택 판단에 쓰기 전에는 **해당 시점에 재확인**한다(이 저장소 규율: 추정 금지·실측 필수).

---

## 1. 왜 이 조사인가 — 모바일은 "같은 앱의 다른 화면"이 아니다

우리 정체성은 **DR-1 제로 컨피그**(실행 = 참여)와 **DR-8 서버리스 우선**이다. 그런데 모바일 OS는
그 둘을 **구조적으로** 제약한다:

| 제약 | 데스크톱 | 모바일 |
|---|---|---|
| 상시 실행 | 창을 닫아도 트레이 상주 | **백그라운드 수 초 후 정지**(iOS) · Doze(Android) |
| LAN 멀티캐스트 | 그냥 된다 | iOS = **엔타이틀먼트 승인 필요** · Android = `MulticastLock` |
| 프로세스 분리 | `imgdec` 자식 프로세스(R-5) | iOS = **자식 프로세스 불가** |
| 네트워크 | 대체로 고정 | Wi-Fi↔셀룰러 **수시 전환** · 셀룰러엔 LAN이 없다 |

★ **결론이 하나 미리 나온다** — 모바일을 지원하면 **[32 ADR-0013 서버 모드](32-adr-0013-server-modes.md)가
선택이 아니라 전제**가 된다. LAN 밖·백그라운드에서 메시지를 받으려면 **푸시 = 서버**가 필요하기 때문이다.
그래서 이 조사의 첫 질문은 *"어떻게 포팅하나"* 가 아니라 **"제로 컨피그를 어디까지 지키면서 모바일에
갈 수 있나"** 다.

## 2. 분류 축 — 세 가지로 갈린다

| 축 | 값 | 의미 |
|---|---|---|
| **전송** | LAN 직접 / P2P 오버레이(DHT·onion) / 서버 경유 / 메시 (BLE) | 서버 의존도 |
| **신원** | 전화번호 / 계정 / **키 지문** / 무식별자 | 우리는 키 지문(DR-8) |
| **모바일 상시성** | 포그라운드 한정 / 포그라운드 서비스 / **푸시** | 백그라운드 수신 가능 여부 |

## 3. 조사표

### 3-1. LAN·근접 직접형 — 우리와 같은 좌표

| 제품 | 플랫폼 | 전송·발견 | 신원 | 라이선스 | 모바일 처리 |
|---|---|---|---|---|---|
| **LocalSend** | Win·mac·Linux·**iOS·Android** | LAN 멀티캐스트 발견 + HTTP(S) 직접 | 임시(기기 별칭·핑거프린트) | Apache/MIT 계열 | ★ **가장 가까운 선례** — Flutter 단일 코드베이스 · **파일 전송 전용**(대화 없음) · 포그라운드 중심 |
| **KouChat** | Win·mac·Linux·**Android** | LAN 멀티캐스트 | 닉네임(신원 없음) | LGPL-3.0 | 데스크톱+안드로이드 동일 자바 코어 · **2016 이후 정체**([03](03-competitive-landscape.md) 5번) |
| **Softros LAN Messenger** | Win·mac·**Android** | LAN(자체) + 선택적 서버 | 조직 계정 | 상용 | 기능 완성도 높음([03](03-competitive-landscape.md) 7번) |
| **Snapdrop / PairDrop** | **브라우저**(모바일 포함) | 시그널링 서버 + WebRTC | 없음(세션) | 오픈소스 | 설치 없이 모바일 대응 — **서버 필요** |
| **Quick Share / AirDrop** | OS 내장 | BLE + Wi-Fi Direct/AWDL | OS 계정 | 비공개 | ⚠️ 메신저가 아니라 **전송 기능** — 앱이 흉내 낼 수 없는 OS 특권 |

### 3-2. 서버리스 P2P 오버레이 — "LAN 밖에서도 서버 없이"

| 제품 | 플랫폼 | 전송 | 신원 | 특징 |
|---|---|---|---|---|
| **Briar** | **Android**(데스크톱 베타) | Tor + **Bluetooth + Wi-Fi 로컬** | 키 기반·QR 대면 교환 | ★ **재난·검열 대비 설계** — 인터넷 없이 LAN/BT로도 동작 · **모바일 우선 P2P의 정석** |
| **Jami** | Win·mac·Linux·**iOS·Android** | **OpenDHT** P2P(서버 없음) | 키(RING ID) | GNU 프로젝트 · 통화까지 · 데몬+네이티브 UI 구조 |
| **Tox**(qTox·aTox 등) | 전 플랫폼 | DHT P2P | 키(Tox ID) | C 코어(`toxcore`) + 클라이언트 다수 — **코어 공유 모델** |
| **Berty** | **iOS·Android** | **BLE 메시** + libp2p | 키 | 모바일 메시 실험 · 오프그리드 지향 |
| **Bridgefy** | iOS·Android | BLE 메시 SDK | 앱 계정 | 상용 SDK · 시위·재난 사례로 알려짐 |

### 3-3. 서버 경유형 — 모바일 상시성을 택한 쪽

| 제품 | 신원 | 서버 역할 | 배울 점 |
|---|---|---|---|
| **Signal** | 전화번호(+사용자명) | 저장형 중계 + **푸시** | ★ **libsignal = Rust 코어**를 iOS/Android/데스크톱이 공유 |
| **Matrix / Element** | 계정(홈서버) | 연합 서버 | ★ **matrix-rust-sdk + UniFFI**로 모바일 바인딩 — 우리 구조와 가장 유사한 이식 경로 |
| **Delta Chat** | **이메일 주소** | 기존 IMAP/SMTP | ★ **Rust 코어 + 플랫폼별 네이티브 UI**의 모범 사례 · "서버를 새로 만들지 않는다"는 발상 |
| **SimpleX Chat** | **식별자 없음** | SMP 릴레이(무상태) | 신원을 안 두고도 성립하는 극단 설계 — 우리 R-18(영구 재식별자)의 반대편 답 |
| **Session** | 계정 키 | Oxen 서비스 노드 | 전화번호 제거 + onion |
| **Output Messenger** | 조직 계정 | **사내 전용 서버** | 국내 기업 시장의 현실형([03](03-competitive-landscape.md) 12번) |
| **하이웍스·잔디 등 국산** | 조직 계정 | 클라우드 | 조직도 기반 · **제로 컨피그와 정반대**([03](03-competitive-landscape.md) 27번) |

### 3-4. 참고 — 메신저는 아니지만 구조가 겹치는 것

| | 왜 참고하나 |
|---|---|
| **Syncthing** | LAN 발견 + **글로벌 발견 서버 + 릴레이 서버**의 3단 사다리 — 우리 X-UDP-e 사다리와 같은 문제를 먼저 풀었다. Android 앱은 **포그라운드 서비스**로 상시성을 확보 |
| **WebRTC / ICE·STUN·TURN** | 홀펀칭·릴레이 폴백의 산업 표준. 우리 자작 ARQ+랑데부와 대조 자료 |
| **Wi-Fi Aware(NAN)·Wi-Fi Direct** | AP 없이 근접 발견 — Android는 API 제공, **iOS는 앱에 개방 안 함**(비대칭) |

## 4. ★ 아키텍처 선례 — 세 제품이 같은 답에 수렴했다

**Signal(libsignal) · Matrix(matrix-rust-sdk) · Delta Chat(deltachat-core-rust)** 은 서로 다른 목적인데
**같은 구조**를 골랐다:

```
        ┌───────────── 공유 코어(Rust) ─────────────┐
        │  프로토콜 · 암호 · 저장 · 상태 기계        │   ← 플랫폼 무관·테스트 가능
        └───────────────────────────────────────────┘
              ↑ FFI(UniFFI / C ABI / JNI)
   ┌──────────┴──────────┬──────────────┬─────────────┐
 SwiftUI(iOS)      Compose(Android)   데스크톱      CLI
```

**왜 이 구조인가** — 메신저에서 틀리면 치명적인 부분(**와이어 포맷·암호·중복 제거·상태 기계**)은
플랫폼과 무관하고, 플랫폼마다 달라야 하는 부분(**입력기·알림·백그라운드·접근성**)은 네이티브가
압도적으로 유리하다. 그 경계를 FFI로 긋는다.

> ⚠️ **반대 선례도 있다** — LocalSend는 **Flutter 단일 코드베이스**로 모바일까지 갔다. 대신
> **파일 전송 전용**이라 상태 기계가 단순하고, 런타임 크기(수십 MB)를 감수했다. 기능 폭이 좁을 때는
> 단일 UI 코드베이스가 확실히 싸다.

## 5. 모바일이 강제하는 것 — 제품 공통 관찰

| 관찰 | 근거 제품 | 우리에게 주는 함의 |
|---|---|---|
| **순수 LAN 메신저는 모바일에서 드물다** | LocalSend(파일만)·KouChat(정체) | 대화까지 하려면 상시성이 필요하고, 상시성은 서버를 부른다 |
| **서버리스를 지킨 쪽은 "지금 켜져 있을 때만"을 받아들였다** | Briar·Jami·Tox | 오프라인 큐·푸시를 포기하거나, 별도 노드에 맡긴다 |
| **푸시를 쓰면 봉투가 샌다** | Signal·Matrix | APNs/FCM은 제3자 경유 — **본문은 안 보내고 "깨우기"만** 하는 설계가 관례 |
| **iOS는 근접 통신에서 항상 더 닫혀 있다** | Wi-Fi Aware 부재·멀티캐스트 엔타이틀먼트 | iOS를 하려면 **애플 승인 절차**가 일정에 들어온다 |
| **BLE 메시는 매력적이지만 실사용이 어렵다** | Berty·Bridgefy·FireChat(종료) | 대역폭·배터리·백그라운드 제약 — 재난 특수 목적에 가깝다 |

## 6. 우리 좌표 — 조사 결과에 비춘 위치

| | 우리(현재) | 가장 가까운 제품 | 차이 |
|---|---|---|---|
| 전송 | LAN 직접 + 홀펀칭 + 릴레이 사다리 | Syncthing(사다리) · Jami(P2P) | 우리는 **LAN이 1급**이고 릴레이가 폴백 |
| 신원 | 키 지문 TOFU + SAS | Briar·Jami·Tox | 전화번호·계정 없음 = 같은 편 |
| 대화 | 1:1 + 공유 그룹 | Briar·Jami | LocalSend는 여기가 없다 |
| 안전 | 수신 파일 4단계 무해화 | **비교 대상 없음** | ★ 조사한 어느 제품에도 이 수준의 수신 게이트가 없다 |
| 모바일 | **없음** | — | 이 문서의 이유 |

★ **차별점은 유지된다** — 모바일로 가도 *"무해화 게이트가 있는 제로 컨피그 LAN 메신저"* 는
여전히 빈칸이다([03 §7](03-competitive-landscape.md)의 결론과 같다).

## 7. 재확인이 필요한 것 (추정 금지)

이 문서는 정리이지 실측이 아니다. 채택 전에 **직접 확인**해야 할 항목:

- [ ] iOS 멀티캐스트 엔타이틀먼트 **실제 승인 조건·소요**(애플 심사)
- [ ] iOS 로컬 네트워크 권한 프롬프트가 **발견 UX에 주는 마찰**
- [ ] Android `MulticastLock`·포그라운드 서비스에서의 **배터리 실측**
- [ ] 각 제품의 현재 버전·라이선스·유지 상태(이 표는 시점 정리)
- [ ] UniFFI·flutter_rust_bridge의 **산출물 크기**(DR-5 예산은 모바일에서 재정의가 필요할 수 있다)

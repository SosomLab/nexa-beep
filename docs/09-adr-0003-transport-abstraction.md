# 09 · ADR-0003 — 전송 계층 추상화 (로컬 직접 / 릴레이 2모드 경계)

> **상태: 📐 Proposed (사용자 확정 대기)** · 제안 2026-08-08 · 결정자 Sangyong Bae
> [DR-8](10-decision-record.md)의 "2모드 전제 설계"를 **구체적인 경계선**으로 옮긴 문서.
> 관련: [08 ADR-0002](08-adr-0002-discovery-transport.md)(프로토콜) · [06](06-network-stack.md)(L1~L4) · [05](05-requirements.md) FR-R-1

## 1. 배경 — 지금 정하지 않으면 나중에 전부 뒤집는다

DR-8은 **v1에서 로컬 직접 모드만 출시**하되 릴레이 모드를 나중에 얹을 수 있게 설계하라고 요구한다. 문제는 **"나중에"가 실제로 가능하려면 지금 무엇이 지켜져야 하는가**다.

전송을 나중에 끼워 넣으려 할 때 실제로 발목을 잡는 것은 전송 코드가 아니라 **상위 계층에 새어 나간 전송 세부사항**이다:

| 새어 나가면 치명적인 것 | 왜 |
|---|---|
| **IP 주소**가 상위 계층 자료구조에 있다 | 릴레이 모드에는 IP가 없다. 대화 기록·그룹·UI를 전부 고쳐야 한다 |
| **연결 = 대화**로 묶여 있다 | 경로가 바뀌면 대화가 끊긴다. 릴레이 전환 시 이력이 갈라진다 |
| 암호화가 **전송 안**에 있다 | 릴레이가 평문을 보게 된다 — DR-7·FR-R-3 위반 |
| 오프라인 큐가 **로컬 저장 전제**로 짜여 있다 | 릴레이는 서버 보관이라 구조가 다르다 |

> **이 ADR의 목적은 "릴레이를 만드는 것"이 아니라 "릴레이를 만들 수 있는 상태를 유지하는 것"이다.**

### 부수 효과가 오히려 더 크다 — 네트워크 없는 테스트

전송을 추상화하면 **인메모리 전송 구현체**를 만들 수 있다. 그러면 세션·대화·그룹·파일 전송·무해화 로직을 **소켓 없이 단위 테스트**할 수 있다. [05](05-requirements.md) NFR-O-2가 요구하는 **4타깃 CI**에서 실제 멀티캐스트를 쏠 수 없다는 점을 생각하면, 이건 "미래를 위한 투자"가 아니라 **당장 필요한 것**이다.

## 2. 4계층 경계

```
┌───────────────────────────────────────────────────────────┐
│ App      대화 · 그룹 · 파일 · 무해화 · UI                   │  PeerId만 안다
├───────────────────────────────────────────────────────────┤
│ Session  Noise 핸드셰이크 · AEAD · 논리 스트림 다중화        │  Link 위에서 동일
├───────────────────────────────────────────────────────────┤
│ Transport 발견 · 경로 확보 · 재연결                          │  ← 여기가 교체 지점
│           ├ LocalDirect (v1)                                │
│           ├ InMemory    (테스트)                             │
│           └ Relay       (v2 — nexa-beepd)                   │
├───────────────────────────────────────────────────────────┤
│ Link     신뢰·순서 있는 바이트 스트림 (TCP 소켓 / 릴레이 스트림)│
└───────────────────────────────────────────────────────────┘
```

**핵심 규칙 하나** — **암호화(Session)는 Transport 위에 있다.** 그래서 전송이 무엇이든 평문은 두 단말에만 존재하고, 릴레이는 봉투만 본다(DR-7·FR-R-3).

## 3. 핵심 타입 (개념 — 구체 시그니처는 M0에서)

| 타입 | 정의 | 규칙 |
|---|---|---|
| **`PeerId`** | 정적 공개키(또는 그 지문). **전송과 무관한 유일 기기 신원** | IP·MAC·계정은 신원이 아니다. **연결·세션·경로가 붙는 단위** |
| **`UserId`** *(추가 08-08 · [DR-20](10-decision-record.md))* | 사람 단위 식별자. **v1은 `UserId == PeerId` 1:1**, v2에서 1:M([20 ADR-0007](20-adr-0007-multi-device-identity.md)) | **대화 스레드·기록·차단 목록이 붙는 단위.** 아래 규칙 6 |
| **`Locator`** | 전송별 도달 경로. `LocalDirect{ip, port, if_index}` / **`Manual{host, port}`**([ADR-0006](19-adr-0006-manual-endpoint.md)) / `Relay{server, peer}` / `InMemory{id}` | **Transport 계층 밖으로 나가지 않는다** |
| **`PeerHint`** | 발견 결과 — `PeerId`(미검증) + `Locator` 후보 + 표시 이름 + 능력 플래그 | "미검증"임이 타입에 드러난다([08](08-adr-0002-discovery-transport.md)) |
| **`Link`** | 신뢰·순서 있는 양방향 바이트 스트림 | 암호화를 모른다. 그냥 바이트 관 |
| **`Session`** | `Link` + Noise 핸드셰이크 → 인증된 `PeerId` + 논리 스트림 다중화 | **모든 전송에서 동일한 구현 하나** |
| **`Transport`** | 발견하고 `Link`를 만들어 주는 것 | 구현 3종: LocalDirect · InMemory · Relay(v2) |

### `Transport`가 제공해야 하는 것

| 기능 | 설명 |
|---|---|
| `discover()` | `PeerHint` 스트림 — 등장·이탈·경로 변경 이벤트 |
| `connect(PeerId)` | 경로 후보를 순서대로 시도해 `Link` 반환. **어떤 경로를 썼는지는 밖으로 알리지 않는다** |
| `listen()` | 수신 `Link` 스트림 |
| `capabilities()` | 오프라인 큐 지원 여부 등 — App이 기능 노출을 조정하는 근거 |

### ★ 절대 규칙 — 추상화 누수 금지

1. **`Locator`(IP·포트·인터페이스)는 Transport 밖으로 나가지 않는다.** 진단 화면조차 문자열로 받는다.
2. **App 계층 자료구조에 IP를 저장하지 않는다.** 대화 기록·그룹 구성원·차단 목록은 전부 신원 기준(**개정 08-08**: `UserId` 기준 — 규칙 6).
3. **연결과 대화는 분리한다.** 대화는 신원에 붙고, 연결은 왔다 갔다 한다. 경로가 바뀌어도 같은 스레드다(FR-D-6과 같은 원리).
4. **`Session`은 Transport를 모른다.** `Link` 하나만 받는다.
5. **타입으로 강제한다** — 규칙을 문서로만 두면 반드시 샌다. `Locator`를 App 계층에서 참조할 수 없도록 모듈 가시성으로 막는다.
6. **연결은 `PeerId`에, 대화는 `UserId`에 붙인다** *(추가 08-08 · [DR-20](10-decision-record.md) V1-1)* — v1에서는 둘이 1:1이라 차이가 안 보이지만, **스레드 키를 `PeerId`로 두면 v2에서 대화 기록 전체가 기기별로 쪼개진 채 남아** 병합 마이그레이션이 필요해진다. 규칙 3과 **같은 논리를 한 단계 위에** 적용한 것이다.

## 4. 다중 전송 동시 활성 (v2에서 실제가 됨)

같은 `PeerId`에 **로컬 경로와 릴레이 경로가 동시에** 있을 수 있다.

| 항목 | 정책 |
|---|---|
| 우선순위 | **로컬 직접 > 수동(Manual) > 릴레이**. 로컬이 되면 인터넷·서버로 우회하지 않는다(지연·프라이버시) |
| 전환 | 로컬이 끊기면 릴레이로 **자동 폴백**. 로컬이 복구되면 되돌아온다 |
| 대화 연속성 | 전환해도 **같은 대화 스레드**(규칙 3). 사용자에게는 경로 표시만 바뀐다 |
| 중복 수신 | 두 경로로 같은 메시지가 오면 **논리 시퀀스로 중복 제거** |

v1에서는 후보가 하나뿐이라 이 로직이 실질적으로 작동하지 않지만, **인터페이스와 시퀀스 규칙은 v1에 있어야** 한다. 없으면 v2에서 메시지 모델을 다시 만든다.

---

## 5. 릴레이가 보는 것 / 못 보는 것 (v2 — 정직하게)

| 릴레이 서버가 **보는** 것 | 릴레이 서버가 **못 보는** 것 |
|---|---|
| 목적지 `PeerId`(또는 그 해시) | 메시지 내용 |
| 봉투 크기 · 타이밍 | 파일 이름 · 파일 내용 |
| 접속 IP · 온라인 시각 | 그룹 구성 · 표시 이름(암호화 후 전달 시) |

> ⚠️ **메타데이터는 릴레이가 본다.** "누가 누구와 언제 얼마나" — 이건 릴레이 방식의 구조적 성질이고, 숨기려면(믹스넷 등) 제품 성격이 달라진다. **[05](05-requirements.md) NFR-S-5(사실만 표시) 원칙대로 릴레이 모드 UI에 이 사실을 명시**한다. 로컬 직접 모드에는 해당 없음.

## 6. v1 구현 범위

| 구성 요소 | v1 | 비고 |
|---|:--:|---|
| `PeerId` · `PeerHint` · `Link` · `Session` | ✅ | 전 모드 공통 |
| `Transport` 경계 | ✅ | 인터페이스만 확정 |
| `LocalDirectTransport` | ✅ | 유일한 실제 구현 |
| **`InMemoryTransport`** | ✅ | **테스트용 — v1에서 실제로 쓴다** |
| `RelayTransport` | ✕ | v2 · [`nexa-beepd`](10-decision-record.md)와 함께 |
| 경로 우선순위·자동 폴백 | 뼈대만 | 후보가 하나라 실질 동작 없음 |
| 중복 제거(논리 시퀀스) | ✅ | v2에서 필요해지지만 **메시지 모델에 지금 넣는다** |

## 7. 결과 (Consequences)

### 긍정
- **네트워크 없이 상위 계층 전체를 단위 테스트**할 수 있다 — 4타깃 CI(NFR-O-2)에서 즉시 값을 한다.
- 릴레이(v2)를 얹을 때 **App·Session 계층을 건드리지 않는다**.
- `PeerId` 중심 모델이 FR-D-6(다중 경로 병합)·FR-S-2(신원=지문)와 **같은 구조**를 공유한다 — 개념이 하나다.
- 경로가 바뀌어도 대화가 끊기지 않는다(FR-D-5 링크 변경 대응).

### 부정 · 감수
- **간접 계층이 하나 늘어난다** — 코드가 조금 길어지고, 디버깅 시 한 겹을 더 내려가야 한다.
- v1에서는 다중 전송 로직이 **쓰이지 않는 채로 존재**한다(중복 제거·우선순위). 죽은 코드처럼 보일 수 있어 **주석에 v2 근거를 남긴다**.
- 추상화가 새면 이 ADR 전체가 무의미해진다 → **모듈 가시성으로 강제**하고 코드 리뷰 체크 항목에 넣는다.

## 8. 열린 질문

1. `Transport`를 **동적 디스패치**(런타임 교체)로 둘지 **정적**(컴파일 타임)으로 둘지 — v1은 구현이 둘(LocalDirect·InMemory)이라 어느 쪽이든 되지만, v2 다중 전송 동시 활성을 생각하면 동적이 자연스럽다. **M0 스캐폴딩에서 결정**.
2. 오프라인 큐를 `Transport::capabilities()`로 노출할지, 상위에서 항상 로컬 큐를 두고 릴레이는 보조로 쓸지 — **ADR-0004/M1에서**.
3. 진단 화면에서 경로 정보를 어디까지 보여줄지(규칙 1과의 절충).

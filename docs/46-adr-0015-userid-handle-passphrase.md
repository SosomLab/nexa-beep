## 0. 한 장 요약

| 질문 | 답 |
|---|---|
| clip과 같은 방식인가 | **만남(랑데부)은 같은 식**(PBKDF2 · 핸들 솔트 · 일 에폭)을 그대로 쓴다. **신뢰는 다르게 만든다** — clip은 패스프레이즈를 "만남 지점 가리기"에만 쓰고 기기마다 사람이 승인한다(clip 09 §6-3 "타협 불가"). beep 요구는 **승인 없이**이므로 패스프레이즈를 **세션 인증에 결합**(Noise **XXpsk3** · PSK = KDF(passphrase, handle))해 *"같은 비밀을 아는 기기끼리만 핸드셰이크가 성립"* = **암호학적 소속 증명**으로 승격한다. 사람의 SAS 자리를 PSK가 대신한다 |
| 기존 설계(ADR-0007)와의 관계 | ADR-0007은 **서명 키 + 서명된 기기 목록 + 주 기기 + 복구 시드**(무거운 정답). 이번 안은 **그 1단계(경량판)** — **3층**(① PeerId 앵커 ② **무작위 UserKey(전 기기 복제 · 암호로 봉인) → `UserId = H(pub)`** ③ 핸들+암호 = 문 열쇠). 서명된 기기 목록·version은 ADR-0007 그대로, **주 기기 전용·복구 시드만 v2로** 미룬다(폐기 경쟁 = 정직한 충돌 · [47 §3-3](47-adr-0015-review-userid-continuity.md)) |
| 코드 현황과의 거리 | V1-2(팬아웃)·V1-3(sender_device·seq)·V1-4(래핑) = ✅ 실물. **V1-1(스레드·기록·차단 키 = UserId) = ❌ 미반영**(문서는 "반영"으로 오기 — 전부 `PeerId`). 신뢰 판정은 `trust.level(peer)` 12곳 직접 호출이지만 **`TrustStore::level` 한 곳**에서 대부분 흡수 가능 |
| 릴레이 | **서버 무변경**. RID는 기기별 그대로 + **페어링 RID 3개 추가 등록**(clip 우회와 동일 · `MAX_RIDS 8` 안). 1 RID = 1 연결 제약은 그대로 살아 있으므로 "공유 URID"는 쓰지 않는다 |
| 동기화 | **2단**. ① 서버 없이 = **sender copy 팬아웃 + 기기 간 따라잡기(catch-up)** — 같은 사용자 기기끼리는 신뢰되므로 세션 성립 시 `after_seq` 이후 기록을 세션 위로 건넨다(clip에는 없는 것 · 대화는 append-only라 충돌 없음) ② 컨텐츠 모드 = [32 §3-8](32-adr-0013-server-modes.md) 동기 저장소(서버는 암호문 blob·봉투·커서만) |
| 파일 | 릴레이까지 = 기기별 격리·기기별 승인(ADR-0007 §6-2 확정 유지 · 단 **승인은 자동**). 컨텐츠 모드 = **1회 업로드 + 봉투 ①(사용자 마스터 키)** → 어느 기기든 다운로드 · 보관함 온라인 통합(X-3) |
| 난이도 | 슬라이스 6개 · **S0~S3(서버 무변경 · 승인 해제 · 스레드 병합 · sender copy) = 중(각 1~3일)** · S4 따라잡기 = 중 · **S5 컨텐츠 모드 = 대(서버+클라 와이어 신설 · 2주+)** — §7 |

## 2. 조사 결과 — 기존 설계·clip·코드 대조

### 2-1. 세 설계의 신뢰 근거가 다르다

| | **beep ADR-0007**(08-08 확정) | **clip DR-39**(09-03 · 구현 진행) | **이번 안(ADR-0015)** |
|---|---|---|---|
| UserId의 정체 | **장기 서명 키**(Ed25519류) | 타입 자리만(v1 = PeerId 1:1) | **무작위 UserKey(Ed25519 · 전 기기 복제 · 암호로 봉인) → `H(pub)`**(§3-1 · 09-06 개정) |
| "같은 사용자" 증명 | 서명된 DeviceList + Noise 소유 증명(양방향) | **없음** — 같은 RID에서 만난 뒤 **사람이 기기마다 승인**(6자리 코드 육안) | **Noise XXpsk3** — PSK를 모르면 핸드셰이크가 수학적으로 실패 |
| 패스프레이즈의 역할 | (없음 — SAS 대조) | **만남 지점 파생만**("인증에 쓰지 않는다" 09 §6-2) | 만남 지점 파생 **+ 세션 PSK + 사용자 마스터 키 래핑**(§6) |
| 폐기(도난 기기) | 주 기기가 더 높은 version으로 서명 | 미구현(설계 = 키 로테이션) | **UserKey 교체 + 후계 증명서** · 경쟁 = 정직한 충돌(§3-5) |
| 승인 마찰 | 페어링 1회 SAS 필수 | 기기마다 1회 승인 | **0회**(사용자 요구) — 대신 패스프레이즈 강도가 전부다 |
| 서버 변경 | 없음 | 없음(DP-1) | **릴레이까지 없음** · 컨텐츠 모드는 신규 |

> **왜 clip을 그대로 못 쓰나** — clip은 클립보드가 *"비밀번호·API 토큰이 매일 지나가는 통로"* 라 승인 생략을 거부했다(09 §6-3). beep의 요구는 승인 생략이고, 그러면 패스프레이즈가 **곧 신뢰의 전부**가 된다. 그렇다면 그 비밀을 **핸드셰이크 안에 넣어 증명으로 쓰는 것**이 "만남 지점만 가리고 신뢰는 아무것도 안 만드는" clip 방식보다 **더 강하다**(§3-3). 두 방식은 랑데부 층에서 호환되고 신뢰 층에서 갈린다.

### 2-2. 코드 현황 — ADR-0007 V1 제약 4건

| 제약 | 실물 | 이번 안에서 |
|:--:|:--:|---|
| V1-1 스레드·기록·차단 키 = `UserId` | ❌ **미반영** — `HashMap<PeerId, Conversation>`(`app.rs:2730`) · `history/{peer.short}.seg` · `trust.rs:89`·`:60` "차단은 이 키 단위" | **S2에서 실반영**(§5-2 — 뷰 계층 병합 → 저장 병합) |
| V1-2 팬아웃 = `수신자 집합` | ✅ `chat.rs:271` `fanout(sessions, recipients, msg)` | 그대로 사용(sender copy = 집합에 내 기기 추가) |
| V1-3 `sender_device` + seq | ✅ 1:1(`chat.rs:83-84`) · ❌ 그룹(`sgroup.rs:169`) · ❌ 재전달 거부(`chat.rs:151` `SenderMismatch`) | 1:1 sender copy는 **원 발신자 = 세션 상대**라 통과. 그룹은 P-10 반영 필요(S3) |
| V1-4 마스터 키 래핑 | ✅ `trust.seg`·`groups.seg` · ⚠️ `history`는 `keytable`이 기기 개인키로 봉인 | 컨텐츠 모드에서 **봉투 ①(사용자 마스터 키)** 추가(§6-2) |

### 2-3. 신뢰 판정 지점 12곳 → 흡수 가능한 1곳

`trust.level(peer)`를 직접 보는 곳: 원격 파일 게이트(`path.rs:57`) · 원격 인바운드 대기(`app.rs:16093`) · 파일 오퍼 자격(`xfer_policy.rs:225`) · 알림 무음 1:1/그룹(`app.rs:14582`·`12559`) · Urgent 강제 · Delivered/Read ack(`app.rs:14560`·`6443`) · 배지·필터·roster 억제·`/verify` 권유. **`TrustStore::level`(`trust.rs:259`) 한 곳**에서 *"내 사용자 기기면 `FingerprintVerified`"* 를 돌려주면 이 중 10곳이 자동 해결된다. 별도로 손댈 곳 = `judge_offer`(미왕래 강등) · `check_send_eligibility` · `file_allowed`(신원 축 인자 없음) · FR-S-25 모달 · `suggest_verify` — §4 표.

### 2-4. 서버 제약 — 그대로 둔다

`nexa-beepd`의 `rids: HashMap<Rid, ConnId>`는 1:1이고 `Open`은 채널 1개만 만든다(`lib.rs:127·459·487·517`). **공유 URID(한 사용자 = 한 RID)는 뒤 등록이 앞을 축출**한다 — clip이 이 벽에 부딪혀 기기별 RID로 회피했고(clip 07 §3-1 · [44 §3 I-2]) 이번 안도 같은 우회를 쓴다(§3-4). 서버 1:N 확장은 **하지 않는다**(R-4 "릴레이까지는 Peer 단위").

## 3. 신원 설계 — R-1

> ✅ **개정 반영(09-06 · D-32-8·9 확정 · 근거 = [47 검토 보고서](47-adr-0015-review-userid-continuity.md))** — 원안 `UserId = H(handle ‖ KP)`는 암호 변경이 신원을 파괴하고 서버 이름공간을 못 지켜 **기각**. 아래는 **3층 구조**로 고친 본문이다. 흐름도는 [48 §3](48-adr-0015-decisions-impact-flows.md).

### 3-1. 파생식 (세 재료를 한 비밀에서 · 도메인 분리)

```text
③ 문 열쇠(핸들+암호에서 · 바꿔도 신원 불변)
KP   = PBKDF2-HMAC-SHA256( passphrase, salt = "nbeep-user-kdf-v1" ‖ handle, iters = 60_000 )  → 32B  (기기 1회 · 메모리)
PSK           = SHA-256( "nbeep-user-psk-v1" ‖ KP )                           → 32B   ← Noise XXpsk3 재료 (§3-3)
RID_pair(day) = SHA-256( "nbeep-user-rid-v1" ‖ KP ‖ epoch_day )[..16]                  ← 랑데부 (§3-4 · 어제·오늘·내일 3개)
LAN_tag(day)  = SHA-256( "nbeep-user-lan-v1" ‖ RID_pair(day) )[..16]                    ← 발견 패킷 힌트 (§3-4)
K_wrap_user   = SHA-256( "nbeep-user-wrap-v1" ‖ KP )                          → 32B   ← UserKey·사용자 마스터 키 봉인 열쇠
② 신원(무작위 · 불변)
UserKey       = Ed25519 쌍 · 핸들·암호를 넣은 **첫 기기가 1회 생성** · 형제 기기에 PSK 세션으로 복제(봉인본 그대로) · 디스크 = user.key(sealed · 0600)
UserId        = SHA-256( "nbeep-user-id-v2" ‖ UserKey.pub )                   → 32B   ← 남이 나를 가리키는 값 · 표시 = 지문 8자리
① 앵커
PeerId        = 기기 정적 키(현행) — 핀·세션·후계 판정 근거
```

| 규칙 | 이유 |
|---|---|
| **핸들은 솔트에만** 들어간다 | 같은 핸들·다른 암호 = 다른 사용자(clip R-c 충돌 소멸). 핸들은 라벨이지 신원이 아니다(FR-S-2) |
| **PBKDF2 60k**(clip과 같은 값 · `sha2`만 사용 · 의존 신규 0) | 추측 1회 비용. 기기에서는 1회 계산 후 메모리 캐시(`KP`는 디스크에 두지 않는다 — §3-6) |
| 도메인 문자열이 clip(`nclip-*`)과 **다르다** | 앱 격리([44 §1](44-nexa-clip-liaison.md)) — 같은 핸들·암호를 두 앱에 넣어도 서로 못 만난다. 브리지는 별도 옵트인 |
| `UserId`는 **UserKey에서만** 나온다 — 핸들·암호 무관 | 암호·핸들 변경이 신원을 안 바꾼다(재래핑/라벨) — §3-5 · 동시 부트스트랩(기기 둘이 각자 생성)은 `created_at` 빠른 쪽(같으면 pub 사전순)이 이기고 진 쪽이 후계 증명서로 병합 |

> ADR-0007의 `UserId`(= 서명 공개키)와 **같은 의미**가 됐다(`H(pub)`). 타입 `UserId`(32B 뉴타입 · `identity.rs:56`) 그대로. v2 주 기기 승격 때 바뀌는 것은 "누가 UserKey를 쥐는가"뿐이고 데이터 형식은 불변.

### 3-2. 같은 사용자 판정 = "두 값이 같다"의 암호학적 형태

*"서로 동일한 두 값이면 동일 사용자"* 를 코드가 직접 비교하지 않는다(값을 주고받으면 그 자체가 유출이다). **같은 값이면 같은 PSK가 나오고, 같은 PSK를 가진 쪽끼리만 핸드셰이크가 성립한다** — 성립 자체가 판정이다.

```text
① 발견/랑데부   LAN_tag 또는 RID_pair가 같다        → "같은 사용자일지도"(미검증 힌트 · 발견 패킷은 힌트다 — 08 §2)
② 핸드셰이크    Noise_XXpsk3(PSK)                    → 성립 = 상대가 KP를 안다 = 같은 사용자 ★ 여기서만 판정
③ 등재          상대 PeerId를 내 UserId의 기기로 기록 · UserKey 봉인본 동기(없는 쪽이 받음) · 서명된 기기 목록 version+1  → 이후 trust.level = 소속 기기(§4)
```

### 3-3. Noise XXpsk3 — 왜 PSK이고, 왜 psk3인가

- `snow 0.9.6`은 `Noise_XXpsk3_25519_ChaChaPoly_BLAKE2s`를 그대로 지원(psk 수식자). **의존 신규 0** · 기존 `NoiseSession::initiate/accept`에 `psk(3, &PSK)` 한 줄.
- **psk3** = XX의 세 번째 메시지 뒤에 PSK를 섞는다 → 양쪽 정적 키 교환·서명은 그대로(**PeerId 확정 · 핀 저장 그대로**), PSK는 최종 세션 키에 결합. PSK가 다르면 마지막 메시지 복호에 실패 = 성립 안 함.
- **오프라인 사전 공격 내성**: PSK는 임시 DH 비밀 이후에 섞이므로 도청자는 핸드셰이크 기록만으로 추측을 검증할 수 없다 — **온라인 추측만**(시도 1회 = 핸드셰이크 1회). 여기에 **인바운드 PSK 실패 백오프**(같은 IP·PeerId 5회/분 → 10분 무시)를 둔다. 60k PBKDF2 + 온라인 한정 = 12자 무작위 패스프레이즈(≈59비트)로 충분하고, 사용자가 고른 약한 암호는 강도 표시로만 경고(clip D-29 동일 · 강제 없음).
- **일반 상대(다른 사용자)는 종전 `Noise_XX` 그대로.** 두 패턴 중 어느 것을 쓸지는 발견 힌트(§3-4)로 정하고, 힌트가 틀리면(같은 태그인데 PSK 불일치) **일반 XX로 1회 재시도** — 실패는 정상 경로(clip AP-2와 같은 결).
- ⚠️ **prologue는 계속 쓰지 않는다**(08-26 실측 = 미사용 · 채택은 와이어 비호환). 앱 격리는 도메인 문자열이 맡는다.

## 5. 메시지 동기화 — R-3 (서버 없이 되는 것까지)

### 5-1. sender copy — 발신은 "상대 기기들 + 내 다른 기기들"

`fanout(sessions, recipients, msg)`(V1-2)에 **수신자 집합 = 상대 UserId의 기기 ∪ 내 UserId의 다른 기기**를 넣는다. 내 기기로 가는 사본은 같은 `ChatMessage`(같은 `sender_device`·`seq`)이고, 받은 기기는 **`sender_device`가 내 UserId 소속이면 "내가 보낸 것"으로 오른쪽에 그린다** · 알림 없음 · Delivered/Read ack 되쏘지 않음. 중복은 `DedupIndex`(발신 기기, seq)가 이미 거른다.

| 항목 | 규칙 |
|---|---|
| 상대가 보낸 메시지 | 상대는 **내 기기 전부**에 팬아웃한다(내 기기 목록은 §5-3 교환으로 안다). 꺼진 기기는 못 받는다 → §5-4 따라잡기 |
| 읽음 상태 | 내 기기 간 Control 프레임 `SyncRead{thread, upto_seq}` — 상대에게는 여전히 "읽음"을 보내지 않는다(DR-25) |
| 그룹 | 그룹 메시지에 `sender_device` 추가(P-10 · 와이어 kind 신설 = 전방 호환) 후 같은 규칙 |
| 파일 | 오퍼는 상대 기기 각각에 간다(ADR-0007 §10 "기기 수만큼 링크에 나간다" 감수 · UI 명시). 내 다른 기기에는 **오퍼 사본을 보내지 않는다**(파일은 §6 컨텐츠 모드가 답) |

### 5-2. 스레드 키 = UserId (V1-1 실반영)

| 단계 | 내용 |
|---|---|
| 뷰 계층(먼저) | `conversations: HashMap<PeerId,…>`는 두고, **표시 키 `ThreadKey = UserId`** 로 접는다: 같은 UserId의 기기 N대 = 한 행 · 한 스레드(여러 세션의 라인을 `(sender_device, seq)`로 병합 정렬 · 도착순 안정) |
| 저장 계층(다음) | `history/u-{uid.short}.seg` 신설 · 기존 `{peer.short}.seg`는 **부팅 시 매핑 표**(`UserId → [PeerId]`)로 읽어 병합 표시(파일 이동 없음 · 셰레딩 키 유지) |
| 차단·핀·프로필 | 레코드에 `user` 필드 · 차단은 UserId · 프로필 카드는 사용자 1장 + 기기 N줄(마지막 접속) |

### 5-3. 기기 목록 교환 — Control 프레임 신설(태그 4~9 비어 있음)

| 태그 | 프레임 | 내용 |
|:--:|---|---|
| 4 ✅ | `UserHello { user_pub, name, devices: [PeerId], list_ver, sig }` | **구현 09-06(S2-e `2cbb58d`)** — 세션 성립 직후 양방향(형제·타인 모두). **UserKey 서명** — 상대는 ①sig 검증 ②제시한 PeerId ∈ devices ③version 단조로 소속을 검증한다(ADR-0007 §4 절차 그대로 · A-1 방어) |
| 5 | `SyncRead` | §5-1 |
| 6 | `SyncPull { thread, after_seq, max }` / 7 `SyncLines{…}` | §5-4 |
| 8 | `Succession{…}` | §3-5 침해 대응 후계 증명서(UserHello에 동봉 가능) |
| 9 ✅ | `UserKeyBlob{sealed}` | **구현 09-06(S2-b `02dfca4`)** — 형제 세션에서 UserKey 봉인본 동기(양쪽이 보내고 "오래된 키가 이긴다" D-32-8로 수렴 · 요청 없음) |
| 11 ✅ | `UserProof{proof}` | **신설 09-06(S1-e `a31a735`)** — 세션 내 형제 증명 `HMAC(PSK, "nbeep-user-proof-v1"‖핸드셰이크 해시‖역할)`: XX로 이미 선 세션(부팅 경합·나중에 기능 켬)을 재접속 없이 승격. 세션당 1회 · 힌트 후보에게만 · 실패 3회 상한 |

> ★ **A-1(남의 기기를 내 사용자라 주장) 방어** — 목록은 **UserKey 서명**이 있어야 하고, 접는 것은 **그 기기 자신과의 세션(Noise 소유 증명) + 그 기기가 제시한 서명 목록에 자기가 있을 때**뿐이다. 남이 준 목록만으로 다른 기기를 편입하지 않는다. 공격자가 내 UserId를 주장하려면 UserKey(= 내 형제 세션 진입 + 봉인 해제)가 필요하다.

### 5-4. 따라잡기(catch-up) — 오프라인 기기가 놓친 것

같은 사용자 기기 사이는 **신뢰된 통로**라 기록을 세션 위로 건널 수 있다(clip에는 이 개념이 없다 — 최신 1개만 덮어쓴다).

```text
PSK 세션 성립 → 양쪽 UserHello(list_ver) → 각 스레드별 (마지막 seq per sender_device) 비교
→ 부족한 쪽이 SyncPull{thread, after_seq, max=200} → SyncLines(평문 라인 · 세션 암호화) → 받은 기기가 자기 키로 봉인 저장
```

| 규칙 | 이유 |
|---|---|
| 대화는 **append-only** → 충돌 없음 · 정렬 = `(sender_device, seq)` + 도착순 | [32 §3-8-2] 동일 |
| 상한 = 스레드당 최근 200줄 · 총 1MiB/세션(설정) | 예산(DR-5) · 나머지는 컨텐츠 모드 |
| 파일 본문은 따라잡지 않는다 — **라인만**("[파일] … (이 기기에는 없음)") | 격리 실체화는 기기별(ADR-0007 §6-2) |
| **저장 키는 각 기기 것** — 기록 파일을 옮기지 않는다 | [17 §3] 래핑 계층 불변 · `UserId` 키로 열지 않는다(§9-1)는 그대로 |

## 6. 컨텐츠 모드 — R-5 "일반 메신저처럼"

> [32 §3-8](32-adr-0013-server-modes.md) 동기 저장소(사용자 확정 B: *"어느 기기에서 접속해도 내 대화와 파일이 있다"*)의 **입력이 이 ADR**이다 — §3-3 *"모드 ②는 다중 기기 없이 성립하지 않는다"*.

### 6-1. 서버가 아는 것(봉투)과 모르는 것

| 서버가 보관 | 형태 | 서버가 모르는 것 |
|---|---|---|
| 스레드 색인 `{UserId(가명 PseudoId) → [thread_id]}` | 암호문 | 상대가 누구인지(thread_id = H(UserId_a ‖ UserId_b)의 가명) |
| 라인 블록 `Enc(K_thread, lines[seq..])` | 암호문 blob | 내용 |
| 파일 blob `Enc(K_content, file)` + **봉투 ① `Wrap(K_user_master, K_content)`** | 암호문 + 32B | 내용·이름 |
| 기기별 커서 `Enc(K_user_master, {thread, seq})` | 암호문 | 진도 |

### 6-2. 키 계층 — 사용자 마스터 키(래핑 재검토 조건 발동)

```text
K_user_master  = 무작위 32B(최초 1회 · 어느 기기든) ── Wrap(K_wrap_user = KDF(passphrase))로 봉인해 서버·전 기기에 보관
K_thread, K_content = 무작위 · Wrap(K_user_master)로 봉투 ① · 상대 사용자에게는 Wrap(상대 K_user_master 공개 래핑 or 기기 키) 봉투 ②
```

- [17 §3-2](17-adr-0005-history-at-rest.md) *"재검토 조건 — Managed Server 모드"* 가 정확히 이것이다. 승격 ②(사용자 암호 KDF)가 제로컨피그 위반으로 실격됐던 것은 **기본 사용자에게 암호를 요구**하기 때문이었고, 여기서는 **핸들·암호를 스스로 입력한 사용자**에게만 열린다(S-0 옵트인).
- ADR-0007 §9-1(서명 키로 기록을 열지 않는다)은 **그대로 성립** — 여는 키는 서명 키가 아니라 패스프레이즈 파생 래핑 키다. 단 **패스프레이즈 = 전 기록의 열쇠**라는 사실을 시드 화면과 같은 강도로 고지한다.
- 암호 변경 = `K_user_master` **재래핑만**(재암호화 없음) — V1-4의 값.
- **복구 불가 지점**: 암호를 잃으면 서버도 못 열어 준다([32 §3-8] *"그게 설계다"*).

### 6-3. 동작 — "같은 대화 목록·같은 사용자·파일 업/다운로드"

| 기능 | 동작 |
|---|---|
| 같은 대화 목록 | 기기 접속 → 서버에서 스레드 색인·커서 pull → 없는 라인 블록 pull → 로컬 봉인. 발신은 **서버 push + 온라인 기기 직접 팬아웃**(S-1 LAN 우선) |
| 같은 사용자로 대화 | 상대는 나를 **UserId 하나**로 본다(§5-2). 어느 기기에서 보내도 같은 스레드 |
| 파일 업로드 | 기존 파일 와이어 재사용 · 서버 = 자동 승인 수신 단말([32 §5-11] 1) · 본문은 `K_content` 암호문 · 1회 업로드 + 봉투 N개(P-9 · kind 8 예약 자리 실체화) |
| 파일 다운로드 | 보관함 온라인 통합(X-3) — 온라인 항목 클릭 = pull → **무해화 게이트 동일 통과** → 격리 → 승인 실체화(기기별). "일반 메신저처럼"의 마지막 차이 = **격리 단계가 보인다**는 것이며 이는 DR-13이라 유지 |
| 오프라인 기기 | 켜지면 커서 이후를 pull — 릴레이의 "파이프" 한계가 여기서 풀린다 |

### 6-4. 서버 변경(신규 · beepd `Content` 타입)

`C2s` 신설: `PutBlob{ns, id, bytes}` · `GetBlob{ns, id}` · `ListIndex{ns}` · `PutCursor/GetCursor` · 쿼터/TTL(L1 90일 기본 · [32 §3-9-3]). 인증 = 세션 정적 키 + **UserKey 서명 챌린지**(nonce ← 서버 · 응답 = Sign(UserKey, nonce) — 이름공간 선점·오염 차단 · 47 P-3) + 가명 `HMAC(server_salt, UserId)` — 서버는 UserId 원본을 저장하지 않는다. 상세 와이어는 착수 시 [32 §12-6] MVP 방식으로 별도 문서.

## 8. 개발 방법 (docs/15 수직 슬라이스)

1. **S0 → S1 → S2 순으로 각각 커밋 1개 이상 · main 항상 green** · 테스트 더블: S1은 `InMemoryLink` 위 XXpsk3 왕복·불일치 실패·폴백 회귀 / S2는 `MemoryTrustStore` 순수 규칙 / S3·S4는 `nbeep-core` 순수 병합·정렬·dedup 회귀 + 트레이스 재생.
2. **실기 게이트**: 같은 mac에서 신원 2개(`relaunch` A·B)에 같은 핸들·암호 → "내 기기" 배지 · 승인 0회 파일 · sender copy · B 껐다 켜기 = 따라잡기. 그다음 Win↔mac 2-PC.
3. **clip 회신**([44 §7-4]): ① `user.passphrase` 평문 저장(clip `settings.cfg`) → 봉인 권고 ② 도메인 문자열 `nbeep-user-*` 등재(격리) ③ 랑데부 등록 6개 규칙 공유 ④ XXpsk3 채택 사실(clip이 원하면 같은 식으로 승인 마찰을 줄일 수 있다 — clip 결정).
4. **문서 동기**: 확정 시 [20](20-adr-0007-multi-device-identity.md) 상단에 "1단계 = ADR-0015" 개정 표 · [10 DR-20](10-decision-record.md) 개정 · [05](05-requirements.md) FR-D-14·FR-S-28~ 갱신 · [40](40-known-limitations.md)에 "패스프레이즈 = 신뢰의 전부" 한계 등재.

## 10. 결과(Consequences)

**긍정** — 요구 R-1~R-4를 서버 무변경으로 만족 · 승인 0회의 근거가 사람의 습관이 아니라 PSK · V1-1(스레드 = UserId)이 드디어 실반영되어 컨텐츠 모드의 선행 조건이 갖춰진다 · clip과 랑데부 층 호환.
**부정·감수** — **패스프레이즈가 신뢰의 전부**(유출 = 전 기기·전 기록(컨텐츠 모드) 노출 · 폐기 = 암호 변경 + 전 기기 재입력) · ADR-0007의 서명 체인·주 기기·복구 시드는 v2로 미뤄져 롤백 방지가 없다(잃은 기기는 옛 암호로 옛 UserId에 남을 뿐 새 UserId에는 못 들어온다 — 이것이 경량판의 폐기다) · 파일은 기기 수만큼 링크에 나간다 · 격리 실체화는 기기별이라 "일반 메신저"와의 마지막 차이가 남는다.

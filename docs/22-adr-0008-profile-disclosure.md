# 22. ADR-0008 — 프로필 옵트인 노출 (발견 시 식별 정보 공개)

> **상태: 📐 Proposed** (2026-08-08) · 근거 요구: 사용자(08-08) — *"내가 배포가 가능하도록 추가한 정보는 auto discovery 시에 노출되도록. 실제 이름·전화번호·이메일·별명·User Id 등 나를 식별하거나 연락을 용이하게 하는 정보 중 **본인이 설정하고 노출 확인을 한 대상**만."*
> 관련: [08 ADR-0002](08-adr-0002-discovery-transport.md)(발견 패킷·미검증 힌트) · [10 §0](10-decision-record.md)(봉투만 본다) · [20 ADR-0007](20-adr-0007-multi-device-identity.md)(`UserId`) · [05 FR-D-15~16](05-requirements.md)

## 1. 문제 — "발견 시 노출"과 기존 결정 둘이 충돌한다

요구 자체는 명확하다: 회사 LAN에서 "김철수 (영업팀, 010-xxxx, kim@corp)"가 목록에 보이면 **누구에게 말 걸지 고르기 쉬워진다**. 호스트명 기반 기본 이름(FR-D-9)만으로는 `DESKTOP-A7X3` 이 누구인지 모른다.

그러나 그대로 발견 패킷에 실으면 두 결정이 깨진다:

| 충돌 | 내용 |
| --- | --- |
| **봉투 원리** ([10 §0]) | *발견 패킷은 존재만 노출한다.* 브로드캐스트는 **평문**이라 앱을 실행하지 않는 스니퍼도 서브넷의 전화번호·이메일을 **수확(harvest)** 할 수 있다. 앱 사용자에게 보여주려던 정보가 네트워크 전체에 공개된다 |
| **발견 무인증** ([08 §2]) | 발견 패킷은 서명하지 않는 "힌트"다. 여기 실은 실명·전화번호는 **누구나 사칭 가능**하다 — 공격자가 "김철수, 010-…" 를 자기 키로 뿌리면 UI가 구분할 수 없다. 스팸 방어가 1차 범위인 제품([03 §6])에서 이건 피싱 표면이다 |

추가 제약: 발견 패킷은 **512B 상한**([08 §2])이라 필드를 늘릴 공간 자체가 없다.

## 2. 결정 — 노출의 **UX는 발견 시점**, 전달은 **세션 경유**

> **핵심: 발견 패킷은 지금처럼 "존재 + 표시 이름"만. 프로필은 세션(암호화·인증) 위에서 조회하고, 발견 직후 자동 프리페치해서 사용자에게는 "발견하자마자 보이는" 경험을 준다.**

### 2-1. 프로필 모델

```text
Profile {
  fields: [ (ProfileField, String) ],   // 본인이 설정한 필드만
  rev: u32,                             // 변경 감지(캐시 무효화)
}
ProfileField = RealName | Nickname | Email | Phone | Department | StatusMessage
             | UserId(v2 — 서명된 주장, ADR-0007) | Custom(label)
```

- **필드 단위 옵트인** — 설정 화면에서 각 필드를 입력하는 것과 **노출을 켜는 것은 별개 행위**다. 노출을 켤 때 **"이 값은 같은 네트워크의 다른 사용자에게 보입니다"** 확인을 받고, **상대 화면에 보이는 그대로의 미리보기**를 보여준다(사용자 요구의 "노출 확인"이 이것이다).
- **기본값 = 전부 비노출.** 표시 이름(FR-D-9)만 지금처럼 나간다. 아무것도 설정하지 않아도 제품은 완전하다(DR-1 — 제로 컨피그 훼손 금지).
- 프로필 필드 값도 표시 전 **무해화**(RLO·제어문자·0폭 — FR-S-13)를 통과한다. `DisplayName::parse` 계열의 필드별 파서를 쓴다.

### 2-2. 전달 경로 — 왜 브로드캐스트가 아닌가

| 경로 | 채택 | 이유 |
| --- | :--: | --- |
| 발견 패킷(ANNOUNCE)에 포함 | ❌ | §1의 충돌 — 평문 수확·무인증 사칭·512B. **어떤 프로필 필드도 브로드캐스트에 싣지 않는다**(전화번호만이 아니라 전부 — "민감한 것만 빼자"는 경계선이 유지되지 않는다) |
| **세션 조회 + 자동 프리페치** | ✅ | 세션은 **암호화**되고(수확 불가) 상대 키가 **인증**된다(이 키의 주장임이 확정). 발견 → 목록 표시 → **백그라운드 자동 핸드셰이크 + 프로필 조회** → 수 초 내 목록에 채워진다 |

- ANNOUNCE에는 **`has_profile` 플래그 1비트 + `profile_rev`** 만 추가한다(캐시가 최신이면 조회 생략 — 트래픽·전력 절약).
- 프리페치는 **속도 제한**한다(동시 N개·피어당 쿨다운) — 대규모 서브넷에서 폭주 금지(NFR-B), 그리고 인바운드 조회도 속도 제한(스팸·수확 방어).
- 프리페치용 세션은 TOFU 핀을 남기는 정식 세션이다 — 별도 경량 채널을 만들지 않는다(공격면 추가 금지).

### 2-3. 프로필은 "주장"이다 — 신뢰 표시 규칙

- 세션 조회로 확정되는 것은 **"이 키(PeerId)가 이 프로필을 주장한다"** 까지다. 실명·전화번호가 **진짜인지는 아무도 보증하지 않는다**. UI는 프로필 필드를 신뢰 배지(미검증/핀/대조완료 — M2-7)와 **함께** 표시하고, 미검증 상대의 실명·연락처엔 그 상태를 명시한다(NFR-S-5 — 보증하지 않는 것을 보증하는 척하지 않는다).
- **이름 재사용 경고(M2-2 `name_conflict`)를 프로필 필드로 확장**한다 — 같은 실명/이메일이 다른 키로 나타나면 경고. 연락처 필드는 표시 이름보다 사칭 유인이 크므로 이 경고가 더 중요하다.
- v2: `UserId` 서명 프로필 — 프로필을 `UserId` 키로 서명하면 "이 **사람**의 주장"으로 승격된다(ADR-0007과 자연 결합).

### 2-4. 원격(수동 엔드포인트) 상대

DR-19의 원격 신뢰 등급에는 **프로필을 보내지 않는 것이 기본**이다(LAN 밖은 위협 모델이 다르다 — 회사 동료라는 암묵 전제가 없다). 원격 상대별로 명시 허용할 수 있다.

## 3. 봉투 대조표 (이 설계의 봉투는 무엇인가)

| 계층 | 보는 것 | 보지 않는 것 |
| --- | --- | --- |
| 발견 패킷 | 존재 + 표시 이름 + `has_profile`/`rev` | **모든 프로필 필드** |
| 세션(전송 경로) | 암호문 | 평문 프로필 |
| 상대 앱 | 본인이 노출 확인한 필드만 | 비노출 필드·설정 화면의 입력값 |
| 저장(상대 측 캐시) | 노출된 필드 + rev | — (rev 변경 시 갱신·필드 철회 시 삭제) |

**노출 철회**: 필드를 끄면 `profile_rev` 가 올라가고, 다음 ANNOUNCE를 본 상대는 캐시를 갱신해 해당 필드를 지운다. (이미 본 사람의 기억까지 지울 수는 없다 — 이 한계는 확인 다이얼로그에 명시한다.)

## 4. 결과 (Consequences)

- ✅ "발견하면 누군지 보인다"는 UX를 **평문 수확·사칭 표면 없이** 얻는다.
- ✅ 발견 패킷 512B·무인증 설계(ADR-0002)를 건드리지 않는다 — 추가는 플래그+rev 뿐.
- ⚠️ 프로필 표시까지 세션 왕복 1회의 지연이 있다(LAN에서 수십 ms — 체감 없음). 대규모 서브넷에서는 프리페치 속도 제한 때문에 목록이 점진적으로 채워진다.
- ⚠️ 자동 프리페치 = 발견된 미지 피어와 **자동 핸드셰이크**다. 핸드셰이크 자체는 안전하지만(키 교환일 뿐) 인바운드 조회 속도 제한·차단 목록 우선 적용(차단 상대에겐 프로필 응답 안 함)이 전제다.

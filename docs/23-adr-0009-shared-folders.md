# 23. ADR-0009 — 공유 폴더 (가상경로 공유·풀 다운로드)

> **상태: 📐 Proposed** (2026-08-08) · 근거 요구: 사용자(08-08) — *"내가 등록한 공유허용 폴더/파일의 목록을 관리할 수 있도록 하고, 해당 폴더/파일을 **가상경로로 묶어서** 다른 사람들이 **바로 다운로드 가능**하도록 공유 기능도 설계에 넣어줘."*
> 관련: [04 안전 송수신](04-safe-transfer.md)(무해화 게이트) · [11 ADR-0004](11-adr-0004-quarantine.md)(`.beepq`) · [19 ADR-0006](19-adr-0006-manual-endpoint.md)(원격 신뢰 등급) · [05 FR-X-8~11](05-requirements.md)

## 1. 문제 — push 전송만으로는 부족하다

기존 파일 전송(FR-X-1~7)은 **push** 다 — 보내는 사람이 파일을 고르고 상대가 수락한다. 하지만 팀 공유의 실사용은 **pull** 이 많다: "설치 파일은 김대리 공유 폴더에서 받아가세요." 국내 LAN 메신저 실사용(IPMsg 계열)에서도 공유 폴더는 핵심 기능이었다([03]). 이걸 위해 별도 SMB/파일서버를 켜는 순간 제로 컨피그(DR-1)가 무의미해진다.

동시에, 내 파일시스템을 노출하는 기능은 **이 제품에서 가장 위험한 공격면**이다. 실경로 노출·경로 탈출(path traversal)·심링크 탈출·의도치 않은 파일 포함이 전부 실제 사고 패턴이다.

## 2. 결정 — 가상 루트 + 세션 위 읽기 전용 pull + 수신은 동일 게이트

### 2-1. 공유 목록(Share Registry)

```text
Share {
  name: ShareName,          // 가상 루트 이름 — 상대에게 보이는 유일한 "경로의 뿌리"
  source: PathBuf,          // 실경로(폴더 또는 단일 파일) — 절대 밖으로 나가지 않는다
  scope: ShareScope,        // 누가 볼 수 있나 (§2-3)
  enabled: bool,            // 일시 중지
}
```

- 사용자는 폴더/파일을 **공유 목록에 등록·해제·일시 중지**한다. 등록 시 프로필 노출(ADR-0008)과 같은 UX 패턴으로 **"이 폴더의 내용이 [범위]에게 보이고 다운로드됩니다"** 확인을 받고, **상대에게 보이는 그대로의 목록 미리보기**를 보여준다.
- **기본값 = 공유 없음.** 아무것도 등록하지 않으면 이 기능은 존재하지 않는 것과 같다(DR-1).

### 2-2. 가상경로 — 상대는 실경로를 절대 보지 못한다 (봉투)

상대가 보는 주소는 `share:<ShareName>/<상대경로>` 뿐이다. `C:\Users\kim\Documents\...` 는 프로토콜 어디에도 나타나지 않는다.

서버 측 해석 규칙(전부 **fail-closed**):

| 규칙 | 내용 |
| --- | --- |
| **정규화 후 조상 검사** | 요청 경로를 canonicalize한 결과가 **공유 루트의 하위가 아니면 거부**. `..`·중복 구분자·유니코드 정규화 우회를 문자열이 아니라 **파일시스템 정규화 결과**로 판정한다 |
| **심링크 탈출 금지** | 해석 결과가 루트 밖을 가리키는 심링크/정션이면 **목록에서 숨기고 요청은 거부** |
| **기본 제외** | 숨김 파일(닷파일·hidden 속성)·OS 메타(`.DS_Store`·`Thumbs.db`)·`.beepq` 등 앱 산출물은 기본 비노출(옵트인으로만 포함) |
| **읽기 전용** | 업로드·수정·삭제 요청 타입 자체가 프로토콜에 없다. v1 공유는 단방향 pull이다 |
| **열람 ≠ 실행** | 서버는 파일을 **열어 읽기만** 한다 — 어떤 경우에도 실행·해석하지 않는다(FR-S-9의 발신 측 대칭) |

### 2-3. 접근 제어(ShareScope) — 누구에게 보이나

| Scope | 의미 |
| --- | --- |
| `Connected` | 세션이 성립한 LAN 상대 누구나(= 발견된 모두). **마찰 최소** — "바로 다운로드"의 기본 후보 |
| `Verified` | SAS 대조 완료(`FingerprintVerified`) 상대만 |
| `Peers(집합)` | 명시한 `PeerId`/로컬 그룹 구성원만. 그룹은 로컬 개념(FR-G-3)이므로 **내 그룹 정의가 곧 ACL**이다 — 상대와 합의가 필요 없다 |

- 공유별로 지정하며 기본값은 **등록 확인 다이얼로그에서 사용자가 고른다**(추천 기본: `Connected` — LAN 공유의 기대 동작. 단 다이얼로그가 범위를 명시적으로 보여준다).
- **차단 상대(TrustStore) 우선** — 어떤 scope여도 차단이면 목록·다운로드 모두 거부.
- **원격(수동 엔드포인트, DR-19) 상대에게는 기본 비노출** — LAN 밖은 위협 모델이 다르다. 원격 상대는 `Peers` 로 명시했을 때만, 그리고 DR-19의 "SAS 전 파일 차단"이 pull에도 그대로 적용된다.

### 2-4. 프로토콜 — 세션 위 두 요청

세션(Noise 암호화·인증) 위에 요청 2종을 얹는다(M2-3 다중화의 논리 스트림):

- `ShareList { share?, path?, page }` → 항목(이름·크기·수정시각·종류) 페이지. **썸네일·미리보기는 없다**(이미지 디코드 공격면을 목록 조회에 열지 않는다 — FR-S-12는 수신 승인 후의 일).
- `ShareGet { share, path, range }` → 스트리밍 바이트(FR-X-5와 같은 청크·백프레셔). `range` 는 v1은 처음부터, 재개(FR-X-7)는 v2.

발견 ANNOUNCE에는 **`has_shares` 플래그 1비트만** 추가한다(ADR-0008과 동일 원칙 — 브로드캐스트에는 목록을 싣지 않는다. scope 판정 전에 존재를 광고할 수 없기도 하다).

### 2-5. 수신(pull) 측 — 무해화는 경로와 무관하다

**내가 요청해서 받은 파일도 4단계 게이트(FR-S-5)를 동일하게 통과한다** — 협상(목록의 메타) → `.beepq` 격리 → 검사 → 승인 실체화. "내가 고른 파일이니 안전하다"는 성립하지 않는다 — 공유 서버 쪽이 악성일 수 있고, 파일명이 보여준 것과 내용이 다를 수 있다([04] T-7 "보낸 사람이 누구든 믿지 않는다"의 pull 형태). SHA-256 검증(FR-X-6)도 동일 — 목록 응답의 해시와 수신 바이트를 대조한다.

### 2-6. 계측·감사

공유는 내 디스크를 남이 읽는 기능이므로 **전 행위를 계측**한다(docs/13 §6): `ShareRegistered / ShareListed / ShareDownloaded / ShareDenied`(거부 사유 코드 포함). 내 공유 화면에서 "누가 언제 무엇을 받아갔나"를 볼 수 있다 — 이것이 공유를 켜 둘 수 있게 하는 심리적 전제다.

## 3. 봉투 대조표

| 계층 | 보는 것 | 보지 않는 것 |
| --- | --- | --- |
| 발견 패킷 | `has_shares` 1비트 | 공유 이름·목록·경로 |
| 상대 앱 | scope 통과한 공유의 **가상경로·메타** | **실경로** · scope 밖 공유의 존재 |
| 서버(내 앱) | 요청 가상경로 → 루트 내 해석 결과 | — (루트 밖은 해석 자체를 거부) |
| 계측 | 누가·언제·무엇·몇 바이트 | 파일 내용 |

## 4. 결과 (Consequences)

- ✅ SMB·별도 서버 없이 "공유 폴더에서 받아가세요"가 된다 — 제로 컨피그 유지.
- ✅ push(기존 FR-X)와 pull이 **같은 세션·같은 스트리밍·같은 게이트**를 탄다 — 코드 경로 이원화 없음.
- ⚠️ 경로 해석기는 **안전 회귀 테스트 전항목**([18])에 traversal·심링크·유니코드 우회 케이스를 추가해야 한다 — 이 모듈의 버그는 곧 정보 유출이다.
- ⚠️ `Connected` scope는 "LAN의 모두"와 같다 — 등록 다이얼로그가 이를 숨기지 않고 말해야 한다.

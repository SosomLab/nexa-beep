# 17 · ADR-0005 — 대화 기록 저장 암호화 (at-rest)

> **상태: 📐 Proposed (사용자 확정 대기)** · 제안 2026-08-08 · 결정자 Sangyong Bae
> **사용자 확정 요구(2026-08-08)**: *"송수신 기록과 내용은 암호화해서 내부에 보관. 일반적으로 서버 모드면 서버 관점에서 보관되는 대상이지만, **서버리스 클라이언트 입장에서도 기록은 관리되어야** 한다. 대신 **외부로 노출되지 않아야** 한다."*
> 관련: [08 ADR-0002](08-adr-0002-discovery-transport.md)(전송 암호화) · [05](05-requirements.md) FR-M-4 · [01 §5](01-architecture.md)(store) · [13 §6](13-code-design-standards.md)(계측)

---

## 1. 배경 — 전송 암호화와는 다른 문제다

[ADR-0002](08-adr-0002-discovery-transport.md)가 푼 것은 **선 위의 데이터**(in transit)다. 이 ADR이 푸는 것은 **디스크 위의 데이터**(at rest)이고, **훨씬 어렵다.**

| | 전송 암호화 | **저장 암호화** |
|---|---|---|
| 키를 어디서 | 핸드셰이크로 **매번 새로** 만든다 | **어딘가에 계속 있어야** 복호할 수 있다 |
| 상대 | 상대가 있다 | **미래의 나 자신** |
| 제약 | — | **DR-1(설정 0개)** — 사용자에게 비밀번호를 물을 수 없다 |

> **핵심 난제**: 비밀번호를 받지 않는데 **키를 어디에 두는가.** 키를 데이터 옆에 두면 "잠그고 열쇠를 문에 꽂아 둔" 셈이 된다 — 그런데도 **의미가 있다.** 무엇을 막고 무엇을 못 막는지 [§2](#2-위협-모델--무엇으로부터-보호하는가)에서 정직하게 가른다.

## 3. ① 키 관리

### 후보

| 안 | 방식 | 막는 범위 | DR-1 | DR-4 포터블 | 판정 |
|---|---|---|:--:|:--:|:--:|
| **A. 기기 키 파생** | 신원 키 파일에서 KDF로 저장 키 유도. **입력 0** | H-1~H-4 | ✅ | ✅ | **✅ 기본** |
| **B. OS 보안 저장소** | Keychain(mac) · DPAPI(Win) · Secret Service(Linux)에 저장 키 보관 | + **H-5 상당 부분** | ✅ | ❌ **깨진다** — 기기에 묶여 USB 이동 불가 | ✗ **실격(08-17 사용자 확정 — 아래 §3-1)** |
| **C. 사용자 암호** | passphrase → KDF | + **H-5 강하게** | ❌ 위반 | ✅ | ✗ **실격(08-17 사용자 확정 — 아래 §3-2)** |
| D. 암호화 안 함 | — | 없음 | ✅ | ✅ | ✗ 요구 위반 |

### ✅ 결정 — **A 기기 키 파생 단일** · **B·C 승격 둘 다 실격** (★ §3 사용자 확정 08-11 · B·C 실격 08-17 — 재검토는 Managed Server 모드에서)

> **구현(M2-5a · 08-11)**: `crypto::keyfile`(신원 키 영속 — 정확히는 §3의 전제) +
> `nbeep-store::FileTrustStore`(핀 세그먼트 — 마스터 무작위 생성·래핑 한 겹·AEAD·
> fail-closed 잠김). 래핑 KDF는 SHA-256(솔트‖기기 키) — **원료가 256비트 무작위
> 키라 메모리-하드가 불필요**(메모리-하드 KDF는 승격 ②(사용자 암호)에서만 필요).
> 신원 키 **백업·복원**(설정 ▸ 프로필 · 폴더/파일 탐색 피커 · 복원 = 핫 로딩)도 08-11 구현.

```
기본(입력 0):        기기 신원 키 ──KDF──► 래핑 키 ──감쌈──► 마스터 저장 키(무작위 생성)
승격 ①(기기 고정):   OS 보안 저장소에 래핑 키 보관        ← ✗ 실격(08-17 · 포터블 정체성 파괴)
승격 ②(암호 보호):   사용자 암호 ──KDF──► 래핑 키          ← ✗ 실격(08-17 · 제로컨피그 위반 · Managed Server서 재검토)
v2(백업·기기 이전):  사용자 보관 백업 키 ──► 래핑 키        ← X-7에서 설계
```

> ⚠️ **`UserId` 키(ADR-0007)는 래핑 후보가 아니다** — 서명 능력과 복호 능력을 **분리**하기로 확정했다([20 §9-1](20-adr-0007-multi-device-identity.md)). `UserId` 키가 탈취돼도 **과거 기록은 열리지 않는다.**

> **개정(08-08 · [DR-20](10-decision-record.md) V1-4) — 마스터 키를 기기 키에서 "직접 파생"하지 않는다.**
> 마스터 키는 **무작위로 생성해 래핑 키로 감싸고**, 기기 키·OS 저장소·사용자 암호·(v2)`UserId` 키는 **래핑 키만** 만든다.
> 직접 파생이면 보호 수준을 바꿀 때마다 **전 기록을 재암호화**해야 하고, [ADR-0007](20-adr-0007-multi-device-identity.md)의 다중 기기는 **아예 불가능**해진다. 지금은 간접 한 겹의 비용뿐이다.

### 3-1. 승격 ①(OS 보안 저장소) 실격 (★ 08-17 사용자 확정)

**결정: 승격 ①(Keychain/DPAPI/Secret Service)은 구현하지 않는다.** 오프라인
디스크 탈취(H-5)를 막는 이득보다 **이 제품의 정체성을 깨는 대가**가 크다.

- **DR-4 포터블 파괴(치명)** — OS 저장소는 기기에 묶인다(그게 보안의 원천).
  wrap_secret을 옮기면 USB를 다른 PC로 옮겼을 때 `trust.seg`·`profile.sec`·
  `.beepq`·사진 캐시가 **전부 안 열린다**. "가끔 프롬프트"가 아니라 **포터블
  실행이 원리적으로 불가**. 3신원 폴더 이동 실기도 깨진다.
- **백업/복원 반쪽화(M2-5a 충돌)** — `data/` 폴더 백업이 복호 능력을 담지
  못해, 다른 기기 복원 시 못 연다(사용자가 "백업했다"고 믿는데 반쪽 — 유실).
- **무서명 앱 반복 프롬프트(mac)** — 키체인 ACL은 서명 신원에 묶이는데 현
  앱은 무서명(M5-4a 미완). 재빌드마다 "다른 앱"으로 보여 **개발·배포 내내
  프롬프트/거부**. 서명 선행 없이는 실용 불가.
- **Linux 백엔드 불확정** — Secret Service 부재(헤드리스·SSH·미니멀 WM)면
  파일 폴백이라 이득 0, 있어도 첫 접근 프롬프트 가능(3-OS 대칭 실패).
- **키체인 손상 = 영구 유실 위험** — 파일과 달리 사용자가 눈에 보이게 백업
  하기 어렵다. OS 재설치·키체인 초기화 시 봉인 전부 복호 불가.

### 3-2. 승격 ②(사용자 암호 래핑) 실격 (★ 08-17 사용자 확정)

**결정: 승격 ②도 구현하지 않는다. 저장 암호화는 A(기기 키 파생) 단일로
확정한다.** ②는 포터블·백업·무서명 문제가 없어 ①보다 낫지만, **DR-1(제로
컨피그 = "실행 = 참여")과 정면 충돌**한다:

- **입력 0 정체성 위반** — "서버 주소·계정·등록이 전부 없다"가 DR-1인데,
  ②는 **앱 시작마다 암호 입력**을 요구한다. 제로컨피그 메신저에 로그인
  단계를 되살리는 셈 — 정체성을 스스로 무너뜨린다.
- **분실 = 영구 유실** — 암호를 잊으면 기록 복구 불가(§3 규칙 표의 대가).
  복구 코드 보관을 또 요구하면 제로컨피그에서 더 멀어진다.
- **막는 위협(H-5)의 실효** — 오프라인 디스크 탈취는 **FileVault/BitLocker
  (전체 디스크 암호화) + OS 계정 보안**의 몫이지 앱 계층의 몫이 아니다.
  앱이 암호 한 겹을 더 얹는 것은 이 제품(LAN 로컬 메신저)의 위협 모델에서
  비용 대비 이득이 낮다.

**A 단일로 확정** — 저장 봉인은 기기 신원 키 파생(입력 0)만. [§2](#2-위협-모델--무엇으로부터-보호하는가)
표대로 우발적·수동적 노출(H-1~H-4)은 막고, **기기 통째 탈취(H-5)는 앱이
막지 않는다**고 UI·문서에 정직하게 명시한다(과장 금지).

> **재검토 조건 — Managed Server 모드**(사용자 확정 08-17): [ADR-0013 모드
> ②/③](32-adr-0013-server-modes.md)처럼 **서버가 신원·기록을 아는** 구동
> 형태가 생기면, 그때는 위협 모델·키 관리 전제가 달라진다(다중 사용자·원격
> 저장·기기 이전). 승격 ②(및 그때의 키 계층)는 **그 시점에 재검토**한다 —
> v1 로컬 서버리스 범위에서는 A 단일이 맞다.



| 규칙 | 내용 |
|---|---|
| KDF | 메모리-하드 KDF(솔트는 기기별 생성). 파라미터는 M2에서 실측 후 고정 |
| **키 계층** | 마스터 키 → **대화별(또는 세그먼트별) 데이터 키**를 파생. [§7 크립토 셰레딩](#7-보존--삭제--크립토-셰레딩)의 전제 |
| 승격 전환 | 언제든 켜고 끌 수 있다. **마스터 키를 다시 감싸기만** 하면 되므로 데이터 재암호화 불필요 |
| 승격 ②의 대가 | 암호를 잊으면 **기록은 복구 불가.** 경고를 명시하고, 원하면 복구 코드를 사용자가 직접 보관 |
| 표시 | 설정 화면에 **현재 보호 수준과 "무엇을 막지 못하는가"** 를 문장으로 |

> **A가 "의미 없다"는 반박에 대해** — 키가 옆에 있으니 무의미해 보이지만, 실무 유출의 대부분은 H-1(동기화 폴더·백업에 딸려 감)과 H-4(폴더째 전달)다. **이 경로에서는 키 파일이 함께 가더라도 그것을 읽어 복호할 도구와 의도가 있어야** 한다. 평문 저장과는 위험 수준이 다르다. 다만 **과장하지 않는다** — [§2](#2-위협-모델--무엇으로부터-보호하는가) 표를 UI에도 그대로 노출한다.

## 4. ② 저장 구조

### 암호화 범위

| 대상 | 암호화 | 이유 |
|---|---|---|
| **메시지 본문(Text)** | ✅ | 요구의 핵심 |
| **이미지·파일 페이로드**(대화에 남는 것) | ✅ | 본문과 동급 |
| 발신/수신 시각·방향·시퀀스 | ✅ | 내용의 일부로 취급 |
| **상대 `PeerId`** | ✅ | 누구와 대화했는지도 보호 대상 |
| 표시 이름 | ✅ | |
| **전문 검색 인덱스** | ✅ | 인덱스는 내용의 사본이다([§5](#5--전문-검색--암호화와의-충돌)) |
| **TOFU 핀 목록** | ✅ **(정정 08-09)** | ⚠️ **초판은 `✕`("공개키라 암호화 이득 없음")였다 — 혼동이었다.** 키 자체는 비밀이 아니지만 **"내가 그 키를 안다"는 사실은 비밀**이다. 핀 파일은 곧 **내가 아는 상대 `PeerId` 전체 목록**이라, 평문이면 바로 윗줄("상대 `PeerId` ✅ — 누구와 대화했는지도 보호 대상")이 **무의미해진다**. H-1(동기화 폴더)·H-4(폴더째 전달)에서 대화는 안 열려도 **인간관계는 그대로 읽힌다** |
| 설정(테마·언어) | ✕ | 민감하지 않음 · 복호 실패 시 진입 불가 방지 |
| **계측 레저** | ✅ | 내용은 없지만 **행위 패턴**이 남는다([13 §6](13-code-design-standards.md)) |

#### ⚠️ 그럼에도 "부팅 초기 필요"는 진짜 제약이다 — 별도 세그먼트로 푼다

핀은 **세션이 서기 전에** 조회돼야 한다. 그래서 기록 본문과 **분리된 작은 세그먼트**에 두고, 마스터 키를 얻는 즉시(기록 인덱스보다 먼저) 연다.

| 보호 수준([§3](#3--키-관리)) | 부팅 시 핀을 열 수 있나 | 못 열 때의 처리 |
|---|:--:|---|
| **기본**(기기 키 파생 · 입력 0) | ✅ 열린다 — 사용자 입력이 필요 없다 | — |
| 승격 ①(OS 보안 저장소) | ✅ 대체로 열린다 | 저장소 접근 실패 시 아래와 동일 |
| 승격 ②(사용자 암호) | ❌ **암호 입력 전에는 못 연다** | ★ **fail-closed** — 전부 `Unverified`로 취급하고 **"신뢰 목록 잠김"을 표시**한다 |

> ★ **핀을 못 읽었을 때 "핀이 없다 = 처음 보는 상대"로 조용히 넘어가면 안 된다.** 그러면 **재핀이 일어나 이력이 오염**되고, 사용자는 자기가 이미 검증한 상대를 다시 검증하게 된다. **모르는 것과 없는 것을 구분**해야 한다.

### 세그먼트 구조

```
segment {
  header  { magic, ver, key_id, nonce_base, created_at }   ← 평문(라우팅용)
  records [ AEAD( record_plaintext, aad = header ‖ seq ) ] ← 개별 봉인
  footer  { record_count, mac }
}
```

| 규칙 | 내용 |
|---|---|
| 알고리즘 | **전송과 같은 AEAD 계열**(ChaCha20-Poly1305) — 스택 하나 더 들이지 않는다(DR-5) |
| 논스 | `nonce_base ‖ seq` — **재사용 금지**를 구조로 보장. 세그먼트 회전 시 새 base |
| **AAD** | 헤더 + 시퀀스를 인증 데이터로 → **레코드 재배치·삭제 탐지** |
| 단위 | 레코드 단위 봉인 → **부분 손상 시 그 레코드만 잃는다**(파일 전체 손실 방지) |
| 회전 | 크기·기간 기준으로 세그먼트 분할. 오래된 세그먼트는 [§7](#7-보존--삭제--크립토-셰레딩) 대상 |
| 첨부 | 큰 페이로드는 별도 블랍 파일로 두고 **레코드에는 참조 + 블랍 키**만 |

### 4-a. 구현 ✅ — 범용 로컬 봉투 `sealed` (08-17 · 사용자 승인 "평문 3면 조치")

> **이 절은 구현 기록이다** — §4의 저장 구조 본체(대화 기록 세그먼트)는 M2-5b
> 몫으로 남아 있지만, 그 전에 발견된 **로컬 평문 3면**(격리물 `.beepq` ·

> 코드 = [`nbeep-store/src/sealed.rs`](../crates/nbeep-store/src/sealed.rs) ·
> M2-5b 기록 세그먼트도 이 봉투 문법을 그대로 이어 쓰면 된다.
>
> ★ **08-21 전수 실측 감사 ✓**(실기 GUI 데이터 2신원 — 파일 매직 + strings 평문
> 탐색): 대화 기록 1:1/그룹(`history/*.seg`·`g-*.seg`) · 오프라인 대기
> (`pending/*.seg`) · 격리물+사이드카(`.beepq`/`.beepq.meta` — 64MiB 실파일 포함) ·
> PII 사이드카(`profile.sec`) · 상대 사진 캐시(`profiles/*.img`) = **전부 NBSE
> 암호문**, 핀·이름 이력(`trust.seg` NBTS)·그룹 roster(`groups.seg` NBGS)도 암호문 ·
> **가독 평문 흔적 0**. 평문으로 남는 것(의도된 경계) = 설정값(`settings.cfg` —
> PII는 사이드카 분리) · `identity.key`(계층의 루트 — 자기 자신으로 봉인 불가) ·
> `profiles/*.meta`(내장 아바타 키+보더색 2줄 — 비PII) · 로그(상태 문구·계수만 —
> 봉투 원리). 관찰 = **본인 축 평문 3종**(내 사진 축소본·custom 사본·클립보드
> 스테이징)은 수신 위협 모델 밖 — 처리 검토 = TODO SEAL-2.

#### 봉투 형식 (파일 바이트 배치)

```text
"NBSE"(4) ‖ ver(1 = 0x01) ‖ salt(16) ‖ nonce(12) ‖ 암호문+Poly1305 태그(16)
└──────── 헤더(평문·AAD 편입) ────────┘
```

- **salt·nonce는 봉인 때마다 OS CSPRNG(getrandom)로 새로** 뽑는다 — 같은
  평문도 매번 다른 봉투(파일 비교로 내용 추측 불가). salt가 키 유도에
  들어가므로 **파일마다 키 자체가 다르다** — nonce 재사용 걱정이 구조적으로
  없다(같은 키로 두 번 봉인하는 일이 없다).

#### 키 유도 — 신원 파생 + 도메인 분리

```text
키 = SHA-256("nexa-beep/adr-0005/sealed-v1" ‖ domain ‖ salt ‖ wrap_secret)
```

- `wrap_secret` = **신원 개인키 32B 그대로**(§3 기본 A "기기 키 파생" —
  256비트 무작위 원료라 메모리-하드 KDF 불필요 · 암호(passphrase)가 아니다).
  `identity.key`(0600)가 곧 이 계층의 루트다 — §3의 계층 그림 그대로.
- **domain** = 파일 종류 태그. 현재 3종: `quarantine-v1`(격리물) ·
  `pii-v1`(연락처 사이드카) · `profile-cache-v1`(상대 사진 캐시).
  도메인은 **키 유도와 AAD 양쪽**에 들어간다 — 격리물 봉투를 사이드카
  자리에 복사해 넣는 **바꿔치기가 두 겹에서 실패**한다.

#### 암호화(봉인) 절차 — `sealed::seal(domain, secret, plain)`

1. salt(16)·nonce(12)를 OS 난수로 생성 — 실패 = 에러(봉인 포기).
2. 헤더(`NBSE`‖ver‖salt) 조립 → **AAD = 헤더 ‖ domain**.
3. 위 식으로 키 유도 → ChaCha20-Poly1305 `encrypt(nonce, 평문, AAD)`.
4. 헤더 ‖ nonce ‖ 암호문(+태그 16B)을 파일에 원자적으로 기록.
5. **어느 단계든 실패 = 평문으로 쓰는 폴백 없음**(fail-closed 원칙 —
   격리물은 저장 포기, 캐시는 캐시 포기, PII는 상태바 경고).

#### 복호화(개봉) 절차 — `sealed::open(domain, secret, bytes)`

1. 매직·버전 검사(`NBSE`·0x01) — 아니면 None.
2. 파일의 salt로 **키 재유도**(호출자의 domain·secret 사용).
3. AAD 재조립 후 `decrypt` — **Poly1305 태그가 기밀성과 무결성을 동시 검증**:
   다른 신원의 secret, 다른 domain(바꿔치기), 1비트 변조 전부 여기서 None.
4. None이면 **평문인 척 읽지 않는다** — 호출자는 값을 비우고 소리 낸다.

#### 면별 배선 — `profile.sec`(PII)를 예로

- **평문 내용**: `profile.email\t값\n profile.phone\t값` 줄 형식.
- **쓰기**: 설정 저장 사이클(SaveScheduler quiet/max-delay + 종료 flush)마다
  ① settings.cfg의 known 목록에서 두 키를 **제외**(구본 평문은 저장 1회로
  파일에서 소거) ② 현재 값을 위 절차로 봉인해 `data/profile.sec`에 기록 ③
  **두 값이 전부 비면 파일 삭제**(철회 대칭 — 빈 봉투를 남기지 않는다).
- **읽기**: 부팅 시 개봉 → 메모리 설정 Entry에 주입(화면·프로필 전파 경로
  무변경). 개봉 실패(다른 신원·손상) = 값 비움 + 상태바 안내.
- 격리물은 저장/읽기 관문(`gate::read_beepq_bytes`) 단일화 + **구본 lazy
  재봉인**(목록 열람·부팅 복원 때 평문 발견 = 즉시 봉인 재기록)으로 이관.

#### 보안 성질 요약

| 위협 | 방어 |
|---|---|
| 디스크·백업 유출(§2 위협 모델) | AEAD 기밀성 — identity.key 없이는 열 수 없다 |
| 파일 변조·절단 | Poly1305 태그(무결성) — 1비트도 fail-closed |
| 파일 종류 간 바꿔치기 | 도메인 분리(키 유도+AAD 이중) |
| 같은 평문의 파일 간 대조 | salt·nonce 매회 신선 — 봉투가 매번 다르다 |
| 한계(명시) | `identity.key` 탈취 = 계층 루트 탈취(§3 승격 ①②가 그 답 — OS 키체인·암호 래핑) |

## 5. ③ 전문 검색 — 암호화와의 충돌

**여기가 이 ADR에서 가장 어려운 부분이다.** FR-M-4는 전문 검색을 요구하는데, 평문 인덱스를 만들면 **암호화가 무의미해진다**(인덱스는 내용의 사본이다).

### 후보

| 안 | 방식 | 평가 |
|---|---|---|
| **A. 인덱스 전체 암호화 + 메모리 로드** | 검색 시 통째로 복호 | 소규모엔 되지만 **RSS 예산(NFR-B-1 ≤30MB)** 을 위협. 대화가 쌓일수록 무너진다 |
| **B. 블라인드 인덱스** | 토큰을 `HMAC(index_key, 정규화 토큰)` 으로 저장 | **역색인이 암호화된 채로 검색 가능.** 등가 일치는 빠름. 부분 일치는 토큰 설계로 해결 |
| C. 순차 복호 스캔 | 인덱스 없이 전부 복호하며 훑기 | 정확하지만 느리다 |
| D. 검색 포기 | — | FR-M-4 위반 |

### ✅ 결정 — **B(블라인드 인덱스) + C(폴백)**

```
저장 시:  본문 → 정규화 → 토큰화 → HMAC(index_key, token) → 역색인에 기록
검색 시:  질의 → 같은 정규화·토큰화 → HMAC → 역색인 조회 → 후보 세그먼트만 복호 → 정밀 대조
```

| 항목 | 설계 |
|---|---|
| **한국어 토큰화** | 형태소 분석기는 **크기 예산상 불가**(사전이 수 MB) → **음절 n-gram**(2~3-gram)을 기본으로. 영문·숫자는 단어 단위 + 접두 n-gram |
| **부분 일치** | n-gram이 접두·중간 일치를 흡수한다 |
| **정밀 대조** | 역색인은 **후보를 좁히는 용도**. 최종 일치 판정은 **후보 세그먼트를 복호해 확인**(오탐 제거) |
| 하이라이트 | 복호한 후보에서만 수행 |
| 폴백 | 인덱스 손상·미구축 시 **C(순차 복호 스캔)** 로 동작. 느리지만 결과는 정확 |

### ⚠️ 블라인드 인덱스가 새는 것 (정직하게)

| 누출 | 설명 |
|---|---|
| **토큰 빈도** | 어떤 토큰이 몇 번 나왔는지가 인덱스 크기·분포로 드러난다 → 빈도 분석 가능 |
| 문서 길이 | 대략적 길이가 추정된다 |
| 완화 | 인덱스 자체도 [§4](#4--저장-구조) 세그먼트로 암호화 · 포스팅 리스트 패딩(선택) |
| 판단 | H-5(기기 탈취)가 이미 성립한 상황에서만 의미 있는 누출이다. **기본 위협 모델(H-1~H-4)에서는 영향 없음** |

## 6. ④ 외부 노출 방지

*"외부로 노출되지 않아야 한다"* 를 구체 규칙으로.

| **2** | **동기화 폴더 감지** — 데이터 경로가 알려진 클라우드 동기화 폴더(OneDrive·iCloud Drive·Dropbox·Google Drive) 안이면 **경고**하고 대안 위치를 제안. H-1 정면 대응 |

| **4** | **크래시 덤프 최소화** — 코어 덤프 비활성 시도 · 패닉 메시지에 내용·경로 금지 |
| **5** | **메모리 위생** — 복호 평문 버퍼는 사용 후 **즉시 zeroize**. 오래 들고 있지 않는다. ⚠️ **스왑 방지(mlock)는 T0 무권한에서 보장할 수 없다** — 완화일 뿐임을 명시 |
| **6** | **클립보드** — 복사는 사용자 행위. 자동 복사 없음 |
| **7** | **내보내기는 명시적 행위** — 무엇이 포함되는지 보여주고, 기본은 **암호화된 형태**로. 평문 내보내기는 별도 경고 + 재확인 |
| **8** | **미리보기 캐시 금지** — 이미지 썸네일도 암호화 저장. 임시 폴더에 평문을 쓰지 않는다 |
| **9** | 검색 질의·최근 항목도 **평문으로 남기지 않는다** |

## 7. ⑤ 보존 · 삭제 — 크립토 셰레딩

**디스크에서 파일을 지워도 실제로 지워졌다고 보장할 수 없다** — SSD의 웨어 레벨링·TRIM 타이밍·저널링 때문에 덮어쓰기가 원본 블록에 닿지 않을 수 있다. 이건 애플리케이션이 해결할 수 없는 문제다.

> **해법: 데이터를 지우는 대신 키를 지운다(crypto-shredding).**
> [§3](#3--키-관리)에서 **대화별·세그먼트별 데이터 키**를 파생하도록 설계한 이유가 이것이다. 키를 폐기하면 남은 바이트는 **복호 불가능한 난수**가 된다.

| 동작 | 구현 |
|---|---|
| 대화 삭제 | **그 대화의 데이터 키 폐기** + 세그먼트 파일 삭제 |
| 기간 만료 | 해당 세그먼트 키 폐기 |
| **전체 초기화** | **마스터 키 폐기** → 모든 기록이 즉시 무의미해진다 |
| 키 폐기 자체 | 키 저장소는 작아서 덮어쓰기가 유효할 확률이 높지만, **보장하지 않는다**고 명시 |
| 보존 기간 | 기본값은 M2에서. **무제한도 선택 가능**(사용자 데이터다) |

## 8. ⑥ 서버 모드와의 관계

사용자가 짚은 지점 — *"일반적으로 서버 모드면 서버 관점에서 보관되는 대상"*.

| | 일반 서버형 메신저 | **Nexa Beep** |
|---|---|---|
| 기록 보관 주체 | 서버 | **각 클라이언트** |
| 서버가 내용을 보는가 | 대개 본다 | **못 본다**(FR-R-3 — 릴레이는 봉투만) |
| 기기 바꾸면 | 서버에서 내려받음 | **기록도 함께 사라진다** |

> **릴레이 모드(v2)가 생겨도 기록은 여전히 클라이언트에만 있다.** 릴레이가 평문을 못 보므로(DR-7) 구조적으로 서버 보관이 불가능하다.
>
> ⇒ **다중 기기 동기화·기기 이전은 v1 범위 밖**이며, 하려면 **E2E 암호화 백업**(사용자가 키를 쥐는)이라는 별도 설계가 필요하다. 포스트 v1 항목으로 등록한다. **지금 이 한계를 문서와 UI에 명시**해 두지 않으면 "기기 바꿨더니 대화가 없어졌다"가 결함으로 접수된다.

### 개정 (08-08 · [DR-20](10-decision-record.md) — 다중 기기)

**"서버 모드면 되나"에 대한 답은 여전히 아니오다.** 릴레이는 **도달**을 풀 뿐 **동일인·이력 공유**를 풀지 않는다([20 §1](20-adr-0007-multi-device-identity.md)).

| 항목 | 처리 |
|---|---|
| **새 메시지**를 여러 기기가 같이 받기 | ✅ **팬아웃으로 해결**(v2) — [20 §2](20-adr-0007-multi-device-identity.md) |
| **과거 기록**을 새 기기가 보기 | ❌ 팬아웃으로 안 된다. **§3 래핑 키에 사용자 보관 백업 키를 추가**하는 별도 설계가 필요하다(X-7). ⚠️ **`UserId` 키로는 열지 않는다**([20 §9-1](20-adr-0007-multi-device-identity.md)) |
| 서버 보관 | ❌ **여전히 불가능** — 릴레이가 평문을 못 보는 성질은 DR-20으로도 바뀌지 않는다 |

> ⇒ **v1은 §3의 래핑 한 겹만 확보**한다(V1-4). 그것이 없으면 v2에서 **전 기록 재암호화**가 된다.

## 9. 예산 영향 (DR-5)

| 항목 | 영향 | 통제 |
|---|---|---|
| 크기 | AEAD·KDF는 **전송에서 이미 쓰는 것 재사용** → 추가 거의 없음 | 스택 하나로 통일 |
| 메모리 | 복호 캐시 · 인덱스 페이지 | **상한 있는 LRU.** 캐시는 유휴 시 비운다(NFR-B-1) |
| CPU | 저장·검색 시 암복호 | 배치 처리 · UI 스레드에서 금지([01 §3](01-architecture.md)) |
| 디스크 | 인덱스 + 태그·논스 오버헤드 | 세그먼트 회전 + 롤업 |
| 시작 시간 | 마스터 키 파생(KDF는 의도적으로 느리다) | **KDF는 1회**, 결과를 세션 동안 보유. NFR-B-11(콜드 스타트 ≤500ms)와 충돌하면 **파라미터를 실측으로 조정** |

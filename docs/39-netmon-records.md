# 39. 네트워크 점검 기록부 — netmon 분석 리포트 (2026-08-21 개설)

> **살아 있는 기록 문서.** 주기 점검(netmon — 설계 [06 §7-1](06-network-stack.md) ·
> 절차 [26 §3-5](26-run-and-manual-test.md))을 돌릴 때마다 **§3에 회차를 시간
> 역순으로 append**한다. §1·§2는 방법·기준선의 SSOT — 새 회차는 여기 수치와
> 대조해 이상 여부를 판정한다. 규약: **수치 없는 "잘 됐다"는 기록이 아니다**
> ([06 §7](06-network-stack.md)).

## 1. 수집·판독 방법 (요약)

- **켜는 법 둘**: ① GUI 설정 ▸ 고급 ▸ 네트워크 점검(`netmon.enabled` · 주기
  `netmon.interval_s` 기본 10s) → `data/logs/netmon-YYYYMMDD.log` ② 어느 모드든
  환경변수 `NEXA_NETMON=<파일>`(+`NEXA_NETMON_SEC` 기본 5s) — 자동 실기·CLI용.
- **줄 포맷**(안정 계약 — 파서 대상): `[unix초] netmon dt_ms=… dtx=… drx=…
  dself=… co=… cok=… ci=… stxf=… srxf=… stxb=… srxb=…[ warn=태그,…]`
- **열 읽는 법**:

| 열 | 뜻 | 과다의 신호 |
| --- | --- | --- |
| dtx / drx | 발견 데이터그램 발신/수신 | 광고 폭주(임계 25/100pps → `warn=disco_*_pps`) |
| dself | 수신 중 자기 멀티캐스트 에코 | 인터페이스 중복 발신·루프 |
| co / cok / ci | 아웃바운드 시도/성립 · 인바운드 수락 | co≫cok = 재연결 폭풍·죽은 후보 (분당 30회 → `warn=conn_rate`) |
| stxf / srxf | 세션 프레임 발신/수신 | 메시지 수 대비 과다 = 제어 프레임 낭비 |
| stxb / srxb | 세션 바이트(프레임 헤더 4B 포함) | 파일 전송 중이 아닌데 큰 값 |

- **판정 원칙**: 절대값이 아니라 **§2 기준선과의 배율**로 본다(환경·상대 수에
  비례하는 축이 있다 — dtx는 인터페이스 수, drx는 이웃 수에 비례).

## 2. 기준선 (2026-08-21 · 1회차 실측 — Windows 11 · 같은 PC 2-인스턴스)

| 상황 | 기대 수치(5초 구간) | 근거 |
| --- | --- | --- |
| 발견 대기(광고) | dtx 18~21(**≈3.7pps**) · 편차 ±1회 발신분 | 광고 0.8s × 경로 ~3(기본 멀티캐스트+브로드캐스트+IF별) + 12.8s 주기 S4 |
| 자기 에코 | dself ≈ dtx (수신의 절반) | same-PC 멀티캐스트 루프백 on(다중 인스턴스 발견용 — 의도) |
| 유휴 세션 | stxf/srxf **0** | keepalive는 OS TCP 계층 — 앱 프레임 없음 |
| 1:1 메시지 | 발신 **85B**/건 + 수신 ack 62B(전달+읽음 2프레임) | ChatMessage 봉투 42B+본문 · ChatAck |
| 세션 성립 직후 | 1회성 ~70KB 양방향 | 프로필(아바타 축소본) 교환 — 설계 비용 |
| 파일 전송 | 프레임당 **≈32.8KB**(= 32KiB 청크+헤더) · 반대 축 침묵 | 청크 32KiB · 오버헤드 실측 0.25% |
| 연결 | 사용자 행위당 co 1 · /quit 후 co **0** | 의도 종료는 재연결 안 함 |

## 3. 점검 기록 (시간 역순)

### 3-1. 2026-08-21 — 1회차: 10분 자동 시나리오 (기준선 수립 · 사용자 요청)

**환경** — Windows 11 · 같은 PC 격리 신원 2개(포터블 exe 복사 = `data/` 분리 ·
A=47301·B=47302) · 디버그 빌드 · 다른 인스턴스 0 · `NEXA_NETMON_SEC=5`.
**시나리오** — P1 발견 대기 210s(chat-live×2) → P2 315s(chat-serve/connect:
접속 → B 메시지 20건(4s 간격)+A 5건(10s 간격) → B `/send` 64MiB(무작위 바이트) →
A 19초 뒤 `/accept` → 유휴 → B `/quit` → 종료 후 60s 관찰).

**P1 — 발견 대기(광고·상호 발견)** · 합계(A 기준 205s): dtx=767 · drx=1,530 ·
dself=765 · 세션/연결 0 · **warn 0**

```text
[1787272855] netmon dt_ms=5000 dtx=21 drx=39 dself=21 co=0 cok=0 ci=0 stxf=0 srxf=0 stxb=0 srxb=0
[1787272860] netmon dt_ms=5000 dtx=18 drx=39 dself=18 co=0 cok=0 ci=0 stxf=0 srxf=0 stxb=0 srxb=0
```

- 발신 3.7pps — 임계(25pps)의 15%. 42개 구간 전체 18~21로 평탄(드리프트 0).
- drx = 자기 에코 765 + 상대 광고 765로 정확 대칭. 패킷이 소형이라 발견 대역
  ≈ **1KB/s 미만**.

**P2 — 세션 축** · A(수신) 합계: srxf=2,088 · srxb=67,277,640 · B(발신) 대칭 ·
co=1/cok=1/ci=0 · **warn 0**

| 구간 | 대표 실측(5s) | 해석 |
| --- | --- | --- |
| 성립(t+6) | `co=1 cok=1 stxf=7 stxb=70318 srxb=70314` | 연결 1회 + 프로필 교환 70KB 양방향(1회성) |
| 채팅 | `stxf=1 stxb=84 srxf=2 srxb=62` | 메시지 1건 = 85B · 되돌아오는 ack 2프레임 62B — 과다 0 |
| 유휴(30s+) | 전 열 0 | 세션 앱 프레임 0 |
| 파일 요청 | `stxf=2 stxb=130` | Offer+manifest 2프레임 130B — 승인 대기 15s 동안 0 |
| 전송 피크 | 발신 `stxf=954 stxb=31305510` / 수신 `srxf=955 srxb=31338325` | **6.2MB/s** · 31.3MB/954프레임 = 32.8KB(32KiB 청크 그대로) |
| 종단 | `srxb=39` 1건 | 수신 확인 ack — 이후 /quit까지·후 **co 0** |

- **64MiB ≈ 12초 완주**(디버그 빌드·localhost · Auto 페이싱 = 관측 절반).
  총 오버헤드 = 67,277,640 − 67,108,864 = **168,776B(0.25%)** — 프레임 헤더
  4B×2,088 + 제어 + 프로필 70KB. 프로필 제외 시 **0.15%**.
- 전송 중 발견·연결 축 완전 침묵 — 축 간 간섭 없음.

**판정** — **과다 송수신 없음.** 발견·채팅·파일·종료 전 축이 설계 기대치와
일치. 4개 로그(2신원×2페이즈) 전 구간 `warn=` 0건.

**한계(정직)** — 같은 PC·localhost라 ① 실제 무선망의 손실·지연 미반영
② dself 비율은 2-PC 환경에선 달라진다(내 에코만 남고 상대분은 실링크 경유)
③ 디버그 빌드 속도는 하한 참고치. **다음 회차 후보 = 2-PC 같은 망**(Win↔Mac ·
release 빌드)로 동일 시나리오 재실측.

> 원본 로그 4종(nm-a1/b1/a2/b2)은 세션 임시 폴더 산출물 — 수치는 본 절에 전량
> 요약했고, 회귀 비교는 §2 기준선 표가 SSOT다. 다음 회차부터는 이상 구간이
> 있을 때만 해당 로그 원문을 이 문서에 첨부한다.

# 49 — 점검 체계(Inspection Framework) — 메신저 일반 + Nexa Beep 고유 · 주기·OS별

> **상태**: 📐 체계 확정 제안(09-26 · 사용자 요청) · **살아 있는 문서** — §9 회차 기록은 시간 역순 append.
> **위치**: 4층 문서 체계의 **절차 층**. 수치 기준(SSOT)은 [05 §2-1](05-requirements.md)이고, 개별 절차 SSOT는 [18](18-build-and-test.md)(빌드·CI) · [26](26-run-and-manual-test.md)(수동 실기) · [39](39-netmon-records.md)(네트워크 기록부) · [29](29-wire-security-audit.md)(와이어 보안)이다. **이 문서는 그것들을 한 표로 묶고, 빠진 축을 채우고, 주기·OS를 배정한다.** 여기서 새 수치를 만들지 않는다.
> **읽는 순서**: §1 원칙 → §2 축 목록 → §3 항목 표(축별) → §4 주기 매트릭스 → §5 OS별 도구 → §6 분석 기법 → §7 자동화 상태·로드맵 → §8 기록 양식 → §9 회차 기록.

## 0. 왜 이 문서인가

사용자 요청(09-26): *파일 용량·실행 속도·최초 로딩·브로드캐스트·송수신·서버 연결 시점과 유지·메모리 할당/회수·신뢰 등급별 메시지/파일·와이어/저장 암호화·서버 경유/LAN 경유 통신·자료 구조·표현계층 어댑터 … 메신저 일반 점검과 이 프로그램 고유 점검을 체계화하고, 분석 기법을 정리해, 주기적으로·OS별로 점검할 수 있게.*

지금까지 점검은 **있었지만 흩어져 있었다** — 예산 게이트는 05, 절차는 18·26, 네트워크 기록은 39, 보안 트리거는 TODO §9, 실기 항목은 journal. 그래서 ① 같은 항목을 세션마다 다시 발명하고 ② 어떤 축이 **한 번도 측정되지 않았는지**(예: 콜드 스타트 NFR-B-11 · 유휴 CPU NFR-B-7 · 24h 누수 NFR-B-6)를 아무도 못 봤다. 09-17의 교훈(**불변식은 검증이 붙어야 지켜진다** — NFR-B-5가 15번의 릴리스를 그냥 지나갔다)이 이 문서의 직접 동기다.
